sdcreds — systemd credentials, without systemd

go-authn/sdcreds reads and writes the systemd credential format (systemd-creds encrypt and decrypt) from Go, with a command line and an s6 helper that gives a supervised service its $CREDENTIALS_DIRECTORY.

What if a service needs the credentials a systemd unit gets fromLoadCredentialEncrypted=, and there is no systemd? sdcreds reads and writes the systemd credential format(systemd-creds encrypt / decrypt) from Go, with a command line and a helper that gives an s6-supervised service the same $CREDENTIALS_DIRECTORY.

Supported keys: null, host (/var/lib/systemd/credential.secret) andhost-scoped (--uid / --user). TPM2 and public-key credentials are recognised and refused with *UnsupportedModeError; nothing is guessed.

Install 

go install github.com/go-authn/sdcreds/cmd/sdcreds@latest

The version these pages describe is v0.4.2. 32-bit OpenBSD (i386, armv7) is refused: the build fails on purpose, because the mount layout (mfsArgsSize 144 and the mount structures) is the LP64 one of amd64 and arm64 and has not been checked against the 32-bit headers.

Command line 

sdcreds setup                                  # create the host secret if missing
sdcreds encrypt --name=db-password plain.txt db-password.cred
sdcreds decrypt db-password.cred -             # the name must match the file name

The same from Go:

host := sdcreds.HostKeyFile{} // $SYSTEMD_CREDENTIAL_SECRET or the default path
blob, err := sdcreds.Encrypt(secret, sdcreds.EncryptOptions{Key: sdcreds.IDHost, HostKey: host, Name: "db-password"})
text := sdcreds.Armor(blob, sdcreds.ArmorWidth) // what systemd-creds prints
raw, _ := sdcreds.Unarmor([]byte(text))
plain, md, err := sdcreds.Decrypt(raw, sdcreds.DecryptOptions{HostKey: host, Name: &name})

s6 

sdcreds s6-run --service=web --user=svc --source=/etc/creds -- /usr/bin/web

s6-run decrypts every file of --source before mounting anything, mounts a per-service tmpfs (nodev,noexec,nosuid,nosymfollow,noswap, mode 0700, size and inode count bounded; ramfs if the kernel lacks those options), writes the plaintext 0400 owned by the service user, remounts it read-only, setsCREDENTIALS_DIRECTORY, then starts the service in a child that drops privileges (no_new_privs, an empty capability set) and waits for it.

  • s6-run is still the process that s6 supervises: it forwards TERM, INT,HUP, QUIT, USR1, USR2, ALRM and CONT to the service, exits with its status (128 plus the signal number if a signal killed it), hands on the descriptors it was given, and the service is killed if s6-run dies.
  • The credentials are taken away when the service ends, and before s6-run fails if the program cannot be executed.
  • The mount lives in a private namespace by default (--unshare=false turns that off), so it disappears with the service.
  • A credential sealed with the null key is refused unless --allow-null is given, and one that carries no name is always refused.
  • sdcreds s6-finish --service=web unmounts lazily and removes the directory;it is idempotent. With --unshare=false, a SIGKILL of s6-run leaves the mount in place until s6-finish runs: put it in the finish script of the service.
  • At most 1024 credentials and 16 MiB per service. Linux only; elsewhere the commands report ErrUnsupported.

The key files named by --secret and --machine-id-file must be root-owned and not writable by group or others, and so must every directory above them up to/. The key file is opened once, without following a final link, and the key is wiped from the memory of s6-run when it is done with the credentials. Only the child takes the identity of the service; s6-run and all its threads stay root.

Keeping a capability: --keep-cap 

sdcreds s6-run --service=vpn --user=svc --source=/etc/creds --keep-cap=CAP_NET_ADMIN -- /usr/bin/vpn

The flag is repeatable and comma-separated (--keep-cap=CAP_NET_ADMIN,CAP_NET_RAW or one flag each) and has no default: without it the service runs with every capability set empty.

It is an allowlist of seven capabilities, none of them root-equivalent or able to read or write the credential tmpfs or to signal s6-run:CAP_NET_ADMIN, CAP_NET_BIND_SERVICE, CAP_NET_RAW, CAP_NET_BROADCAST,CAP_IPC_LOCK, CAP_WAKE_ALARM and CAP_BLOCK_SUSPEND. Any other capability,or a name that is not a capability, is an error that names the allowlist,reported before the key is read or anything is mounted.

The service has, in its bounding, permitted, inheritable, effective and ambient sets, exactly the kept capabilities and nothing else. no_new_privs stays on,and the securebits are 0x3 (SECBIT_NOROOT set and locked). s6-run’s own privileges are unchanged.

CAP_NET_ADMIN acts on the network namespace the service runs in, which is the host’s unless the service is started in a network namespace of its own(--unshare only gives it a private mount namespace): there it can change interfaces, routes and the firewall. Run such a service in its own network namespace when that matters.

sdcreds run: OpenBSD and Linux 

sdcreds run --service=web --user=svc --source=/etc/creds [--class=daemon] -- /usr/local/bin/web

run decrypts the sealed files of --source, makes them visible to the program as read-only files owned by --user under $CREDENTIALS_DIRECTORY, runs it as that user and removes them when it ends. On Linux it is s6-run with the same flags. --check runs every refusal and decrypts nothing (use it in an rc.drc_pre). A refusal exits with status 2 and happens before the host key is read. On OpenBSD the files live in a memory file system (MFS) mounted for the service and zeroed at the end:

  • There is no mount namespace. While the program runs, the credentials are visible to every process that can reach the directory, and root can always read them.
  • The host key is /etc/sdcreds/host.key, owned by root, mode 0600; any other mode or owner is refused. Create it withsdcreds setup --path /etc/sdcreds/host.key, then chmod 600 it. The machine id is sysctl hw.uuid. --secret and --machine-id-file override both and go through the same ownership and mode checks.
  • --user is never root: uid 0, gid 0 and any supplementary group 0 are refused, in run and in the library (s6.Run, delivery); there is no flag to allow it. The program must be an absolute, normalised path that the user can execute.
  • Killing sdcreds kills the program and unmounts, even with SIGKILL. A helper process holds the service lock and watches sdcreds; on any end it kills everything the service user runs (by uid, so a program that called setsid does not escape) and then unmounts. Root never signals a pid it read from a list. Since v0.4.0 the kill is made by a short-lived killer process that root starts and that drops to split credentials (real and saved uid of a reserved killer user, effective uid of the service user) before it signals anything:the kernel then lets it signal every process of the service user, while no process of that user can signal it. The killer sends kill(-1, SIGKILL) until the kernel reports nothing left; the kills of one service user are serialised by a lock of that user (/var/run/sdcreds-killer-<uid>.lock), and a kill of another user never makes a release wait or give up. Two killers of different users share the killer’s real uid and can signal each other: a killer that dies of it is run again, because the process table decides, and a user that is not empty at the budget is reported (fail closed). Install requirement: create the killer user, which must own no process and must not be root or a service user:useradd -s /sbin/nologin -d /var/empty -c "sdcreds killer" _sdkill. A delivery is refused to start without it, or when it owns a process (a start waits up to 20 s for the killer of a release that is running). A process that holds the user only through a set-uid file run by another user is counted by the start check but is not reached by the killer: the release then reports that a process survived and the next start is refused until it is gone (fail-closed). When a process survives the 20 s budget, the helper still unmounts (the secrets go),reports the failure and exits non-zero. A user is owned by one delivery at a time (the.uid-<N>.lock in /var/run/sdcreds), and run refuses a user that already has other processes: give the service its own user. If sdcreds and the helper both die, sdcreds sweep [--base DIR] [--service S] (or the next start of the service) removes the leftover. When the release fails after the program ends,sdcreds exits with status 70, whatever the program’s own status was (it is printed on stderr, with the reason).
  • Exit status of run (since v0.4.0). The program’s own status is passed through (a program killed by signal n gives 128+n). sdcreds’ own endings have reserved statuses, outside the 0-2 and 64-78 ranges that daemons commonly use: 125 sdcreds refused, nothing was started (bad flag, unknown or root user, unencrypted swap, a run that is alive; permanent until something changes); 126 sdcreds failed after it began (delivery, helper lost, the program could not be executed; may be transient); 70 the program ended but the release failed, whatever the program’s own status was (it is then printed on stderr). A program that itself exits 125 or 126 cannot be told apart. Before v0.4.0 a refusal exited 2 and a failure 1.
  • Restart. A start waits up to 47 s for the previous run of the same service to finish tearing down (which can take up to 46 s) instead of being refused; a run still alive after 47 s is refused (125). A second service for the same user is still refused at once.
  • Swap must be encrypted. run refuses to start whensysctl vm.swapencrypt.enable is 0, cannot be read, or does not exist. There is no flag to override it. In the library, s6.Config needs a ReadSource (the command gives the trust-walked reader), or s6.Run refuses.
  • The embedded file-system images are pinned: the sha256 of eachdelivery/images/ffs-<N>MiB.gz is checked before the helper decompresses it.
  • --class is looked up in /etc/login.conf.d/<class> first, then/etc/login.conf; login.conf.db is not consulted. The resource limits of the class are applied to the program, only ever lowering what it would have, and a class that cannot be read or parsed is a refusal. Priority and umask are not applied; the program gets umask 077.
  • The program’s environment is an allow-list: PATH (a fixed default),CREDENTIALS_DIRECTORY, LANG, TZ, TERM and LC_*. Descriptors above 2 are closed before it runs.
  • Passing the environment and descriptors (OpenBSD, since v0.4.0).--pass-env NAME (repeatable) hands the variable NAME of sdcreds’ own environment to the program as it is (not passed when unset); --pass-fd N (repeatable) keeps descriptor N open in the program at the same number.Both are refused for what sdcreds owns: PATH, CREDENTIALS_DIRECTORY,__SDCREDS_*; descriptors 0 to 3; a descriptor that is not open or is close-on-exec. A supervisor of a notify-type service passes, for example,--pass-env NOTIFY_SOCKET --pass-env LISTEN_FDS --pass-env LISTEN_PID --pass-fd 4.LISTEN_PID is passed as it is: it names the pid the caller expected, not the program’s.
  • Memory. The plaintext is in the memory of the sdcreds process for a short time. mlockall cannot be used from a Go process on OpenBSD (measured on 8.0), so protection is vm.swapencrypt.enable (checked at start), core dumps off and kern.nosuidcoredump. A crash dump taken by an administrator can still contain the plaintext.
  • --keep-cap is Linux only.

docs/openbsd/authn_bridge in the repository is an rc.d script that runs go-authn/bridge this way. The delivery is also a library, package delivery.

Interoperability

Both directions are tested against the real systemd-creds 262.2, built from the v262.2 tag (no distribution package).

  • testdata/systemd-v262.2 holds 44 credentials written by systemd-creds (null,host and host-scoped; with and without a name; no, past and future not-after;0 B, 1 B and 64 KiB payloads; five tampered variants), and manifest.json records what systemd-creds itself answered for each of 272 decryption attempts(right and wrong name, before and after not-after, with and without --uid).The library gives the same answer, with the same class of error, for every one.
  • With a fixed IV, Encrypt reproduces systemd’s bytes exactly.
  • In the container, systemd-creds decrypt opens what Encrypt wrote, and the command line passes the same round trip in both directions.
docker build -t sdcreds-interop docker
docker run --rm --privileged -e SDCREDS_REQUIRE_SYSTEMD=1 -e SDCREDS_S6_INTEGRATION=1 \
  -v "$PWD":/src/sdcreds -w /src/sdcreds sdcreds-interop \
  sh -c 'echo 0123456789abcdef0123456789abcdef > /etc/machine-id && go test -count=1 ./...'

Without SDCREDS_REQUIRE_SYSTEMD=1 the tests that need the binary are skipped;CI sets it, so an absent binary is a failure there. The 1 MiB boundary is covered by the library tests only, not by interop vectors.

Deviations from systemd

  • A host secret whose machine id does not match is refused (ErrHostKeyMachine); systemd removes it.
  • --with-key=auto means host: there is no TPM2 here.
  • A credential sealed with the null key has no secrecy: sdcreds decrypt refuses it on every machine unless --allow-null is given (systemd instead consults the TPM2 and SecureBoot state; that library policy,SystemNullPolicy, is not used by the CLI).
  • SDCREDS_MACHINE_ID_FILE (encrypt, decrypt, setup) points at another machine id file. s6-run ignores it and SYSTEMD_CREDENTIAL_SECRET: its key comes from the default files, or from --secret and --machine-id-file.
  • A variable IV size is accepted when reading, as in systemd; this library always writes 12 bytes.
  • The secret is opened without following a final symlink, and must be a regular file with one link and mode 0400, as systemd requires.

Safety

Every length is checked before it is used, before anything is allocated, and on both sides of its bound; credentials are limited to 1 MiB (as systemd) and the host secret to 16 MiB. The parsers are fuzzed in CI with the corpus committed,and govulncheck runs in CI. The README has no performance table yet: the measurement is deferred, an open item and not a result.
