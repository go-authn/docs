sdcreds

sdcreds — systemd-Credentials, ohne systemd

go-authn/sdcreds liest und schreibt das systemd-Credential-Format (systemd-creds encrypt und decrypt) aus Go, mit einer Kommandozeile und einem s6-Helfer, der einem überwachten Dienst sein $CREDENTIALS_DIRECTORY gibt.

Was, wenn ein Dienst die Credentials braucht, die eine systemd-Unit überLoadCredentialEncrypted= erhält, und es kein systemd gibt? sdcreds liest und schreibt das systemd-Credential-Format(systemd-creds encrypt / decrypt) aus Go, mit einer Kommandozeile und einem Helfer, der einem von s6 überwachten Dienst dasselbe $CREDENTIALS_DIRECTORY gibt.

Unterstützte Schlüssel: null, host (/var/lib/systemd/credential.secret)und host-scoped (--uid / --user). TPM2- und Public-Key-Credentials werden erkannt und mit *UnsupportedModeError abgelehnt; nichts wird geraten.

Installation 

go install github.com/go-authn/sdcreds/cmd/sdcreds@latest

Die Version, die diese Seiten beschreiben, ist v0.2.0.

Kommandozeile 

sdcreds setup                                  # create the host secret if missing
sdcreds encrypt --name=db-password plain.txt db-password.cred
sdcreds decrypt db-password.cred -             # the name must match the file name

Dasselbe aus Go:

host := sdcreds.HostKeyFile{} // $SYSTEMD_CREDENTIAL_SECRET or the default path
blob, err := sdcreds.Encrypt(secret, sdcreds.EncryptOptions{Key: sdcreds.IDHost, HostKey: host, Name: "db-password"})
text := sdcreds.Armor(blob, sdcreds.ArmorWidth) // what systemd-creds prints
raw, _ := sdcreds.Unarmor([]byte(text))
plain, md, err := sdcreds.Decrypt(raw, sdcreds.DecryptOptions{HostKey: host, Name: &name})

s6 

sdcreds s6-run --service=web --user=svc --source=/etc/creds -- /usr/bin/web

s6-run entschlüsselt jede Datei von --source, bevor etwas eingehängt wird,hängt ein tmpfs pro Dienst ein (nodev,noexec,nosuid,nosymfollow,noswap, Modus 0700, Größe und Inode-Anzahl begrenzt; ramfs, wenn der Kernel diese Optionen nicht kennt), schreibt den Klartext mit 0400 und dem Dienstbenutzer als Besitzer,hängt es schreibgeschützt neu ein, setzt CREDENTIALS_DIRECTORY und startet dann den Dienst in einem Kindprozess, der Privilegien abgibt (no_new_privs, eine leere Capability-Menge), und wartet auf ihn.

  • s6-run bleibt der Prozess, den s6 überwacht: Es leitet TERM, INT, HUP,QUIT, USR1, USR2, ALRM und CONT an den Dienst weiter, beendet sich mit dessen Status (128 plus Signalnummer, wenn ein Signal ihn beendet hat), reicht die erhaltenen Deskriptoren weiter, und der Dienst wird beendet, wenn s6-run stirbt.
  • Die Credentials werden entfernt, wenn der Dienst endet, und bevor s6-run fehlschlägt, wenn das Programm nicht ausgeführt werden kann.
  • Das Einhängen geschieht standardmäßig in einem privaten Namensraum(--unshare=false schaltet das ab), es verschwindet also mit dem Dienst.
  • Ein mit dem Null-Schlüssel versiegeltes Credential wird abgelehnt, es sei denn,--allow-null ist gesetzt, und eines ohne Namen wird immer abgelehnt.
  • sdcreds s6-finish --service=web hängt verzögert aus und entfernt das Verzeichnis; es ist idempotent. Mit --unshare=false lässt ein SIGKILL vons6-run das Einhängen bestehen, bis s6-finish läuft: Setzen Sie es in das Finish-Skript des Dienstes.
  • Höchstens 1024 Credentials und 16 MiB pro Dienst. Nur Linux; anderswo melden die Befehle ErrUnsupported.

Die mit --secret und --machine-id-file benannten Schlüsseldateien müssen root gehören und für Gruppe und andere nicht beschreibbar sein, ebenso jedes Verzeichnis darüber bis /. Die Schlüsseldatei wird einmal geöffnet, ohne einem abschließenden Link zu folgen, und der Schlüssel wird aus dem Speicher vons6-run gelöscht, sobald es mit den Credentials fertig ist. Nur das Kind nimmt die Identität des Dienstes an; s6-run und alle seine Threads bleiben root.

Eine Capability behalten: --keep-cap 

sdcreds s6-run --service=vpn --user=svc --source=/etc/creds --keep-cap=CAP_NET_ADMIN -- /usr/bin/vpn

Die Option ist wiederholbar und kommagetrennt (--keep-cap=CAP_NET_ADMIN,CAP_NET_RAW oder je eine Option) und hat keinen Standardwert: ohne sie läuft der Dienst mit leeren Capability-Mengen.

Es ist eine Allowlist von sieben Capabilities, von denen keine root-äquivalent ist oder das Credential-tmpfs lesen oder schreiben oder s6-run signalisieren kann: CAP_NET_ADMIN, CAP_NET_BIND_SERVICE, CAP_NET_RAW, CAP_NET_BROADCAST,CAP_IPC_LOCK, CAP_WAKE_ALARM und CAP_BLOCK_SUSPEND. Jede andere Capability oder ein Name, der keine Capability ist, ist ein Fehler, der die Allowlist nennt und gemeldet wird, bevor der Schlüssel gelesen oder etwas eingehängt wird.

Der Dienst hat in seinen Mengen bounding, permitted, inheritable, effective und ambient genau die behaltenen Capabilities und sonst nichts. no_new_privs bleibt aktiv, und die Securebits sind 0x3 (SECBIT_NOROOT gesetzt und gesperrt). Die Rechte von s6-run selbst bleiben unverändert.

CAP_NET_ADMIN wirkt auf den Netzwerk-Namensraum, in dem der Dienst läuft; das ist der des Hosts, sofern der Dienst nicht in einem eigenen Netzwerk-Namensraum gestartet wird (--unshare gibt ihm nur einen privaten Mount-Namensraum): dort kann er Schnittstellen, Routen und die Firewall ändern. Starten Sie einen solchen Dienst in einem eigenen Netzwerk-Namensraum, wenn das wichtig ist.

Interoperabilität

Beide Richtungen werden gegen das echte systemd-creds 262.2 getestet, aus dem Tag v262.2 gebaut (kein Distributionspaket).

  • testdata/systemd-v262.2 enthält 44 von systemd-creds geschriebene Credentials (null, host und host-scoped; mit und ohne Namen; kein, vergangenes und zukünftiges not-after; Nutzlasten von 0 B, 1 B und 64 KiB; fünf manipulierte Varianten), und manifest.json hält fest, was systemd-creds selbst für jeden von 272 Entschlüsselungsversuchen geantwortet hat (richtiger und falscher Name, vor und nach not-after, mit und ohne --uid). Die Bibliothek liefert für jeden dieselbe Antwort mit derselben Fehlerklasse.
  • Mit festem IV reproduziert Encrypt die Bytes von systemd exakt.
  • Im Container öffnet systemd-creds decrypt, was Encrypt geschrieben hat, und die Kommandozeile besteht denselben Hin- und Rückweg in beiden Richtungen.
docker build -t sdcreds-interop docker
docker run --rm --privileged -e SDCREDS_REQUIRE_SYSTEMD=1 -e SDCREDS_S6_INTEGRATION=1 \
  -v "$PWD":/src/sdcreds -w /src/sdcreds sdcreds-interop \
  sh -c 'echo 0123456789abcdef0123456789abcdef > /etc/machine-id && go test -count=1 ./...'

Ohne SDCREDS_REQUIRE_SYSTEMD=1 werden die Tests, die das Binary brauchen,übersprungen; die CI setzt es, ein fehlendes Binary ist dort also ein Fehler. Die 1-MiB-Grenze wird nur von den Bibliothekstests abgedeckt, nicht von Interop-Vektoren.

Abweichungen von systemd

  • Ein Host-Secret, dessen Machine-ID nicht passt, wird abgelehnt (ErrHostKeyMachine); systemd entfernt es.
  • --with-key=auto bedeutet host: Hier gibt es kein TPM2.
  • Ein mit dem Null-Schlüssel versiegeltes Credential bietet keine Geheimhaltung:sdcreds decrypt lehnt es auf jeder Maschine ab, es sei denn, --allow-null ist gesetzt (systemd dagegen prüft den Zustand von TPM2 und SecureBoot; diese Bibliotheksrichtlinie, SystemNullPolicy, wird von der CLI nicht verwendet).
  • SDCREDS_MACHINE_ID_FILE (encrypt, decrypt, setup) verweist auf eine andere Machine-ID-Datei. s6-run ignoriert sie undSYSTEMD_CREDENTIAL_SECRET: Sein Schlüssel stammt aus den Standarddateien oder aus --secret und --machine-id-file.
  • Eine variable IV-Größe wird beim Lesen akzeptiert, wie in systemd; diese Bibliothek schreibt immer 12 Bytes.
  • Das Secret wird geöffnet, ohne einem abschließenden Symlink zu folgen, und muss eine reguläre Datei mit einem Link und Modus 0400 sein, wie es systemd verlangt.

Sicherheit

Jede Länge wird geprüft, bevor sie verwendet wird, bevor etwas alloziert wird, und auf beiden Seiten ihrer Grenze; Credentials sind auf 1 MiB begrenzt (wie bei systemd) und das Host-Secret auf 16 MiB. Die Parser werden in der CI mit eingecheckter Korpusdatei gefuzzt, und govulncheck läuft in der CI. Das README hat noch keine Performance-Tabelle: Die Messung ist aufgeschoben, ein offener Punkt und kein Ergebnis.
