ldap — los bytes de un servidor LDAP

go-authn/ldap es el protocolo LDAP como biblioteca de servidor: el formato en la red, el filtro, las operaciones y sus límites, con handlers que deciden qué se responde.

¿Cuáles son los bytes de un servidor LDAP? Una biblioteca, no un demonio: el formato en la red, el filtro, las operaciones. authnd es el servidor que la ejecuta y que es dueño de la configuración, de los orígenes del directorio y de la política de bind; esta es dueña de los bytes.

go get github.com/go-authn/ldap@v0.10.1

Escrita a partir de los RFC 4511 (el protocolo), 4512 (el root DSE y el esquema), 4513 (autenticación), 4514 y 4515 (formas en cadena de los DN y de los filtros), 4517 y 4518 (sintaxis, reglas de comparación, preparación de cadenas), 4526, 2696 (resultados paginados), 3672 (subentradas), 3673, 4527(controles de lectura de entrada), 4532 (whoami) y 3045.

Un Server es un conjunto de handlers, cada uno un campo opcional: Bind, SASL,Search, Compare, Extended, Add, Modify, Delete, ModifyDN, Abandon.Uno nil significa este servidor no hace eso, y la operación se responde conunwillingToPerform, no con insufficientAccessRights, que abriría una discusión sobre permisos que no existen. El root DSE lo responde el propio servidor, y publica exactamente lo que respeta.

Ejemplo

Un servidor con una persona que puede hacer un bind y una búsqueda que escribe lo que coincide con el filtro:

package main

import (
	"context"
	"crypto/subtle"
	"log"
	"log/slog"
	"os"

	"github.com/go-authn/ldap"
)

var people = []*ldap.Entry{
	{DN: "uid=dora,ou=people,dc=example,dc=org", Attributes: []*ldap.Attribute{
		ldap.StringAttribute("objectClass", "posixAccount"), ldap.StringAttribute("uid", "dora")}},
	{DN: "uid=svc-web-prod,ou=people,dc=example,dc=org", Attributes: []*ldap.Attribute{
		ldap.StringAttribute("objectClass", "posixAccount"), ldap.StringAttribute("uid", "svc-web-prod")}},
	{DN: "uid=svc-web-stage,ou=people,dc=example,dc=org", Attributes: []*ldap.Attribute{
		ldap.StringAttribute("objectClass", "posixAccount"), ldap.StringAttribute("uid", "svc-web-stage")}},
}

// binder checks one password. A real one asks a directory: see go-authn/directory.
type binder struct{}

func (binder) Bind(_ context.Context, _ ldap.Session, req *ldap.BindRequest) (ldap.Result, error) {
	if req.Name == "" && len(req.Simple) == 0 {
		return ldap.Result{Code: ldap.Success}, nil // anonymous: the connection stays unbound
	}
	// A name with an empty password is an UNAUTHENTICATED bind (RFC 4513
	// 5.1.2). This package hands it to the handler, and the handler refuses it:
	// the comparison below does, since the password is never empty.
	ok := ldap.EqualDN(req.Name, "uid=dora,ou=people,dc=example,dc=org") &&
		subtle.ConstantTimeCompare(req.Simple, []byte("hunter2")) == 1
	if !ok {
		return ldap.Refuse(ldap.InvalidCredentials, "invalid credentials"), nil
	}
	return ldap.Result{Code: ldap.Success}, nil
}

// searcher writes each entry in scope that the filter matches, as it finds it.
type searcher struct{}

func (searcher) Search(_ context.Context, s ldap.Session, req *ldap.SearchRequest, w ldap.EntryWriter) (ldap.Result, error) {
	if s.BoundDN() == "" {
		return ldap.Refuse(ldap.InsufficientAccessRights, "bind first"), nil
	}
	for _, e := range people {
		if ldap.InScope(e.DN, req.BaseObject, req.Scope) && req.Filter.Matches(e) {
			if err := w.Entry(e); err != nil {
				return ldap.Result{}, err // the client went away, or a limit was reached
			}
		}
	}
	return ldap.Result{Code: ldap.Success}, nil
}

func main() {
	srv := &ldap.Server{
		Bind:           binder{},
		Search:         searcher{},
		NamingContexts: []string{"dc=example,dc=org"},
		Log:            slog.New(slog.NewTextHandler(os.Stderr, nil)),
		// On anything but loopback: TLSConfig, and RequireTLS so that a
		// client that never asks for StartTLS is refused rather than
		// sending its password in the clear.
	}
	log.Fatal(srv.ListenAndServe("127.0.0.1:3389"))
}

La biblioteca a la que esta sustituye evaluaba ese filtro como (uid=svc-*) y devolvía tambiénsvc-web-stage; ese defecto es la razón por la que se escribió esta biblioteca. El root DSE no anuncia StartTLS, porque no se indicó ningún TLSConfig.

Lo que rechaza, y por qué

Un filtro significa una sola cosa. Se analiza o se decodifica una sola vez en un árbol, y String, EncodeFilter y Matches leen todos ese árbol. Un atributo que no es una descripción de atributo según el RFC 4512 §2.5, o una regla de coincidencia que no es un OID, lo rechazan tanto ParseFilter como DecodeFilter: antes de la v0.6.1, al volver a imprimirlo, un filtro «present» sobre el atributo !x se leía como un NOT.

Texto en claro, cuando se había prometido lo contrario. StartTLS lo pide elcliente, así que un servidor que solo lo ofrece no ha prometido nada.RequireTLS rechaza cada operación en una conexión que no está protegida, conconfidentialityRequired.

Un bind fallido no conserva nada. RFC 4511 §4.2.1: la conexión se vuelve anónima cuando se recibe la petición de bind, y sigue así salvo que el bind tenga éxito; así que un nuevo bind con una contraseña errónea no conserva los derechos de la persona anterior. Un bind simple sin handler Bind se responde con authMethodNotSupported,y LDAPv2 se rechaza como error de protocolo.

El handler decide qué significa una contraseña vacía

Un bind no autenticado —un nombre con una contraseña vacía, RFC 4513 §5.1.2— se pasa al handler Bind como cualquier otro bind simple, y un handler que devuelveSuccess para él vincula la conexión a ese nombre. Recháselo en el handler, como hace el ejemplo. El ldapdir de directory lo rechaza del lado del cliente.

Un control crítico que no respeta. ManageDsaIT (RFC 3296), password modify(RFC 3062) y cancel (RFC 3909) se nombran como constantes porque un cliente puede enviarlos, no porque se respondan: aquí nada sigue alias ni referencias, así que un ManageDsaIT crítico se rechaza con unavailableCriticalExtension.

Lo que puede retener un interlocutor no autenticado:

por defecto
MaxMessageSize4 MiBuna cabecera de cinco bytes que anuncia cuatro gigabytes se rechaza antes de reservar nada
MaxMessageElements16384elementos BER contados antes de decodificar: antes de la v0.5.0, 4 MiB de cadenas vacías retenían 373 MiB antes de cualquier bind

El anidamiento de los filtros también está acotado: un desbordamiento de pila en Go mata el proceso. Nada registra el valor de una aserción —un filtro lleva lo que alguien tecleó—, solo la forma del filtro.

Una búsqueda paginada responde a lo que se preguntó. Hasta la v0.8.0, el lector de páginas enviaba cada entrada tal como la escribía el handler: una búsqueda paginada solo de cn volvía con todos los atributos, operativos incluidos, y typesOnly se ignoraba, mientras que la misma búsqueda sin paginar se ceñía a la selección. ldapsearch -E pr=N es como pagina un cliente, así que la misma pregunta recibía dos respuestas. Desde la v0.8.0 ambas aplican la selección, lo que el propio ldapsearch comprueba en la CI.

Sin esquema —Server.Schema a nil, el valor por defecto—, cada comparación ignora mayúsculas y minúsculas en el valor: la más segura de las dos para leer, ya que nunca oculta una entrada que una comparación exacta habría encontrado.

El esquema

Desde la v0.8.0, el paquete schema es el esquema de directorio del RFC 4512 §4, y Server.Schema hace que un servidor lo use. Nil deja un servidor exactamente como estaba.

  • schema.Standard() incorpora las definiciones de los RFC 4512, 4517, 4519,4524, 4523, 2798, 2307, 3672 y 3045, más ldapPublicKey y sshPublicKey de openssh-lpk y las dos definiciones de OpenLDAP que necesitan, copiadas del texto de los RFC; cada archivo de schema/defs nombra su fuente y su sección. schema.Build(append(schema.StandardFiles(), mine)...) añade las propias de un despliegue, y rechaza una cuyos SUP, reglas, sintaxis, MUST o MAY no se resuelven.
  • (*ldap.Entry).Validate(s) comprueba una sola cadena estructural con cada superclase listada, cada MUST, nada fuera de MUST y MAY, SINGLE-VALUE, tipos conocidos, valores de su sintaxis y los valores del RDN en la entrada, y nombra cada problema, como un *schema.ValidationError.
  • Con un esquema, el root DSE lleva subschemaSubentry: cn=Subschema, y una búsqueda de base sobre cn=Subschema (ldap.SubschemaDN) la responde la biblioteca, como el root DSE (RFC 4512 §4.2). Las definiciones solo llegan cuando se piden por nombre o con +. Está detrás de la barrera deRequireTLS.
  • Los filtros se evalúan con las reglas de comparación del esquema(RFC 4517 §4.2, con la preparación de cadenas del RFC 4518) en la lógica de tres valores del RFC 4511: un atributo desconocido, un tipo sin regla para la comparación pedida o un valor de aserción no válido es Undefined,nunca un error. El servidor vuelve a comprobar cada entrada que envía un handler y descarta las que el filtro no hace TRUE; un handler filtra conreq.Matches(e), que usa el mismo esquema.
package main

import (
	"errors"
	"fmt"

	"github.com/go-authn/ldap"
	"github.com/go-authn/ldap/schema"
)

func main() {
	s := schema.Standard() // RFC 4512, 4517, 4519, 4524, 2798, 2307, ... and openssh-lpk

	// An account with posixAccount, and no homeDirectory.
	eli := &ldap.Entry{DN: "uid=eli,ou=people,dc=example,dc=org", Attributes: []*ldap.Attribute{
		ldap.StringAttribute("objectClass", "top", "account", "posixAccount"),
		ldap.StringAttribute("uid", "eli"),
		ldap.StringAttribute("cn", "eli"),
		ldap.StringAttribute("uidNumber", "1001"),
		ldap.StringAttribute("gidNumber", "1001"),
		ldap.StringAttribute("mail", "eli@example.org"),
	}}
	var v *schema.ValidationError
	if errors.As(eli.Validate(s), &v) {
		for _, p := range v.Problems {
			fmt.Println("-", p)
		}
	}

	// uidNumber orders as an integer: 1001 >= 999, which as strings it is not.
	for _, f := range []string{"(uidNumber>=999)", "(uid>=a)"} {
		filter, _ := ldap.ParseFilter(f)
		fmt.Println(f, ldap.Evaluate(filter, eli, s))
	}
}
- mail is not allowed by any of the entry's object classes
- homeDirectory is required by posixAccount and is missing
(uidNumber>=999) TRUE
(uid>=a) Undefined

mail pertenece a inetOrgPerson, no a account. uid no tiene regla ORDERING, así que un rango sobre él es Undefined.

Una desviación del RFC 2307: uidNumber y gidNumber se ordenan como enteros

El RFC 2307 da a uidNumber y gidNumber una regla EQUALITY y ninguna regla ORDERING, lo que haría Undefined todo filtro de rango sobre ellos, incluido el que SSSD construye a partir de ldap_min_id y ldap_max_id. slapd define él mismo ambos tipos con ORDERING integerOrderingMatch (servers/slapd/schema_prep.c; su nis.schema los comenta como“builtin”), y lo mismo hace draft-howard-rfc2307bis-02 §2.1, así que las definiciones incorporadas los siguen. Eso, y permitir clases auxiliares sin reglas de contenido DIT (el RFC 4512 §2.4.3 las prohíbe estrictamente; todos los servidores en uso las permiten), se dicen en lugar de descubrirse.

No están, deliberadamente: las reglas de contenido DIT, las reglas de estructura DIT y las formas de nombre; cambiar el esquema por LDAP; las reglas de comparación de certificados del RFC 4523 ydirectoryStringFirstComponentMatch, que están definidas y no implementadas,así que las aserciones que las usan son Undefined; los atributos colectivos;las opciones distintas de lang- y binary.

authnd sirve este esquema y somete a él cada entrada que publica.

Leer un archivo de esquema grande

Hasta v0.10.0, schema.Read tardaba un tiempo cuadrático en el número de líneas de continuación del archivo leído: un archivo de 4 MiB de líneas de continuación cortas tardaba unos tres minutos, y 1 MiB reservaba 139,6 GB. Un programa que lee un archivo de esquema que no controla, como hace authnd con sus schema_files al arrancar, podía quedar bloqueado por uno. Desde v0.10.1 el tiempo es lineal (TestManyContinuationLinesJoinInLinearTime), y Read ya no copia ni divide todo el archivo para mirar su primera línea.

schema.Format escribía líneas de más de 2000 bytes, que slapd y Read rechazan; ahora las pliega. El analizador estricto es unas 2,6 veces más rápido, con 147 asignaciones en lugar de 498 en cosine.schema. Frente a libldap (SDK de macOS, ldap_str2attributetype y ldap_str2objectclass con LDAP_SCHEMA_ALLOW_ALL), sobre las 54 definiciones del cosine.schema de OpenLDAP, medido el 2026-10-26 en un Apple M4 Max con una carga de 6,5 a 7,6 (-cpu 1 -count 10, benchstat): go-authn/ldap 25,65 µs ± 32 %, libldap 35,62 µs ± 2 %, es decir, unas 0,72 veces el tiempo de libldap. El lado Go hace 147 asignaciones (20,6 KiB) por ejecución; -benchmem no ve las asignaciones en C de libldap, así que no hay cifra para ellas. Para reproducirlo, ejecute go test -bench . -benchmem -cpu 1 -count 10 en bench/libldap de go-authn/ldap (requiere cgo y libldap). authnd tiene estas correcciones desde v0.12.3.

Un esquema que no se construye

Desde la v0.10.0, una definición que schema.Build o schema.BuildFrom rechazan es un *schema.BuildError, que se obtiene con errors.As. Un programa informa de un rechazo a partir de sus campos, nunca comparando el mensaje. Build se detiene en la primera definición que rechaza, así que solo hay una.

  • Kind es una de todas las comprobaciones que hace Build: UnknownReference,DuplicateOID, DuplicateName, SuperiorCycle, KindViolation,UsageMismatch, CollectiveMismatch y UsageViolation.
  • Element (sintaxis, regla de comparación, tipo de atributo o clase de objeto), OID y Name (su primer NAME) son los de la definición rechazada,y Pos es el lugar donde empieza: archivo:línea:columna, la línea de la palabra clave del .schema o de la línea attributeTypes: del LDIF, también cuando esa línea está plegada o en base64, y la posición del propio bloque en HCL. Una definición construida en código no tiene ninguna.
  • Field es el término que falla (SUP, EQUALITY, SYNTAX, MUST, NAME …), y Ref aquello a lo que se refiere el error: el nombre o el OID sin definir, o la otra definición, con su RefOID y su RefPos. En un duplicado es la primera definición, y el mensaje dice dónde está.
package main

import (
	"errors"
	"fmt"

	"github.com/go-authn/ldap/schema"
)

// An object class whose superclass is defined nowhere.
const site = `# site.schema
objectclass ( 1.3.6.1.4.1.99999.1.1 NAME 'siteMember'
	SUP top AUXILIARY )
objectclass ( 1.3.6.1.4.1.99999.1.2 NAME 'siteGuest'
	SUP nobody AUXILIARY )
`

func main() {
	files := append(schema.StandardFiles(), schema.File{Name: "site.schema", Data: []byte(site)})
	_, err := schema.Build(files...)

	var be *schema.BuildError
	if !errors.As(err, &be) {
		fmt.Println("not a BuildError:", err)
		return
	}
	fmt.Println("error:  ", be)
	fmt.Println("Kind:   ", be.Kind)
	fmt.Println("Element:", be.Element)
	fmt.Println("OID:    ", be.OID)
	fmt.Println("Name:   ", be.Name)
	fmt.Println("Field:  ", be.Field)
	fmt.Println("Ref:    ", be.Ref)
	fmt.Println("Pos:    ", be.Pos)
	fmt.Println("RefPos: ", be.RefPos.IsValid())
	fmt.Println("is UnknownReference:", be.Kind == schema.UnknownReference)
}
error:   site.schema:4:1: schema: the object class siteGuest has the superclass nobody, which is not defined
Kind:    unknown reference
Element: object class
OID:     1.3.6.1.4.1.99999.1.2
Name:    siteGuest
Field:   SUP
Ref:     nobody
Pos:     site.schema:4:1
RefPos:  false

Ejecutado desde un módulo vacío con github.com/go-authn/ldap v0.10.1. La primera clase es correcta; la segunda empieza en la línea 4, y nada más falla,así que RefPos está vacío. Toda definición que devuelve schema.Read lleva también una Pos, y el String de la Position omite la columna cuando no se conoce.

Esquemas en HCL2, y el conversor

Desde la v0.9.0, un esquema puede escribirse en HCL2 además de en los archivos que lee slapd. El paquete schema/hclschema decodifica HCL2 en los mismos *schema.Definitions que devuelve schema.Read, y los vuelve a codificar (hclschema.Decode, hclschema.Encode); schema en sí no depende de HCL. Un bloque es una definición, y su tipo dice cuál:object_identifier, ldap_syntax, matching_rule, attribute_type uobject_class. La etiqueta es el primer NAME. Los atributos son los términos del RFC 4512 §4.1 en minúsculas y con guiones bajos (desc, sup,equality, single_value, kind, must, may, etcétera), y el {len} de una sintaxis es syntax_len.

Sólo valores literales. Un valor es una cadena entre comillas, un número,un booleano o una lista de ellos. Una variable, una función, un operador o una plantilla ${...} se rechaza antes de evaluar nada, de modo que leer un esquema nunca lo ejecuta. Cada campo lo comprueba el analizador estricto del RFC 4512, y los errores que necesitan una posición llegan con el archivo, la línea y la columna.

El comando ldapschema convierte entre los formatos:

go install github.com/go-authn/ldap/cmd/ldapschema@v0.10.1
  • ldapschema to-hcl [--macros] FILE... lee archivos .schema de OpenLDAP,LDIF de cn=config y LDIF del subesquema, y escribe HCL2.
  • ldapschema to-schema [--macros] FILE... lee HCL2 y escribe un archivo.schema de OpenLDAP.
  • ldapschema check FILE... construye las definiciones sobreschema.Standard() e informa.

La salida va a stdout. El código de salida es 0 cuando el comando funcionó, 1 cuando se rechaza un archivo o una definición, y 2 ante un error de uso.

Los lectores leen los archivos como slapd, porque los esquemas publicados se escriben para slapd: términos en cualquier orden, la continuación de línea de slapd en un archivo .schema y el plegado del RFC 2849 en LDIF, valores en base64, el prefijo {N} de cn=config, y macros objectidentifier resueltas en el orden de los archivos. Las funciones Parse* exportadas, y lo que un servidor publica, siguen siendo estrictamente RFC 4512.

Un ejemplo, ejecutado desde un directorio vacío con ldapschema v0.10.1. El esquema está inventado para esta página: 1.3.6.1.4.1.99999 es un arco de ejemplo de uso privado, no asignado a nadie. Una macro, un tipo de atributo,una clase auxiliar:

$ cat site.schema
# An example arc: 1.3.6.1.4.1.99999 is for private use.
objectidentifier site 1.3.6.1.4.1.99999

attributetype ( site:1.1 NAME 'siteBadge'
	DESC 'the badge number'
	EQUALITY caseIgnoreMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15{32}
	SINGLE-VALUE )

objectclass ( site:2.1 NAME 'sitePerson'
	DESC 'a person with a badge'
	SUP top AUXILIARY
	MAY siteBadge )

  oid = "1.3.6.1.4.1.99999"
}

attribute_type "siteBadge" {

Los OID numéricos son la salida por defecto, porque es lo que un cliente ve en el subesquema; --macros conserva los nombres de las macros. check informa también de las definiciones que schema.Standard() ya tiene, y de cada referencia que nada define, donde Build se detiene en la primera.

check puede salir con código 1 en un archivo que slapd carga. Elcore.schema de OpenLDAP remite a cuatro cosas que slapd incorpora y queschema.Standard() no define: las sintaxis 1.3.6.1.4.1.1466.115.121.1.42 y 1.3.6.1.4.1.1466.115.121.1.43, y las reglas de comparaciónprotocolInformationMatch y presentationAddressMatch. ldapschema check core.schema las lista como missing: y sale con código 1. Debe leerse como«no definido aquí», no como un defecto del archivo.

Lo que no admite: las reglas de contenido del DIT, las reglas de estructura del DIT y las formas de nombre; las directivas include, porque un archivo .schema se lee como definiciones y no se ejecuta como una configuración de slapd; y X-SUBST en ldapsyntax.

Los esquemas publicados se convierten. La versión se midió con los archivoscore, cosine, inetorgperson y nis de OpenLDAP, con SUPANN 2021 de RENATER, con eduPerson de REFEDS y con el esquema de Samba: en cada uno,.schema a HCL y vuelta, y LDIF frente a .schema, dan definiciones iguales.Sólo los archivos de OpenLDAP están en el repositorio. SUPANN y eduPerson no se reproducen aquí; léalos en las páginas de sus autores:SUPANN 2021 y eduPerson.

Contra qué se comprueba

El ldapsearch de OpenLDAP, en la CI, y obligatorio donde está instalado: la vía de pruebas de Linux, el detector de carreras y la vía de cobertura fijanLDAP_REQUIRE_JUDGE=1, así que un cliente ausente hace fallar en lugar de omitir.Windows no lo tiene y omite esas pruebas. ldaptest, el cliente de red propio de este módulo, deliberadamente no es el juez: solo pregunta lo que ldapsearch no puede,sobre el estado de una conexión: dos binds en un mismo socket, un bind SASL con un mecanismo arbitrario, StartTLS seguido de más LDAP.

FuzzMessage hace pasar cada mensaje que puede enviar un cliente por la trama, los decodificadores y la ida y vuelta del filtro. El umbral de cobertura es del 99,7 %,con las tres líneas no alcanzadas nombradas en el workflow.
