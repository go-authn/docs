authnd
엔트리와 스키마

authnd가 게시하는 엔트리와 제공하는 스키마

각 사람과 그룹이 무엇으로 게시되는지, 모든 엔트리가 통과하는 cn=Subschema의 스키마, 파일이나 SQL 쿼리로 속성을 추가하는 방법, 그리고 제외되거나 보류되는 것.

authnd가 게시하는 모든 엔트리는 자신이 제공하는 스키마를 통과합니다. v0.11.0부터 각 사람과 그룹은 소스가 제공한 것으로 만들어지는 표준 스키마 엔트리이며,검색으로 반환되기 전에 go-authn/ldap의 schema.Validate로 클라이언트가cn=Subschema에서 읽을 수 있는 스키마에 맞게 검사됩니다. 스키마를 읽고 믿는 클라이언트 — LDAP 브라우저, 동기화 도구, 이 디렉터리를 복제하는 디렉터리 — 는 들은 대로의 내용을 보게 됩니다. v0.10.2까지는 모든 사람이 top, person, posixAccount였고 그 클래스가 요구하는 속성은 하나도 없었으며,sambaNTPassword는 그것을 허용하는 클래스가 없는 엔트리에 붙어 있었습니다.

posixAccount나 posixGroup으로 필터링하는 소비자는 더 적은 엔트리를 봅니다

uidNumber, gidNumber, homeDirectory가 없는 사람은 더 이상posixAccount가 아니고, gidNumber가 없는 그룹은 더 이상 posixGroup이 아닙니다. (objectClass=posixAccount)나 (objectClass=posixGroup)을 검색하는 프로그램은 더 이상 이들을 찾지 못합니다. 여기에는 v0.13.0까지의 go-authn/directoryldapdir이 포함되며, 따라서 account, uidObject, groupOfNames도 읽는 기본값을 가진 directory v0.14.0을 요구하기 전까지의 go-fileshare도 포함됩니다(directory).사람과 그룹에 해당 속성을 부여하거나, 모든 사람이 가지고 있는(objectClass=uidObject)를 소비자가 사용하도록 지정하십시오.

형태

RFC 4512 §3.3이 요구하는 대로 모든 상위 클래스가 나열됩니다.

이런 사람은…objectClasscn
sn이 없음top, account (RFC 4524 §3.1)다른 클래스가 허용할 때만
sn이 있음top, person, organizationalPerson, inetOrgPerson (RFC 4519, RFC 2798)예
… 그리고 uidNumber, gidNumber, homeDirectory 세 가지 모두+ posixAccount (RFC 2307)예
… 그리고 SSH 키+ ldapPublicKey (openssh-lpk), sshPublicKey 포함
… 그리고 sambaSID가 있는 게시된 NT 해시+ sambaSamAccount (Samba), sambaSID와 sambaNTPassword 포함: samba 블록을 참조허용됨
… 항상+ uidObject (RFC 4519 §3.14), 그래서 (objectClass=uidObject)가 모든 사람을 찾음
이런 그룹은…objectClass구성원
gidNumber가 있음top, posixGroup (RFC 2307)memberUid, 이름
gidNumber가 없고 구성원이 있음top, groupOfNames (RFC 4519 §3.5)member, 이 서버가 게시하는 DN
gidNumber가 없고 구성원도 없음top, organizationalRole (RFC 4519 §3.10)없음
gidNumber가 있고 구성원이 없음top, posixGroup없음: 속성에는 값이 최소 하나 있어야 함

uid는 사람의 이름이며, 클래스가 허용하는 곳에서는 cn도 그렇습니다.account만으로는 cn이 허용되지 않으므로(MAY는 description, seeAlso, l,o, ou, host), sn도 POSIX 세 가지도 없는 사람은 uid만 있고 cn은 없습니다.

authnd 자체의 이유로 본 이 선택들의 근거는 다음과 같습니다.

  • posixGroup은 draft-howard-rfc2307bis-02가 아니라 RFC 2307을 따릅니다. 초안은 posixGroup을 AUXILIARY로 만들었고 게시되지 않은 채 만료되었습니다.AUXILIARY posixGroup에는 옆에 구조 클래스인 groupOfNames가 필요한데, 빈 그룹은 그 member를 줄 수 없습니다.
  • gidNumber가 없는 빈 그룹에는 organizationalRole. groupOfNames와 groupOfUniqueNames는 둘 다 구성원을 요구하며, 구성원을 지어내는 방법은 모두 거짓입니다. member: ""는 루트 DSE를 가리키고, 그룹 자신의 DN을 쓰면 그룹이 자기 자신의 구성원이 됩니다. organizationalRole은 유일한 MUST가 cn인 표준 구조 클래스이며, groupOfNames처럼 description, ou,seeAlso를 받습니다.
  • DIT 콘텐츠 규칙 없는 보조 클래스. RFC 4512 §2.4.3은 구조 클래스에 DIT 콘텐츠 규칙이 없는 엔트리에 보조 클래스를 두는 것을 금지합니다. 사용 중인 모든 디렉터리 서버가 이를 허용하며 Validate도 마찬가지입니다.

속성 추가하기

소스가 누군가에 대해 말하는 것 중 아무것도 증명하지 않는 것 — uidNumber, 홈 디렉터리, 메일 주소 — 은 속성이며, 주어진 대로 게시됩니다. 이것들은 v0.13.0부터의 go-authn/directory 속성이고 자격 증명과 분리되어 있습니다. 비밀 값을 담는 이름이나 서버가 직접 파생하는 이름은 아무것도 읽기 전에 거부됩니다.

user 또는 group 블록에서 

user "dora" {
  password_file   = "/etc/authnd/passwords/dora.pw"
  authorized_keys = ["ssh-ed25519 AAAA… dora@laptop"]
  attributes = {
    sn            = "Explorer"          # inetOrgPerson
    uidNumber     = "1000"              # the three: posixAccount
    gidNumber     = "1000"
    homeDirectory = "/home/dora"
    mail          = ["dora@example.org", "d.explorer@example.org"]
  }
}

group "engineers" {
  members    = ["dora", "eli"]
  attributes = { gidNumber = "2000" }   # a posixGroup; without it, a groupOfNames
}

값은 문자열이거나 문자열 목록이며, null은 그 속성을 생략합니다. 숫자는 거부됩니다. LDAP 값은 문자열이고 authnd는 숫자를 어떻게 표기할지 선택하지 않기 때문입니다.

$ authnd check cases/number.hcl
authnd: user "alice": attributes: uidNumber is the number 1000: write it as a string, "1000" -- an LDAP value is a string, and this does not choose how a number is spelled

$ authnd check cases/secret.hcl
authnd: user "alice": attributes: directory: not an attribute this package carries: "userPassword" holds a secret, and attributes are published: a credential has its own option or none

대소문자와 상관없이 같은 방식으로 거부되는 것: 비밀 값을 담는 모든 이름(userPassword, sambaNTPassword, unicodePwd, krbPrincipalKey와 go-authn/directory 목록의 나머지, 또는 password, passwd, pwd, secret, credential, hash,privatekey를 포함하는 모든 이름), authorized_keys가 따로 있는 sshPublicKey,서버가 파생하는 uid, cn, objectClass, members가 대신 답하는 member,memberUid 및 기타 구성원 속성, 서버가 유지하는 운영 속성, 그리고 숫자 형식의 이름(2.5.4.35는 userPassword입니다).

SQL 데이터베이스에서

users "sql" 블록의 선택적 쿼리 두 개는 열 별칭으로 속성을 읽습니다. 첫 번째 열은 사람 또는 그룹의 이름이고, 나머지 모든 열은 별칭이 이름이 되는 속성입니다.

users "sql" {
  driver   = "sqlite"
  dsn_file = "/etc/authnd/people.dsn"
  users    = "select login, secret, null, ssh_keys from staff"
  groups   = "select team, member from teams"
  users_attributes  = "select login, sn, uid as uidNumber, gid as gidNumber, home as homeDirectory, mail from person_attrs"
  groups_attributes = "select team, gid as gidNumber, description from team_attrs"
}
  • 위치 기반 users와 groups 쿼리는 그대로이며, 여섯 번째 위치 열은 여전히 거부됩니다. 속성은 이름으로, 자신만의 쿼리에서 가져옵니다.
  • 별칭이 속성 설명이 아닌 열(count(*)처럼 별칭 없는 표현식)이나 자격 증명을 지정하는 열은 행을 읽기 전에 열 번호와 함께 거부됩니다.
  • NULL과 ''는 없는 것으로 취급합니다. 하나의 이름이 여러 행에 나올 수 있으며 모든 행의 값이 유지되므로, 주소 테이블을 조인하면 한 사람이 여러 개를 갖게 됩니다.
  • groups_attributes에서만 지정된 그룹은 구성원이 없는 채로 존재합니다.사람 자신의 기본 그룹은 이렇게 기록합니다.

별칭의 대소문자는 데이터베이스가 정합니다

PostgreSQL은 따옴표 없는 별칭을 소문자로 접습니다. as uidNumber는uidnumber로 돌아옵니다. 속성 이름은 대소문자를 구분하지 않으므로 같은 속성이고 모든 LDAP 클라이언트에게 같은 엔트리이지만, authnd가 출력하는 표기는 데이터베이스의 것입니다. 표기가 중요한 곳에서는 별칭에 따옴표를 쓰십시오: gid as "gidNumber".SQLite는 별칭을 쓴 그대로 유지합니다.

다른 LDAP 디렉터리에서

users "ldap" 블록은 지시받은 속성을 각 사람의 엔트리와 각 그룹의 엔트리에서 복사합니다: attributes = ["mail", "uidNumber", "homeDirectory"]와group_attributes = ["gidNumber"]. 사람들을 참조하십시오.

구성과 그것이 게시하는 것

위의 SQL 블록에 reader를 더하고, 다섯 사람과 네 그룹이 든 SQLite 데이터베이스를 v0.11.0 릴리스 바이너리로 검사한 결과입니다.

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret, null, ssh_keys from staff"
  groups   = "select team, member from teams"
  users_attributes  = "select login, sn, uid as uidNumber, gid as gidNumber, home as homeDirectory, mail from person_attrs"
  groups_attributes = "select team, gid as gidNumber, description from team_attrs"
}
$ authnd check etc/authnd

PUBLISHED AS는 top을 제외한 각 엔트리의 객체 클래스이고, WITH는 검색이 반환하는 엔트리에서 읽은 속성입니다. hal은 uidNumber, gidNumber, mail이 있고 homeDirectory와 sn이 없습니다. hal은 account이며 account는 세 가지 모두 허용하지 않으므로, 그 속성들은 제외되고 나머지가 게시됩니다. 서버도 시작할 때 같은 내용을 알려 줍니다(그리고 멈추면 stopping).

무엇이 제외되고 무엇이 보류되는가

주어진 것엔트리이유
uidNumber, gidNumber, homeDirectory 없음, sn 없음account, uidObject, 두 속성 제외no class of the entry allows it; posixAccount would
mail, sn 없음account, uidObject, mail 제외no class of the entry allows it; inetOrgPerson would
스키마가 정의하지 않는 타입나머지the schema served here does not define it
gidNumber 없는 그룹의 mailgroupOfNames, mail 제외
POSIX 세 가지와 함께 homeDirectory 값 두 개보류: SINGLE-VALUE이므로 제외할 것이 없음
정수가 아닌 gidNumber보류: 구문에 맞지 않음

소스가 제공한 것만 제외되며, 어떤 속성이 허용되지 않는지는 스키마를 다시 읽은 결과가 아니라 Validate의 답입니다. 제외한 뒤 엔트리를 다시 검증합니다. 그래도 실패하는 엔트리는 보류됩니다. 모든 검색에서 사라지고, 시작 로그가 이를 지정하며,check는 Validate가 찾은 모든 문제와 함께 이를 나열합니다. authnd가 직접 파생하는 속성(uid, cn, objectClass, sshPublicKey, sambaSID, sambaNTPassword)을 스키마가 거부한다면 이는 authnd의 결함이며, 그 속성 없이 게시하지 않고 엔트리를 보류합니다.

여기서 alice의 gidNumber는 단어입니다.

  password_file = "etc/authnd/alice.pw"
  attributes = {
    uidNumber     = "1000"
    gidNumber     = "staff"

제공하는 스키마

루트 DSE가 이를 지정하며(루트 DSE의subschemaSubentry: cn=Subschema), cn=Subschema의 베이스 검색이 이를 반환합니다(RFC 4512 §4.2). go-authn/ldap이 내장한 표준 정의 — RFC 4512, 4517,4519, 4523, 4524, 2798, 2307, 3672, 3045와 openssh-lpk — 에,samba 블록이 있으면 Samba의sambaSamAccount, sambaSID, sambaNTPassword가 더해집니다. 정의는 이름으로 요청하거나 +로 요청할 때만 게시됩니다. 표시한 곳은 줄였습니다.

필터는 스키마의 매칭 규칙을 사용하므로 (uidNumber>=1000)은 정수를 비교합니다. uidNumber와 gidNumber에는 ORDERING integerOrderingMatch가 있는데, RFC 2307은 이를 주지 않습니다. slapd와 draft-howard-rfc2307bis-02는 주며, go-authn/ldap도 줍니다(유일한 차이점).문자열로 비교하면 1000이 999보다 앞에 정렬됩니다.
