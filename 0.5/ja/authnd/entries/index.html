エントリとスキーマ

authnd が公開するエントリと、提供するスキーマ

各人とグループが何として公開されるか、すべてのエントリが適合する cn=Subschema のスキーマ、ファイルまたは SQL クエリで属性を追加する方法、そして破棄または保留されるもの。

authnd が公開するすべてのエントリは、自身が提供するスキーマに適合します。 v0.11.0 からは、各人とグループが標準スキーマのエントリとなり、ソースが与えたものから組み立てられ、検索で返される前に、クライアントが cn=Subschema で読めるスキーマに照らしてgo-authn/ldap の schema.Validate で検証されます。スキーマを読んでそれを信じるクライアント、つまり LDAP ブラウザー、同期ツール、このディレクトリをレプリケートするディレクトリには、告げられたとおりのものが見えます。v0.10.2 までは、すべての人が top, person, posixAccount で、それらのクラスが必須とする属性は一つもなく、sambaNTPassword はそれを許すクラスのないエントリに載っていました。

posixAccount や posixGroup で絞り込むコンシューマーには、見えるエントリが減ります

uidNumber、gidNumber、homeDirectory のない人はもはや posixAccount ではなく、gidNumber のないグループはもはや posixGroup ではありません。(objectClass=posixAccount) や (objectClass=posixGroup) を検索するプログラムは、それらを見つけられなくなります。これには v0.13.0 までの go-authn/directory の ldapdir が含まれ、したがって directory v0.14.0 を要求するまでの go-fileshare も含まれます。v0.14.0 の既定値はaccount、uidObject、groupOfNames も読みます(directory)。人とグループにそれらの属性を与えるか、コンシューマーを (objectClass=uidObject) に向けてください。すべての人がそれを持っています。

各形態

RFC 4512 §3.3 が求めるとおり、すべてのスーパークラスを列挙しています。

次を持つ人…objectClasscn
sn なしtop, account (RFC 4524 §3.1)別のクラスが許す場合のみ
sn ありtop, person, organizationalPerson, inetOrgPerson (RFC 4519, RFC 2798)あり
… さらに uidNumber、gidNumber、homeDirectory の三つすべて+ posixAccount (RFC 2307)あり
… さらに SSH 鍵+ ldapPublicKey (openssh-lpk)、sshPublicKey を伴う
… さらに sambaSID を伴う公開された NT ハッシュ+ sambaSamAccount (Samba)、sambaSID と sambaNTPassword を伴う: samba ブロックを参照許可
… 常に+ uidObject (RFC 4519 §3.14)。そのため (objectClass=uidObject) で全員が見つかる
次を持つグループ…objectClassメンバー
gidNumber ありtop, posixGroup (RFC 2307)memberUid、名前
gidNumber なし、メンバーありtop, groupOfNames (RFC 4519 §3.5)member、このサーバーが公開する DN
gidNumber なし、メンバーなしtop, organizationalRole (RFC 4519 §3.10)なし
gidNumber あり、メンバーなしtop, posixGroupなし: 属性には少なくとも一つの値が必要

uid は人の名前で、クラスが許す場合は cn も同じです。account 単独では cn を許さない(その MAY は description、seeAlso、l、o、ou、host) ため、sn がなく POSIX の三つ組もない人は、uid を持ち cn を持ちません。

これらの選択の理由を、authnd 自身の言葉で示します。

  • posixGroup は RFC 2307 に従い、draft-howard-rfc2307bis-02 には従いません。 このドラフトは posixGroup を AUXILIARY にしており、未公開のまま失効しました。AUXILIARY のposixGroup には構造クラスが必要で、それは groupOfNames ですが、空のグループはその member を与えられません。
  • gidNumber のない空のグループには organizationalRole。 groupOfNames と groupOfUniqueNames はどちらもメンバーを必須とし、メンバーをでっち上げる方法はどれも偽りです。member: "" はルート DSE を指し、グループ自身の DN を入れると自分自身のメンバーになってしまいます。organizationalRole は、唯一の MUST が cn である標準の構造クラスで、groupOfNames と同様に description、ou、seeAlso を受け付けます。
  • DIT コンテンツルールのない補助クラス。 RFC 4512 §2.4.3 は、構造クラスに DIT コンテンツルールがないエントリに補助クラスを付けることを禁じています。実用されているディレクトリサーバーはすべてそれを許しており、Validate も同様です。

属性の追加

ソースが誰かについて述べるもので、何も証明しないもの、たとえば uidNumber、ホームディレクトリ、メールアドレスは属性であり、与えられたとおりに公開されます。これは go-authn/directory の属性で、v0.13.0 からあり、認証情報とは切り離されています。シークレットを保持する名前や、サーバー自身が導出する名前は、何かが読まれる前に拒否されます。

user または group ブロックで 

user "dora" {
  password_file   = "/etc/authnd/passwords/dora.pw"
  authorized_keys = ["ssh-ed25519 AAAA… dora@laptop"]
  attributes = {
    sn            = "Explorer"          # inetOrgPerson
    uidNumber     = "1000"              # the three: posixAccount
    gidNumber     = "1000"
    homeDirectory = "/home/dora"
    mail          = ["dora@example.org", "d.explorer@example.org"]
  }
}

group "engineers" {
  members    = ["dora", "eli"]
  attributes = { gidNumber = "2000" }   # a posixGroup; without it, a groupOfNames
}

値は文字列または文字列のリストです。null はその属性を省きます。数値は拒否されます。LDAP の値は文字列であり、authnd は数値の綴り方を決めないためです。

$ authnd check cases/number.hcl
authnd: user "alice": attributes: uidNumber is the number 1000: write it as a string, "1000" -- an LDAP value is a string, and this does not choose how a number is spelled

$ authnd check cases/secret.hcl
authnd: user "alice": attributes: directory: not an attribute this package carries: "userPassword" holds a secret, and attributes are published: a credential has its own option or none

大文字小文字にかかわらず、同様に拒否されるもの: シークレットを保持するあらゆる名前(userPassword、sambaNTPassword、unicodePwd、krbPrincipalKey、および go-authn/directory のリストの残り、または password、passwd、pwd、secret、credential、hash、privatekey を含む名前)、authorized_keys がある sshPublicKey、サーバーが導出する uid、cn、objectClass、members が担う member、memberUid とその他のメンバーシップ属性、サーバーが維持する操作属性、そして数値形式の名前 (2.5.4.35 は userPassword) です。

SQL データベースで

users "sql" ブロックの二つの任意のクエリは、属性を列のエイリアスで読みます。最初の列は人またはグループの名前で、それ以外のすべての列は、そのエイリアスで名付けられた属性です。

users "sql" {
  driver   = "sqlite"
  dsn_file = "/etc/authnd/people.dsn"
  users    = "select login, secret, null, ssh_keys from staff"
  groups   = "select team, member from teams"
  users_attributes  = "select login, sn, uid as uidNumber, gid as gidNumber, home as homeDirectory, mail from person_attrs"
  groups_attributes = "select team, gid as gidNumber, description from team_attrs"
}
  • 位置で指定する users と groups のクエリは変わらず、六番目の位置の列は引き続き拒否されます。属性は名前で、専用のクエリで渡されます。
  • エイリアスが属性記述でない列 (count(*) のようなエイリアスのない式) や、認証情報を名指しする列は、行が読まれる前に、列番号付きで拒否されます。
  • NULL と '' は存在しないものとして扱います。一つの名前が複数の行に現れることがあり、そのすべての値が保持されます。そのため、アドレスのテーブルへの結合は、人に複数の値を与えます。
  • groups_attributes にだけ名前のあるグループは、メンバーがいなくても存在します。人自身のプライマリグループはそのように書きます。

エイリアスの大文字小文字はデータベース次第です

PostgreSQL は引用符のないエイリアスを小文字に畳み込みます。as uidNumber は uidnumber として返ります。属性名は大文字小文字を区別しないので、同じ属性であり、どの LDAP クライアントにとっても同じエントリですが、authnd が表示する綴りはデータベースのものです。綴りが重要な場合はエイリアスを引用符で囲んでください: gid as "gidNumber"。SQLite はエイリアスを書かれたとおりに保ちます。

別の LDAP ディレクトリから

users "ldap" ブロックは、指示された属性を、各人のエントリと各グループのエントリからコピーします。attributes = ["mail", "uidNumber", "homeDirectory"] と group_attributes = ["gidNumber"] のように指定します。人々を参照してください。

設定と、それが公開するもの

上の SQL ブロックに reader を加え、五人と四つのグループを持つ SQLite データベースに対して、v0.11.0 のリリースバイナリが check した結果です。

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret, null, ssh_keys from staff"
  groups   = "select team, member from teams"
  users_attributes  = "select login, sn, uid as uidNumber, gid as gidNumber, home as homeDirectory, mail from person_attrs"
  groups_attributes = "select team, gid as gidNumber, description from team_attrs"
}
$ authnd check etc/authnd

何が破棄され、何が保留されるか

与えられたものエントリ理由
uidNumber、gidNumber、homeDirectory なし、sn なしaccount, uidObject、この二つなしno class of the entry allows it; posixAccount would
mail、sn なしaccount, uidObject、mail なしno class of the entry allows it; inetOrgPerson would
スキーマが定義していない型残りの部分the schema served here does not define it
gidNumber のないグループへの mailgroupOfNames、mail なし
POSIX の三つ組と共に二つの homeDirectory 値保留: SINGLE-VALUE であり、破棄できるものがない
整数でない gidNumber保留: その構文に適合しない

破棄されるのはソースが与えたものだけで、どの属性が許されないかは Validate の答えであり、スキーマの二度目の解釈ではありません。エントリは破棄の後にもう一度検証されます。それでも適合しないエントリは保留されます。どの検索にも現れず、起動ログがその名前を挙げ、check が Validate の見つけたすべての問題とともに一覧します。authnd 自身が導出する属性(uid、cn、objectClass、sshPublicKey、sambaSID、sambaNTPassword) がスキーマに拒否された場合は authnd の欠陥であり、その属性なしで公開するのではなく、エントリを保留します。

ここでは alice の gidNumber が単語になっています。

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

user "alice" {
  password_file = "etc/authnd/alice.pw"
  attributes = {
    uidNumber     = "1000"
    gidNumber     = "staff"
    homeDirectory = "/home/alice"
  }
}

user "bob" { password_file = "etc/authnd/bob.pw" }
$ authnd check cases/withheld.hcl
ldap://127.0.0.1:3893, base dc=example,dc=org

USER   FROM                    CAN PROVE   PUBLISHED AS               WITH
alice  the configuration file  a password  NOT PUBLISHED (see below)  uid, cn, gidNumber, homeDirectory and uidNumber
bob    the configuration file  a password  account, uidObject         uid

bob has no uidNumber, gidNumber or homeDirectory: not a posixAccount, published as account, uidObject
alice is NOT published: as account, posixAccount, uidObject it fails the schema:
  - the value "staff" of gidNumber is not of its syntax 1.3.6.1.4.1.1466.115.121.1.27

a bind carries a password
cn=reader,dc=example,dc=org may search; every other bound client may not
sambaNTPassword is not published, so nothing here can authenticate an SMB session (NTLMv2 needs the password or its MD4, and a bind cannot answer it)

保留されるのは検索が返すエントリであって、ID ではありません。

提供するスキーマ

ルート DSE がそれを指し (subschemaSubentry: cn=Subschema、ルート DSE上)、cn=Subschema のベース検索がそれを返します (RFC 4512 §4.2)。go-authn/ldap が組み込む標準の定義、つまり RFC 4512、4517、4519、4523、4524、2798、2307、3672、3045 と openssh-lpk に加え、samba ブロックがある場合は Samba のsambaSamAccount、sambaSID、sambaNTPassword です。定義は、名前を指定するか + を付けて要求した場合にのみ公開されます。印のある箇所は省略しています。

$ ldapsearch -x -LLL -o ldif-wrap=no -H ldap://127.0.0.1:3893 -D cn=reader,dc=example,dc=org -y reader.pwin -s base -b cn=Subschema '+' '*'

エントリ全体は 327 行で、49 の構文、40 のマッチングルール、36 のマッチングルール使用、143 の属性型、52 のオブジェクトクラスでした。ベース以下の検索と違い、サブスキーマエントリはルート DSE と同様に匿名のクライアントにも応答されます。-D と -y を付けない同じクエリがそれを返しました。

フィルターはスキーマのマッチングルールを使うので、(uidNumber>=1000) は整数として比較します。uidNumber と gidNumber には ORDERING integerOrderingMatch があり、RFC 2307 はこれを与えていません。slapd とdraft-howard-rfc2307bis-02 は与えており、go-authn/ldap も同様です(唯一の逸脱)。文字列として扱うと、1000 は 999 より前に並びます。

$ ldapsearch -x -LLL -H ldap://127.0.0.1:3893 -D cn=reader,dc=example,dc=org -y reader.pwin -b dc=example,dc=org '(uidNumber>=1000)' uidNumber
dn: uid=dora,ou=people,dc=example,dc=org
uidNumber: 1000

dn: uid=eli,ou=people,dc=example,dc=org
uidNumber: 1001

$ ldapsearch -x -LLL -H ldap://127.0.0.1:3893 -D cn=reader,dc=example,dc=org -y reader.pwin -b dc=example,dc=org '(uidNumber>=999)' uidNumber
dn: uid=dora,ou=people,dc=example,dc=org
uidNumber: 1000

dn: uid=eli,ou=people,dc=example,dc=org
uidNumber: 1001

hal はいません。hal の uidNumber は破棄されたためです。uid のように ORDERING ルールのない属性への範囲指定は Undefined となり、何にも一致しません。
