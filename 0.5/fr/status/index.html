État

Les versions que décrivent ces pages, ce que chaque version a ajouté, et ce qui n'est pas encore implémenté.

Ces pages sont la version 0.5 de la documentation, et décrivent :

programmeversionmodule
authndv0.12.4github.com/go-authn/authnd
authn-bridgev0.23.4github.com/go-authn/bridge
authn-revokdv0.6.6github.com/go-authn/revocation
sshcert-authorizev0.1.9github.com/go-authn/sshcert

Les versions des bibliothèques sont sur leur propre page ;ldap est en v0.10.2, avec une BuildError typée pour un schéma qui ne se construit pas, les schémas en HCL2 et le convertisseurldapschema, et directory en v0.15.0, avec les classes d’objet déclarées.authnd v0.12.4 embarque ldap v0.10.2 et directory v0.15.0.Une nouvelle version mineure de l’un des programmes ci-dessus est une nouvelle version de la documentation,de sorte que les pages qu’une personne trouve sous /docs/0.5/ continuent de décrire ce qu’elle a installé ; celles des versions précédentes restent sous /docs/0.1/,/docs/0.2/, /docs/0.3/ et /docs/0.4/.

Sécurité : utilisez authnd v0.12.0, pas la v0.11.1

authnd vérifie des certificats (x509.Certificate.Verify, atteint depuis main selon govulncheck), et le crypto/x509 de Go 1.27.2 ne révoquait pas la confiance dans les certificats intermédiaires compromis que nomme GO-2026-6809.Les binaires de la v0.11.1 ont été compilés avec Go 1.27.2 et sont touchés. La v0.12.0 est compilée avec Go 1.27.3 et sa directive go est 1.27.3 : go install passe donc de lui-même à la chaîne d’outils corrigée ; govulncheck sous 1.27.3 ne signale aucune vulnérabilité. Son binaire de la version affiche go1.27.3 dansgo version -m. Voir la note de mise à niveau.

Sécurité : prenez authn-bridge v0.23.3 et authn-revokd v0.6.5

Sous Go 1.27.2, govulncheck signale GO-2026-6809 dans les deux programmes : Certificate.Verify de crypto/x509 ne rejetait pas des certificats intermédiaires compromis connus. Le correctif est dans Go 1.26.10 et 1.27.3. Les binaires de version construits avec un Go plus ancien sont concernés. v0.23.3 et v0.6.5 sont construits avec Go 1.27.3 et leur directive go vaut 1.27.3 ; go install bascule donc de lui-même vers la chaîne d’outils corrigée, et leurs binaires de version affichent go1.27.3 dans go version -m. sshcert n’est pas concerné et n’a pas de nouvelle version.

Ce que chaque version a ajouté

Chaque ligne est le changement pour lequel une version a été publiée. Les versions qui n’ont fait que mettre à jour des dépendances sont omises, sauf celles que décrit cette version de la documentation.

authnd

v0.1.0un serveur LDAP pour des personnes qui sont ailleurs : un fichier, une base de données SQL, un autre annuaire
v0.2.0un second facteur, sur un protocole qui n’a qu’un champ
v0.5.0des changements de mot de passe qui touchent exactement une identité ; un rechargement sans concurrence ; le KDC voit les changements
v0.6.0les correctifs de sécurité d’oidc, directory, ldap, totp et mfa
v0.7.0l’ancien mot de passe est exigé pour en changer ; les secrets sont comparés sous forme d’empreintes de longueur fixe
v0.8.2un code ne compte que derrière le bon mot de passe ; un lecteur est identifié par son DN configuré
v0.9.0compilé et testé avec Go 1.27.1, épinglé au lieu de stable
v0.9.2binaires de version, SHA256SUMS et provenance de compilation à chaque étiquette
v0.9.3binaires compilés hors de l’extraction ; chacun doit annoncer exactement l’étiquette
v0.9.4un SIGHUP n’arrête plus authnd : il est journalisé, et rien n’est rechargé
v0.9.5la publication vérifie les informations de compilation de chaque binaire, pas d’un seul
v0.9.6check dit pourquoi chaque personne ne peut pas recevoir de ticket
v0.10.0check ouvre le certificat et le keytab, comme le fait le serveur ; il nomme qui ne peut pas se lier avec un mot de passe, et qui un jeton admet encore ; la ligne d’écoute vient après l’ouverture du royaume
v0.10.1go-authn/kdc v0.4.2 : un till de 19700101000000Z obtient le ticket le plus long, et non un ticket expiré en 1970
v0.10.2go-authn/directory v0.12.0 : un groupe vide est publié comme posixGroup sans memberUid
v0.11.0des entrées des schémas standard, chacune soumise au schéma servi à cn=Subschema ; attributes, users_attributes et groups_attributes ; (uidNumber>=1000) compare des entiers. ⛔ publish_nt_hash demande un bloc samba, et un consommateur qui filtre sur posixAccount ou posixGroup voit moins d’entrées
v0.11.1la ligne de démarrage ne nomme que les sources d’où quelqu’un est servi : sans bloc user, elle ne nomme plus le fichier de configuration
v0.12.0schémas de site : schema_files (.schema OpenLDAP et LDIF cn=config, tels que publiés ; une redéfinition est refusée, même identique, comme le fait slapd) et un bloc schema { } ; classes auxiliaires déclarées par source avec object_classes, validées au démarrage et publiées avec leurs superclasses ; check rapporte les fichiers, les déclarations, les classes retirées à une personne faute d’un MUST, et les groupes sur lesquels deux sources sont en désaccord. ⛔ Compilée avec Go 1.27.3 : les binaires de la v0.11.1 (Go 1.27.2) sont touchés par GO-2026-6809
v0.12.1un fichier ou un bloc de schéma qui ne se construit pas est refusé à la position que porte la BuildError de go-authn/ldap v0.10.0, avec une colonne (site.schema:6: devient site.schema:6:1:) ; le message se termine par le genre de refus, et un doublon dit où se trouve sa première définition
v0.12.2les binaires de release sont liés avec -ldflags="-w" au lieu de -s -w : la table des symboles est conservée, donc govulncheck -mode binary est précis au lieu de signaler des vulnérabilités dans du code qui n’est pas lié ; environ 9 % plus gros (18,8 Mo à 20,5 Mo sur darwin/arm64)
v0.12.3go-authn/ldap v0.10.1 : les schema_files sont lus en temps linéaire. ⛔ Jusqu’à v0.12.2, un gros fichier de schéma fait de courtes lignes de continuation (4 Mio : environ trois minutes) bloquait le démarrage : un déni de service par un fichier qu’on ne maîtrise pas
v0.12.4go-authn/ldap v0.10.2 : les valeurs de DESC de 13 définitions de la RFC 2307 dans cn=Subschema (uidNumber, gidNumber, ipHostNumber, ipNetworkNumber, ipNetmaskNumber, macAddress et les classes ipService, ipProtocol, oncRpc, ipHost, ipNetwork, ieee802Device, bootableDevice) ne portent plus l’indentation de la mise en page de la RFC : DESC 'An integer uniquely identifying a user in an administrative domain', et non ... in an administrative domain'

oidc v0.4.1testée avec Go 1.27.2 ; ni le code ni le go.mod n’ont changé

Pas encore implémenté

  • Les écritures par LDAP, au-delà d’une personne qui change son propre mot de passe. authnd répond à une modification de son propre userPassword et à l’opération de modification de mot de passe de la RFC 3062 (ce qu’envoie ldappasswd), toutes deux uniquement avec le mot de passe actuel, et à rien d’autre : add, delete et modifyDN existent dans go-authn/ldap et ne sont délibérément pas branchés (server.go). La bibliothèque porte une modification sous forme de liste ordonnée (RFC 4511 4.6) et répond aux contrôles de lecture d’entrée (RFC 4527), donc la forme est là ; ce qui manque, c’est la politique de qui peut écrire quoi.
  • Un second facteur dans Kerberos : la pré-authentification OTP (RFC 6560) dans FAST (RFC 6113). Tant qu’elle n’existe pas, un bloc kerberos et un bloc mfa ne peuvent pas être configurés ensemble.
  • RC4-HMAC : le royaume n’émet que aes256-cts-hmac-sha1-96, donc une personne connue uniquement par une empreinte NT ne peut pas recevoir de ticket. C’est un choix (RC4 est déprécié par la RFC 8429), pas une lacune en attente d’être comblée.
