Entrées et schéma

Les entrées que publie authnd, et le schéma qu'il sert

Ce sous quoi chaque personne et chaque groupe est publié, le schéma servi à cn=Subschema que respecte chaque entrée, comment ajouter des attributs dans un fichier ou une requête SQL, et ce qui est écarté ou retenu.

Chaque entrée que publie authnd respecte le schéma qu’il sert. Depuis la v0.11.0, chaque personne et chaque groupe est une entrée des schémas standard,construite à partir de ce que sa source a donné, et vérifiée par leschema.Validate de go-authn/ldap contre le schéma qu’un client peut lire àcn=Subschema, avant d’être jamais renvoyée par une recherche. Un client qui lit le schéma et le croit — un navigateur LDAP, un outil de synchronisation, un annuaire qui réplique celui-ci — se voit montrer ce qu’on lui a annoncé.Jusqu’à la v0.10.2, chaque personne était top, person, posixAccount sans aucun des attributs que ces classes exigent, et sambaNTPassword se trouvait sur une entrée dont aucune classe ne l’autorise.

Un consommateur qui filtre sur posixAccount ou posixGroup voit moins d’entrées

Une personne sans uidNumber, gidNumber et homeDirectory n’est plus unposixAccount, et un groupe sans gidNumber n’est plus un posixGroup. Un programme qui cherche (objectClass=posixAccount) ou(objectClass=posixGroup) ne les trouve plus. Cela comprend le ldapdir de go-authn/directory jusqu’à la v0.13.0, et donc go-fileshare tant qu’il n’exige pas directory v0.14.0, dont les valeurs par défaut lisent aussiaccount, uidObject et groupOfNames (directory).Donnez ces attributs aux personnes et aux groupes, ou pointez le consommateur sur (objectClass=uidObject), que porte chaque personne.

Les formes

Chaque superclasse est listée, comme le demande la RFC 4512 §3.3.

une personne avec…objectClasscn
pas de sntop, account (RFC 4524 §3.1)seulement quand une autre classe l’autorise
sntop, person, organizationalPerson, inetOrgPerson (RFC 4519, RFC 2798)oui
… et uidNumber, gidNumber, homeDirectory, les trois+ posixAccount (RFC 2307)oui
… et des clés SSH+ ldapPublicKey (openssh-lpk), avec sshPublicKey
… et une empreinte NT publiée avec un sambaSID+ sambaSamAccount (Samba), avec sambaSID et sambaNTPassword : voir le bloc sambaautorisé
… toujours+ uidObject (RFC 4519 §3.14), si bien que (objectClass=uidObject) trouve tout le monde
un groupe avec…objectClassmembres
un gidNumbertop, posixGroup (RFC 2307)memberUid, des noms
pas de gidNumber, quelqu’un dedanstop, groupOfNames (RFC 4519 §3.5)member, les DN que publie ce serveur
pas de gidNumber, personne dedanstop, organizationalRole (RFC 4519 §3.10)aucun
un gidNumber, personne dedanstop, posixGroupaucun : un attribut a au moins une valeur

uid est le nom de la personne, et cn aussi partout où une classe l’autorise. Un account seul n’autorise pas cn (son MAY est description,seeAlso, l, o, ou et host), si bien qu’une personne sans sn et sans le trio POSIX porte uid et pas de cn.

Pourquoi ces choix, selon les raisons propres d’authnd :

  • posixGroup suit la RFC 2307, pas draft-howard-rfc2307bis-02. Le brouillon fait de posixGroup une classe AUXILIARY et a expiré sans être publié ; un posixGroup AUXILIARY aurait besoin d’une classe structurelle à côté de lui, groupOfNames, dont un groupe vide ne peut pas donner lemember.
  • organizationalRole pour un groupe vide sans gidNumber. groupOfNames et groupOfUniqueNames exigent tous deux un membre, et les façons d’en inventer un sont fausses : member: "" nomme le DSE racine, et le DN du groupe lui-même en fait un membre de lui-même. organizationalRole est la seule classe structurelle standard dont l’unique MUST est cn, et elle prend description, ou et seeAlso comme groupOfNames.
  • Des classes auxiliaires sans règles de contenu DIT. La RFC 4512 §2.4.3 interdit les classes auxiliaires sur une entrée dont la classe structurelle n’a pas de règle de contenu DIT. Tous les serveurs d’annuaire en usage les autorisent, et Validate aussi.

Ajouter des attributs

Ce qu’une source dit de quelqu’un sans rien prouver — un uidNumber, un répertoire personnel, une adresse de messagerie — est un attribut, publié tel quel. Ce sont les attributs de go-authn/directory, depuis la v0.13.0, et ils sont tenus à l’écart des identifiants : un nom qui contient un secret, ou un nom que le serveur dérive lui-même, est refusé avant que quoi que ce soit ne soit lu.

Dans un bloc user ou group 

user "dora" {
  password_file   = "/etc/authnd/passwords/dora.pw"
  authorized_keys = ["ssh-ed25519 AAAA… dora@laptop"]
  attributes = {
    sn            = "Explorer"          # inetOrgPerson
    uidNumber     = "1000"              # the three: posixAccount
    gidNumber     = "1000"
    homeDirectory = "/home/dora"
    mail          = ["dora@example.org", "d.explorer@example.org"]
  }
}

group "engineers" {
  members    = ["dora", "eli"]
  attributes = { gidNumber = "2000" }   # a posixGroup; without it, a groupOfNames
}

Une valeur est une chaîne ou une liste de chaînes ; null omet l’attribut.Un nombre est refusé, parce qu’une valeur LDAP est une chaîne et qu’authnd ne choisit pas comment un nombre s’écrit :

$ authnd check cases/number.hcl
authnd: user "alice": attributes: uidNumber is the number 1000: write it as a string, "1000" -- an LDAP value is a string, and this does not choose how a number is spelled

$ authnd check cases/secret.hcl
authnd: user "alice": attributes: directory: not an attribute this package carries: "userPassword" holds a secret, and attributes are published: a credential has its own option or none

Sont refusés de la même façon, quelle que soit leur casse : tout nom qui contient un secret (userPassword, sambaNTPassword, unicodePwd,krbPrincipalKey et le reste de la liste de go-authn/directory, ou tout nom contenant password, passwd, pwd, secret, credential, hash ouprivatekey) ; sshPublicKey, qui a authorized_keys ; uid, cn etobjectClass, que le serveur dérive ; member, memberUid et les autres attributs d’appartenance, auxquels répond members ; les attributs opérationnels qu’un serveur maintient ; et un nom sous forme numérique(2.5.4.35 est userPassword).

Dans une base de données SQL

Deux requêtes facultatives d’un bloc users "sql" lisent des attributs par alias de colonne. La première colonne est le nom de la personne ou du groupe ; chaque autre colonne est un attribut nommé par son alias :

users "sql" {
  driver   = "sqlite"
  dsn_file = "/etc/authnd/people.dsn"
  users    = "select login, secret, null, ssh_keys from staff"
  groups   = "select team, member from teams"
  users_attributes  = "select login, sn, uid as uidNumber, gid as gidNumber, home as homeDirectory, mail from person_attrs"
  groups_attributes = "select team, gid as gidNumber, description from team_attrs"
}
  • Les requêtes positionnelles users et groups sont inchangées, et une sixième colonne positionnelle est toujours refusée : les attributs viennent par nom, dans leur propre requête.
  • Une colonne dont l’alias n’est pas une description d’attribut (une expression sans alias comme count(*)), ou nomme un identifiant, est refusée avec son numéro de colonne avant qu’une ligne ne soit lue.
  • NULL et '' valent absence. Un nom peut revenir sur plusieurs lignes, et les valeurs de toutes sont gardées, si bien qu’une jointure vers une table d’adresses en donne plusieurs à une personne.
  • Un groupe nommé seulement dans groups_attributes existe, sans personne dedans : c’est ainsi que s’écrit le groupe principal propre d’une personne.

La casse d’un alias est celle de la base de données

PostgreSQL met en minuscules un alias sans guillemets : as uidNumber revient sous la forme uidnumber. Les noms d’attributs ne tiennent pas compte de la casse, donc c’est le même attribut et l’entrée est la même entrée pour tout client LDAP, mais la graphie qu’affiche authnd est celle de la base. Mettez l’alias entre guillemets là où la graphie compte : gid as "gidNumber".SQLite garde un alias tel qu’il est écrit.

Depuis un autre annuaire LDAP

Un bloc users "ldap" copie les attributs qu’on lui indique, depuis l’entrée de chaque personne et celle de chaque groupe : attributes = ["mail", "uidNumber", "homeDirectory"] et group_attributes = ["gidNumber"]. Voirpersonnes.

Une configuration, et ce qu’elle publie

Le bloc SQL ci-dessus, avec un lecteur, sur une base SQLite de cinq personnes et quatre groupes, tel que le vérifie le binaire de la version v0.11.0 :

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret, null, ssh_keys from staff"
  groups   = "select team, member from teams"
  users_attributes  = "select login, sn, uid as uidNumber, gid as gidNumber, home as homeDirectory, mail from person_attrs"
  groups_attributes = "select team, gid as gidNumber, description from team_attrs"
}

Le schéma qu’il sert

Le DSE racine le nomme (subschemaSubentry: cn=Subschema, surle root DSE),et une recherche de base sur cn=Subschema le renvoie (RFC 4512 §4.2) : les définitions standard qu’embarque go-authn/ldap — RFC 4512, 4517, 4519, 4523,4524, 2798, 2307, 3672 et 3045, et openssh-lpk — plus sambaSamAccount,sambaSID et sambaNTPassword de Samba quand il y a unbloc samba. Les définitions ne sont publiées que lorsqu’on les demande par leur nom ou avec+. Abrégé là où c’est indiqué :
