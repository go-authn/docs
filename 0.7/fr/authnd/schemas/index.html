Schémas de site

Schémas de site, et les classes qu'une source déclare

Servir SUPANN, eduPerson ou les attributs propres à un site : schema_files et le bloc schema ajoutent des définitions, object_classes déclare quelles classes auxiliaires portent les personnes et les groupes d'une source, et check dit ce qui a été retiré. Depuis la v0.13.0, les règles de contenu DIT, les formes de noms et les règles de structure DIT sont appliquées.

Un attribut SUPANN ou eduPerson est écarté tant qu’une classe de son entrée ne l’autorise pas. authnd ne publie que ce que permet le schéma qu’il sert (voirles entrées),et le schéma standard ne connaît rien de supannEtablissement ni deeduPersonAffiliation. À partir de la v0.12.0, un site dit trois choses, dans cet ordre :

  1. quelles définitions ajouter : schema_files, les fichiers que son slapd charge déjà, et un bloc schema { } pour ce qui n’est que local ;
  2. quelles classes auxiliaires portent ses personnes et ses groupes : object_classes ;
  3. rien d’autre. Une classe est déclarée, jamais déduite : un attribut qui apparaît dans une base de données ne change pas ce sous quoi une entrée est publiée.

L’exemple de cette page est un exemple

example.schema ci-dessous a été écrit pour cette page. Ses OID sont sous1.3.6.1.4.1.99999, un arc que personne ne se voit attribuer : utilisez les vôtres, et ne copiez jamais ceux-ci. Pour SUPANN, voir la fin de la page.

Un exemple : un schéma, une base de données, une configuration

Un schéma sous la forme .schema d’OpenLDAP : une classe qu’une source peut déclarer(exampleStaff, AUXILIARY, avec un MUST), et une qu’elle ne peut pas(exampleUnit, STRUCTURAL).

objectidentifier exampleRoot  1.3.6.1.4.1.99999
objectidentifier exampleAttr  exampleRoot:1
objectidentifier exampleClass exampleRoot:2

attributetype ( exampleAttr:1 NAME 'exampleBadge'
	DESC 'the number on a badge'
	EQUALITY caseIgnoreMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

attributetype ( exampleAttr:2 NAME 'exampleEmployeeId'
	DESC 'a staff number'
	EQUALITY caseExactMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

# AUXILIARY: it can be declared. exampleStaff has a MUST.
objectclass ( exampleClass:1 NAME 'exampleStaff' SUP top AUXILIARY
	DESC 'somebody employed: has a staff number'
	MUST exampleEmployeeId
	MAY exampleBadge )

# STRUCTURAL: it cannot be declared (an entry has one structural chain).
objectclass ( exampleClass:2 NAME 'exampleUnit' SUP top STRUCTURAL
	MUST cn )

Une base de données SQLite de trois personnes, avec sn, un badge et un numéro de personnel(sqlite3 var/people.db < people.sql) :

create table staff (login text primary key, secret text);
create table person_attrs (login text primary key, sn text, badge text, empid text, locker text);
insert into staff values ('ann', 'ann-password'), ('ben', 'ben-password'), ('cat', 'cat-password');
insert into person_attrs values ('ann', 'Archer', 'B-0001', 'E-1001', 'L-12'), ('ben', 'Brook', 'B-0002', null, null), ('cat', 'Cole', null, 'E-1003', null);

Et la configuration :

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

# Files first, then the blocks: a definition may use anything before it.
schema_files = ["etc/authnd/example.schema"]

schema {
  attribute_type "exampleLocker" {
    oid    = "1.3.6.1.4.1.99999.1.3"
    syntax = "1.3.6.1.4.1.1466.115.121.1.15"
  }
  object_class "exampleLockerHolder" {
    oid  = "1.3.6.1.4.1.99999.2.3"
    kind = "auxiliary"
    may  = ["exampleLocker"]
  }
}

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret from staff"
  users_attributes = "select login, sn, badge as exampleBadge, empid as exampleEmployeeId, locker as exampleLocker from person_attrs"
  object_classes   = ["exampleStaff", "exampleLockerHolder"]   # declared, never inferred
}

schema_files

schema_files est une liste de fichiers .schema d’OpenLDAP ou de fichiers LDIF cn=config.Ils sont chargés tels que publiés, dans l’ordre, par-dessus le schéma standard (et les trois définitions de Samba, avec le bloc samba), par leslecteurs compatibles slapd de go-authn/ldap :n’importe quel ordre des termes, les continuations de slapd et de la RFC 2849, le base64, les préfixes de longueur {N}, et les macros objectidentifier, qu’un fichier peut définir et que le suivant utilise, comme à travers l’include de slapd. Rien n’est converti au préalable : le fichier que charge le slapd d’un site est le fichier que charge authnd. Les définitions sont servies àcn=Subschema.

  • Un chemin relatif l’est au répertoire de travail, comme tous les autres chemins de la configuration. Utilisez des chemins absolus dans un service : le répertoire de travail d’une unité systemd est /.

  • Chaque fichier doit être un fichier ordinaire d’au plus 4 Mio, et il est lu une seule fois, au démarrage.

  • Les fichiers décident de ce que chaque entrée peut contenir. Ce ne sont pas des secrets, mais gardez-les avec le reste de la configuration : root:authnd, mode 0640, dans un répertoire que seul root peut écrire (l’installation).

  • Un fichier qui ne se construit pas refuse le démarrage, et check, avec le fichier, la ligne et la colonne où la définition commence, et le genre de refus à la fin du message : une superclasse, un attribut, une règle de comparaison ou une syntaxe inconnus (unknown reference), une classe structurelle dérivée d’une classe auxiliaire (kind violation), un OID ou un nom défini deux fois (duplicate OID, duplicate name). Depuis la v0.12.1,la place et le genre viennent de la*schema.BuildError typée de go-authn/ldap, et non de la lecture de son message. Une définition lue dans un fichier commence à la colonne 1, y compris quand son texte est replié sur plusieurs lignes. Un doublon dit où se trouve sa première définition, et une redéfinition dit quel fichier standard, ou quelle ligne d’un fichier précédent, détient l’original. Deux exemples :

    cases/unknown.schema a un MAY qui n’est défini nulle part :

    # exampleB has a MAY that is defined nowhere.
objectclass ( 1.3.6.1.4.1.99999.2.9 NAME 'exampleB' SUP top AUXILIARY
	MAY noSuchAttribute )
    $ authnd check cases/unknown.hcl
authnd: schema_files: cases/unknown.schema:2:1: the object class exampleB has MAY noSuchAttribute, which is not a defined attribute type (unknown reference)

    cases/twice.schema donne un même OID à deux types d’attribut :

    attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleA'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )

attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleB'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )
    $ authnd check cases/twice.hcl
authnd: schema_files: cases/twice.schema:4:1: the attribute type 1.3.6.1.4.1.99999.1.9 is defined twice (first defined at cases/twice.schema:1:1) (duplicate OID)

Une redéfinition est refusée, même identique

Un fichier ne peut pas définir ce qui est déjà là : les définitions du schéma standard,celles de Samba, ou celles d’un fichier précédent. Elle est refusée même mot pour mot, ce qui est la règle de slapd lui-même : les définitions d’un fichier de schéma passent parparse_at et parse_oc, et slapd répond à un OID ou un nom déjà indexé par Duplicate attributeType (mêmes OID et noms) ou Inconsistent duplicate attributeType (servers/slapd/at.c, oc.c). Seul le schéma codé en dur de slapd a le droit au premier. Un fichier que slapd refuse est un fichier qu’authnd refuse.

L’autre lecture devrait choisir un gagnant, et ce serait un changement silencieux de ce que l’on dit à chaque client qu’est un attribut standard ; refuser nomme la ligne à la place. Le refus dit si le texte était le même. Un fichier qui redéfinit cn (2.5.4.3) avec une définition qui lui est propre :

$ authnd check cases/dup.hcl
authnd: schema_files: cases/cn-copy.schema:1:1: the attribute type cn (2.5.4.3) is already defined by the standard schema (rfc4519.schema:42:1), and this is a different definition: a schema file adds definitions and never replaces one -- slapd refuses this too ("Duplicate attributeType", servers/slapd/at.c and oc.c). Remove it from this file

Le bloc schema { }

Pour les définitions qui ne sont que locales, un bloc schema les contient en HCL2, dans la forme de hclschema :attribute_type, object_class, object_identifier, matching_rule etldap_syntax. Il est lu après les fichiers, il peut donc utiliser leurs définitions, et il peut y en avoir plusieurs.

Les valeurs doivent être des littéraux : ni variables, ni fonctions, ni ${...} ni%{...}. Le bloc est décodé par le même décodeur que celui qui lit un fichier de schéma.hcl, avec les mêmes bornes, et chaque erreur nomme la ligne et la colonne de la configuration elle-même. Un bloc qui n’est pas dans la syntaxe native de HCL est refusé.

object_classes

Une définition dans le schéma autorise un attribut ; elle ne met la classe sur personne. Une source déclare les classes auxiliaires sous lesquelles ses personnes et ses groupes sont publiés :

oùcléce qu’elle déclare
bloc users, de toute sorteobject_classesles classes de chaque personne que donne le bloc
bloc users, de toute sortegroup_object_classesles classes de chaque groupe
bloc userobject_classesles classes de cette personne
bloc groupobject_classesles classes de ce groupe
users "sql" {
  # ...
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

user  "alice" { object_classes = ["siteMember"] }
group "staff" { object_classes = ["supannGroupe"] }

Ces clés sont celles de go-authn/directory, à partir de la v0.15.0(bibliothèque). Les noms sont comparés sans tenir compte de la casse, et gardés une seule fois, dans l’ordre où ils sont écrits.

Ce que fait authnd d’une classe déclarée :

  • Elle est publiée avec ses superclasses, après les classes qu’authnd déduit(RFC 4512 §3.3 : toutes les superclasses des classes nommées sont implicitement ajoutées). Les attributs que la classe autorise sont gardés au lieu d’être écartés.
  • Elle n’est jamais déduite. Une personne dont la source ne déclare rien continue de perdre les attributs qu’aucune de ses classes n’autorise, quoi que contienne la base de données.
  • Une personne à qui manque un MUST d’une classe déclarée est publiée sans cette classe. Ses attributs sont écartés comme tout attribut qu’aucune classe n’autorise, et les deux sont rapportés. C’est la règle qu’authnd suit partout : la personne reste publiée, le problème est dit, rien n’est changé en silence.Retenir la personne la sortirait de toute recherche pour un seul attribut manquant ;publier la classe sans son MUST servirait une entrée qui ne respecte pas le schéma servi.
  • Deux sources peuvent déclarer des classes différentes pour un même groupe. La première source qui déclare des classes pour un groupe décide, en entier, et une liste ultérieure est ignorée : ni fusionnée ni une erreur. check le dit.

Ce qui est refusé, et pourquoi

Une classe déclarée est vérifiée au démarrage, et par check, contre le schéma servi. Elle doit être :

  • définie, par le schéma standard, un fichier ou un bloc ;
  • AUXILIARY (RFC 4512 §4.1.1). Une entrée a exactement une chaîne structurelle(§2.4.2), qu’authnd choisit d’après ce que la personne a ; une déclaration ne peut pas en ajouter une seconde ;
  • pas une classe qu’authnd déduit lui-même : account, inetOrgPerson et ses superclasses, posixAccount, posixGroup, ldapPublicKey, uidObject,sambaSamAccount, groupOfNames et organizationalRole, sous n’importe lequel de leurs noms. Elles découlent de ce qu’une personne ou un groupe a, et une déclaration ne peut pas passer outre check.

Sinon le démarrage est refusé, en nommant le bloc, sa position et la classe.exampleUnit est STRUCTURAL :

$ authnd check cases/structural.hcl
authnd: cases/structural.hcl:10:20: users "sql" object_classes: exampleUnit is STRUCTURAL, and an entry has exactly one structural chain (RFC 4512 §2.4.2), which authnd chooses: only an AUXILIARY class (§4.1.1) can be declared

go-authn/directory vérifie la graphie avant cela : une classe est un descripteur, jamais un OID, un espace, un guillemet ni une parenthèse.

Refusés aussi, pour la même raison de garder le schéma honnête :

refusépourquoi
un fichier qui redéfinit une définition, même mot pour motla règle de slapd : ci-dessus
un fichier qui n’est pas un fichier ordinaire, ou de plus de 4 Mioun FIFO bloquerait le démarrage, /dev/zero ne finirait jamais
un bloc schema avec une variable, une fonction ou ${...}des valeurs littérales seulement, comme dans un fichier de schéma .hcl
une classe indéfinie dans object_classesune promesse que rien ne peut vérifier
une classe STRUCTURAL, ou une que déduit authndla liste ci-dessus

Ce qu’affiche check

Quatre sortes de lignes, en plus de celles d’habitude ; le journal de démarrage porte les mêmes :

  • schema: <file> adds … et schema: the schema block at <file>:<line>:<column> adds … :ce que chaque fichier et chaque bloc a ajouté, compté en macros d’identifiant d’objet, types d’attribut et classes d’objet ;
  • <file>:<line>:<column>: users "sql" declares … for its people (un bloc user ou group dit user "ann" declares … for this person etgroup "staff" declares … for this group) : ce que déclare chaque source ;
  • <name> is published without <class>, which its source declares: …,en nommant le MUST qui manque à la personne ;
  • group staff: the configuration file declares supannGroupe and a postgres database declares eduMember; the first is published and the second is ignored (the first source that declares classes for a group decides) :deux sources en désaccord sur un groupe, ce qui serait sinon silencieux.

Les attributs écartés faute d’une classe sont les lignes is published without <attribute>: no class of the entry allows it; <classes> would queles entrées décrivent déjà : avec une déclaration, elles nomment la classe que vous n’avez pas déclarée.

Règles de contenu DIT, formes de noms et règles de structure DIT

Depuis la v0.13.0, schema_files et le bloc schema { } acceptent aussi les trois sortes de définitions que la RFC 4512 §4.1.6 et §4.1.7 ajoutent aux classes et aux attributs, et authnd les applique (go-authn/ldap v0.11.0 les lit, les construit et les vérifie ; la page de la bibliothèque dit comment) :

définitionRFC 4512ce qu’elle ditce qu’authnd en fait
règle de contenu DIT§4.1.6pour une classe structurelle : quelles classes auxiliaires (AUX) peuvent être ajoutées, quels attributs sont requis (MUST), permis (MAY) ou exclus (NOT)façonne chaque entrée (les données)
forme de nom§4.1.7.2quels attributs nomment (le RDN) une entrée d’une classe structurelletient l’arbre (la configuration)
règle de structure DIT§4.1.7.1où une forme de nom peut être placée : sous l’entrée gouvernée par la règle que nomme son SUPtient l’arbre (la configuration)

Elles sont publiées à cn=Subschema (dITContentRules, nameForms,dITStructureRules) seulement quand il y en a. Sans elles, rien de cette page ne s’applique, et rien ne change par rapport à la v0.12.4.

Même arc d’exemple

rules.schema ci-dessous est, comme example.schema plus haut, écrit pour cette page, sous 1.3.6.1.4.1.99999. Utilisez votre propre arc. Les OID de la règle de contenu et d’inetOrgPerson sont les mêmes par définition : une règle de contenu porte le nom de la classe structurelle à laquelle elle s’applique.

Un schéma avec une règle de chaque sorte, et son HCL

Sous la forme .schema d’OpenLDAP. ditcontentrule est la directive de slapd.conf(5) ; nameform et ditstructurerule sont celles de go-authn/ldap,puisque slapd n’en a pas (plus bas). authnd vérifie aussi l’arbre qu’il publie (suffixe, ou=people, ou=groups, comptes, personnes et groupes dessous), si bien que le fichier contient cinq formes de noms et cinq règles de structure, et non une de chaque :

# Rules for the tree authnd publishes. 1.3.6.1.4.1.99999 is an example arc:
# nobody is assigned it, use your own.

# A content rule belongs to a structural class and takes that class's OID.
# inetOrgPerson (2.16.840.1.113730.3.2.2): posixAccount and uidObject may be
# added, ldapPublicKey may not; telephoneNumber is required; description is
# precluded.
ditcontentrule ( 2.16.840.1.113730.3.2.2 NAME 'examplePersonRule'
	AUX ( posixAccount $ uidObject )
	MUST telephoneNumber
	NOT description )

# A name form says which attribute names an entry of a structural class.
nameform ( 1.3.6.1.4.1.99999.9.1 NAME 'exampleDomainForm' OC domain MUST dc )
nameform ( 1.3.6.1.4.1.99999.9.2 NAME 'exampleUnitForm' OC organizationalUnit MUST ou )
nameform ( 1.3.6.1.4.1.99999.9.3 NAME 'exampleAccountForm' OC account MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.4 NAME 'examplePersonForm' OC inetOrgPerson MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.5 NAME 'examplePosixGroupForm' OC posixGroup MUST cn )

# A structure rule gives a name form a place: the rule ID is a number, SUP
# names the rule of the parent entry.
ditstructurerule ( 1 NAME 'exampleSuffix' FORM exampleDomainForm )
ditstructurerule ( 2 NAME 'exampleUnit' FORM exampleUnitForm SUP 1 )
ditstructurerule ( 3 NAME 'exampleAccounts' FORM exampleAccountForm SUP 2 )
ditstructurerule ( 4 NAME 'examplePersons' FORM examplePersonForm SUP 2 )
ditstructurerule ( 5 NAME 'examplePosixGroups' FORM examplePosixGroupForm SUP 2 )

Les mêmes définitions en HCL, telles que les écrit ldapschema v0.11.0(ldapschema to-hcl rules.schema). Chaque bloc est une définition, étiquetée par son premier NAME ; une règle de structure a un id, la form qu’elle place et les règles sup sous lesquelles elle va :

Ce qu’une règle de contenu fait à une entrée

La configuration est deux personnes et deux groupes, avec les règles chargées depuis schema_files. dave a un sn (il est donc un inetOrgPerson), un numéro de téléphone, une description et une clé publique SSH ; erin a un sn et rien d’autre ; staff a un gidNumber ; team n’en a pas :

    telephoneNumber = "+33 1 23 45 67 89"
    description     = "on call"

}

  password   = "erin-password"
  attributes = { sn = "Evans" }
}

  members    = ["dave"]

La règle s’applique à la classe structurelle de l’entrée, et ce qu’elle fait est dit, au démarrage et par check, entrée par entrée :

la règle ditl’entréedit sous la forme
AUX ne liste pas une classe auxiliaire, qu’elle soit déclarée ou qu’authnd la dérive (posixAccount, ldapPublicKey, sambaSamAccount, uidObject)la classe est écartée, avec les attributs que seule elle autorisait (et les sshPublicKey, sambaSID et sambaNTPassword qu’authnd ajouterait pour elle) ; une classe déclarée dont la superclasse est écartée part avec elle<name> is published without <class>: the DIT content rule <rule> does not allow it (not in its AUX)
NOT nomme un attributl’attribut est retiré, quelle que soit son origine<name> is published without <attribute>: the DIT content rule <rule> precludes it (NOT)
MUST nomme un attribut que l’entrée n’a pasl’entrée est laissée de côté : la règle s’applique à l’entrée dans son ensemble, et aucune classe ne peut être écartée pour la rendre valide<name> is NOT published: … <attribute> is required by the DIT content rule <rule> and is missing (RFC 4512 4.1.6)

Ce que les règles de structure font à l’arbre

Avec au moins une règle de structure DIT active, authnd parcourt l’arbre qu’il va publier, au démarrage et dans check :

  • le suffixe (base_dn), auquel il donne la classe que nomme son RDN : dc un domain, o une organization, ou une organizationalUnit, c uncountry, l une locality. Un suffixe nommé par tout autre attribut est refusé ;
  • ou=people et ou=groups, comme organizationalUnit ;
  • l’attribut de RDN par lequel authnd nomme ses personnes (uid) et ses groupes(cn).

Un conteneur qu’aucune règle ne place, un suffixe d’un genre pour lequel aucune règle n’a de forme de nom, une forme de nom qui refuse uid ou cn, ou un conteneur sous lequel rien de ce qu’authnd publie ne pourrait être placé,empêche le démarrage, et check : tous les refus à la fois, nommant le DN, la règle ou la forme de nom et la clause, sans jamais répéter un secret. Une personne ou un groupe dont la classe structurelle dépend de ses données (un sn,un gidNumber) et qui n’a aucune règle sous son conteneur est laissé de côté et signalé à la place, comme team plus haut : le serveur démarre. Sans règle de structure active, rien ne change.

Un schéma dont la seule règle de structure pour les personnes, peopleByCN,place une forme de nom qui veut cn (accountByCN : OC account MUST cn) :

$ authnd check cases/bad.hcl
authnd: DIT structure rules: authnd names its people uid=<name>,ou=people,dc=example,dc=org, and an account named so is refused: the RDN (uid) is allowed by the name form of no DIT structure rule that places account under an entry governed by the rule 2: accountByCN needs cn

authnd nomme ses personnes uid=<name> : les règles doivent l’autoriser. Et un schéma dont la règle pour organizationalUnit n’a pas de SUP, si bien qu’uneorganizationalUnit ne peut être qu’à la racine, laisse ou=people etou=groups sans place, et dit les deux à la fois :

$ authnd check cases/root.hcl

Les deux sortent avec le code 1. Les fichiers derrière eux (cases/bad.schema etcases/root.schema) contiennent les mêmes cinq formes de noms et seulement les règles de structure qui font la démonstration.

Où authnd et slapd diffèrent

go-authn/ldap lit les fichiers d’OpenLDAP, et certaines des règles sont celles d’OpenLDAP. Voici les différences, dites plutôt que découvertes :

  • slapd n’implémente que les règles de contenu. Il n’a pas de directive pour les formes de noms ni pour les règles de structure. Format écrit des mots-clés nameform et ditstructurerule, qui sont ceux de cette bibliothèque, et que slapd refuse : gardez-les dans le HCL, ou dans un fichier que seul authnd lit. ditcontentrule est celui de slapd.
  • Une règle OBSOLETE est inactive (RFC 4512 §4.1.6), de même que sa forme de nom ou sa règle de structure. slapd refuse l’entrée à la place.
  • Sans règle de contenu, les classes auxiliaires sont autorisées. C’est le comportement de slapd (son drapeau SLAP_DISALLOW_AUX_WO_CR n’est posé par aucun mot-clé disallow), et celui d’authnd. La RFC 4512 §2.4.3 dit l’inverse ; la bibliothèque l’offre sous la formeValidateOptions{StrictAuxiliary: true}, et authnd ne la pose pas.
  • libldap ne sait pas lire le SUP d’une règle de structure. Une règle de structure avec un SUP est lue ici et pas par libldap, si bien que le refus d’un tel fichier par libldap n’est pas un verdict sur le fichier.
  • Un fichier qui redéfinit une règle est refusé, même mot pour mot, comme toute autre définition (plus haut).

Ce que cela coûte

Mesuré le 2026-10-30 avec BenchmarkPublish10k (go-authn/authnd,rules_bench_test.go, -cpu 1) sur authnd v0.13.3, qui embarque go-authn/ldap v0.11.3 : publier 10 000 personnes fait 97 allocations par entrée avec les règles de testdata/rules.schema et 69 sans (v0.13.2 : 128 et 85 ; v0.13.0 : 416 et 265), et une exécution occupe 42,6 Mio avec les règles et 25,7 Mio sans (v0.13.2 : 54,8 et 33,7 ; v0.13.0 : 147,5 et 88,0). Cela inclut le retrait d’une description exclue et une nouvelle validation. Les durées, environ 66 ms contre 36 ms, sont la médiane de cinq exécutions entrelacées sous une charge de 4,8 :les règles coûtent encore environ 1,8 fois plus. La seconde validation que demande le retrait de la description et la seconde lecture du DN par les règles de structure figurent parmi les plus grandes parts attribuées de l’écart.

Mise à niveau

Rien ne change pour un schéma sans règles : la v0.12.4 refusait les trois sortes, si bien qu’une configuration qui a démarré dessus n’en contient aucune.Il y a une exception. Une chaîne schema { } qui n’est pas de l’UTF-8 valide (un encodage trop long que HCL laisse passer) démarrait sur la v0.12.4 et est refusée maintenant, parce qu’elle ne pourrait pas être publiée telle qu’elle a été écrite.

SUPANN, comme exemple réel

SUPANN est l’ensemble d’attributs de l’enseignement supérieur et de la recherche français(supannPerson, supannEtablissement, supannEntite…), avec eduPerson à côté. RENATER publie le schéma technique, avec les autres, sur sa page de documentation :

https://services.renater.fr/documentation/supann/supann2021/recommandations/tables_references/schemas_techniques_supann

Téléchargez le fichier depuis là. Il n’est pas reproduit sur ce site : il n’indique aucune licence, cette page ne le copie donc pas, et une copie ici deviendrait périmée quand RENATER le révise. Ensuite :

sudo install -o root -g authnd -m 0640 supann.schema eduperson.ldif /etc/authnd/
schema_files = ["/etc/authnd/supann.schema", "/etc/authnd/eduperson.ldif"]

users "sql" {
  # ...
  users_attributes     = "select login, sn, etab as \"supannEtablissement\" from staff"
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

Lancez authnd check et lisez d’abord les lignes schema: : un fichier que slapd charge se charge ici, et un fichier qui redéfinit une définition standard est refusé avec sa ligne. Lisez ensuite les lignes published without : une personne à qui manque un MUST de supannPerson ou d’eduPerson est publiée sans la classe, etcheck nomme le MUST. Mettez un alias entre guillemets là où sa graphie compte(PostgreSQL met en minuscules un alias sans guillemets ; voirles entrées).
