ステータス

これらのページが説明するリリース、各リリースで追加されたもの、そしてまだ実装されていないもの。

これらのページはドキュメントバージョン 0.7 で、次のものを説明しています。

プログラムリリースモジュール
authndv0.15.0github.com/go-authn/authnd
authn-bridgev0.23.6github.com/go-authn/bridge
authn-revokdv0.6.7github.com/go-authn/revocation
sshcert-authorizev0.1.9github.com/go-authn/sshcert

ライブラリのバージョンは専用ページにあります。ldap は v0.12.0 で、DIT コンテンツルール、ネームフォーム、DIT 構造ルールの読み込み、適用、公開、ビルドできないスキーマのための型付きの BuildError、HCL2 のスキーマと ldapschema コンバーターを備えています。directory は v0.17.0 で、宣言されたオブジェクトクラスを備えています。authnd v0.15.0 は ldap v0.12.0 と directory v0.17.0 を組み込んでいます。上記のいずれかのプログラムのマイナーバージョンが新しくなると、新しいドキュメントバージョンになります。そのため、/docs/0.7/ 以下のページは、読者がインストールしたものを説明し続け、以前のリリースのページは /docs/0.1/、/docs/0.2/、/docs/0.3/、/docs/0.4/、/docs/0.5/、/docs/0.6/ 以下に残ります。

authnd を v0.14.x からアップグレードする: 既定値が二つ変わります

max_connections は 4096 (以前は無制限)、operation_timeout は 30s (以前はなし) です。上流のディレクトリが落ちているときは unavailable (52) が返り、invalidCredentials (49) ではなくなります。max_connections = 0 と operation_timeout = "0" で以前の動作になります。制限と期限を参照してください。

セキュリティ: authnd は v0.11.1 ではなく v0.12.0 を使ってください

authnd は証明書を検証します (x509.Certificate.Verify。govulncheck によれば main から到達可能)。そして Go 1.27.2 の crypto/x509 は、GO-2026-6809 が挙げる侵害された中間証明書を信頼から外していませんでした。v0.11.1 のリリースバイナリは Go 1.27.2 でビルドされており、影響を受けます。 v0.12.0 は Go 1.27.3 でビルドされ、その go ディレクティブは 1.27.3 なので、go install は修正済みのツールチェーンへ自動的に切り替わります。Go 1.27.3 でのgovulncheck は脆弱性なしと報告します。そのリリースバイナリは go version -m でgo1.27.3 と報告します。アップグレードの注記を参照してください。

セキュリティ: authn-bridge v0.23.3 と authn-revokd v0.6.5 を使ってください

Go 1.27.2 では、govulncheck が両方のプログラムで GO-2026-6809 を報告します。crypto/x509 の Certificate.Verify が、既知の侵害された中間証明書を拒否していませんでした。Go 1.26.10 と 1.27.3 で修正されています。より古い Go でビルドしたリリースバイナリは影響を受けます。 v0.23.3 と v0.6.5 は Go 1.27.3 でビルドされ、go ディレクティブも 1.27.3 なので、go install は自動的に修正済みのツールチェーンに切り替わります。両方のリリースバイナリは go version -m で go1.27.3 と表示されます。sshcert は影響を受けず、新しいリリースもありません。

v0.12.0サイトスキーマ: schema_files (公開されているとおりの OpenLDAP .schema と cn=config LDIF。再定義は、slapd と同様に、同一であっても拒否される) と schema { } ブロック。ソースごとに object_classes で宣言する補助クラスは、起動時に検証され、スーパークラスとともに公開される。check はファイル、宣言、MUST が足りないために人から外されたクラス、二つのソースの意見が食い違うグループを報告する。⛔ Go 1.27.3 でビルド: v0.11.1 のバイナリ (Go 1.27.2) は GO-2026-6809 の影響を受ける
v0.12.1ビルドできないスキーマファイルまたはブロックは、go-authn/ldap v0.10.0 の BuildError が持つ位置で、列付きで拒否される (site.schema:6: は site.schema:6:1: になる)。メッセージは拒否の種類で終わり、重複は最初の定義の場所を示す
v0.12.2リリースバイナリは -s -w ではなく -ldflags="-w" でリンクされる。シンボルテーブルが残るので、govulncheck -mode binary はリンクされていないコードの脆弱性を報告せず、正確になる。約 9 % 大きくなる (darwin/arm64 で 18.8 MB から 20.5 MB)
v0.12.3go-authn/ldap v0.10.1: schema_files を線形時間で読む。⛔ v0.12.2 までは、短い継続行から成る大きなスキーマファイル (4 MiB で約 3 分) が起動を止めた。管理できないファイルによるサービス拒否
v0.12.4go-authn/ldap v0.10.2: cn=Subschema の RFC 2307 の 13 個の定義(uidNumber、gidNumber、ipHostNumber、ipNetworkNumber、ipNetmaskNumber、macAddress と、クラス ipService、ipProtocol、oncRpc、ipHost、ipNetwork、ieee802Device、bootableDevice)の DESC の値に、RFC のページ組みのインデントが含まれなくなりました。... in an administrative domain' ではなく DESC 'An integer uniquely identifying a user in an administrative domain' です
v0.13.0DIT コンテンツルール、ネームフォーム、DIT 構造ルール (go-authn/ldap v0.11.0): schema_files と schema { } ブロックは三種類を受け付け、authnd はそれらを適用する。コンテンツルールは各エントリの形を定める。AUX が挙げていない補助クラスは (それだけが許していた属性とともに) 外され、NOT の属性は破棄され、MUST を欠くエントリは公開されない。いずれもログに出て check が報告する。有効な構造ルールがあれば、木 (サフィックス、ou=people、ou=groups、uid または cn の RDN) が起動時と check で検査され、違反があれば起動を拒否し、拒否はすべて一度に示され、シークレットは決して出力されない。どのルールも配置しないエントリは外される。⛔ 有効な UTF-8 でない schema { } の文字列は拒否されるようになった。10,000 人の公開は、ルールありでエントリごとに 416 回の割り当て、なしで 265 回 (時間は負荷時に計測したので信頼できない)
v0.13.1性能のみ、go-authn/ldap v0.11.1 を組み込む。10,000 人の公開 (BenchmarkPublish10k、-cpu 1) は、ルールありでエントリごとに 364 回の割り当て、なしで 239 回 (v0.13.0 は 416 回と 265 回)、1 回の実行でルールありは 102.5 MiB (v0.13.0 は 147.5 MiB)。時間は負荷 10〜16 で計測したので信頼できない
v0.13.2性能のみ、go-authn/ldap v0.11.2 を組み込む。10 属性のエントリで Validate の割り当ては 76 回から 12 回に減った。10,000 人の公開 (BenchmarkPublish10k、-cpu 1) は、ルールありでエントリごとに 128 回の割り当て、なしで 85 回 (v0.13.1 は 364 回と 239 回)、1 回の実行でルールありは 54.8 MiB (v0.13.1 は 102.5 MiB)。時間 (負荷 8〜11): ルールありで約 158 ms から約 90 ms
v0.13.3性能のみ、go-authn/ldap v0.11.3 を組み込む。unmet が検証したばかりのエントリは、変わっていなければ validated で再び検証されない。10,000 人の公開 (BenchmarkPublish10k、-cpu 1) は、ルールありでエントリごとに 97 回の割り当て、なしで 69 回 (v0.13.2 は 128 回と 85 回で、-24 % と -19 %)。時間はルールありで約 66 ms、なしで約 36 ms (負荷 4.8)
v0.13.4カオス試験。グループは人と同じく起動時に 1 回だけ読み込まれます。SQLite で 500 人・50 人ずつ 200 グループに対する検索は 4.13 秒かかり (検索のたびにグループを再問い合わせしていた)、今は 1.2 ミリ秒です。また、検索中に失敗したグループクエリが、Success を返す応答からグループを黙って落とすことはなくなりました。起動時に読み込めないソース (実行できないグループクエリ、複数のデータベースのうち 1 つの停止) は起動と check を拒否します。約 3 MiB を超えるエントリ (10 MB の属性値が 1 つ) は公開されません。公開内容は人の集合ごとに 1 回だけ構築されます。テストで確認済み: 全バイト位置で切ったスキーマファイル、削除または破損したデータベース、悪意のある行、放置された接続、過大な BER 長、20,000 段の入れ子フィルタ
v0.14.0変更: v0.13.4 ではグループの変更に再起動が必要で、データベースから外したメンバーが、誰かが authnd を再起動するまでアクセス権を持ち続けていました。v0.14.0 で適時の失効を取り戻しました。refresh (既定 60 秒、0 で無効) が、人とグループのすべてのソースを、応答経路の外で組み立てた新しいスナップショットに読み直し、丸ごと入れ替えます。失敗した更新は最後に正常だったスナップショットを保ち、失敗が続く間に 1 回だけ、ソース名を添えてログに記録されます。max_age (既定は未設定) を設定すると、提供中のデータがそれより古くなった時点で、検索・人の bind・パスワード変更が unavailable を返します。authnd 経由で書かれたパスワードも同じ入れ替えを通ります。計測: SQLite で 500 人・50 人ずつ 200 グループの更新は 1 コアで約 2 秒、検索は 0.5 ミリ秒 (更新コストは v0.14.1 で修正)
v0.14.1性能のみ。更新のコストが、グループ数 × メンバーシップ行数に比例して増えなくなりました。directory v0.16.0 が各ソースを一括で 1 回だけ読み込みます。SQLite で 500 人・50 人ずつ 200 グループの更新は 1.87 秒から 0.155 秒に、10,000 人・2,000 グループの更新は 391 秒 (更新周期の 6.5 回分) から 1.6 秒 (60 秒周期の 2.7 %) になりました。アロケーションは 39,959,235 から 3,095,482 に、6,373,736,235 から 31,198,460 に減りました。時間は負荷 17〜67 の下で計測した目安で、アロケーション数は正確です
v0.15.0可用性とセキュリティ。go-authn/ldap v0.12.0 と go-authn/directory v0.17.0 を使用。⛔ 既定値が二つ変わります: max_connections は 4096 (以前は無制限)、operation_timeout は 30s (以前はなし)。新規で省略可能: max_connections_per_ip と startup_timeout (60s)。check は制限を表示します。上限を超えた接続には busy が送られて閉じられ、期限を過ぎた操作は、ハンドラーがブロックしていても timeLimitExceeded で答えられます。バインド中の上流の障害 (単純バインド、パスワード変更、mfa のパスワード要素) は unavailable (52) で、invalidCredentials (49) にはなりません。間違ったパスワードは今も 49 です。遅いソースに対する起動は startup_timeout の後に失敗し、段階とソースを名指しします。TLS 証明書は読み直されます (cert_file や key_file が変わったとき。5 秒後の最初のハンドシェイクと SIGHUP)。読み込めない組は提供中の証明書を保ち、一度だけログに記録されます。アロケーション数は下のライブラリにあります。実時間は未測定 (開始時の負荷は 21)

まだ実装されていないもの

  • LDAP 経由の書き込み。本人が自分のパスワードを変更する場合を除きます。authnd は自分自身の userPassword の modify と RFC 3062 のパスワード変更操作 (ldappasswd が送るもの) に応答しますが、どちらも現在のパスワードがある場合に限られ、それ以外には応答しません。add、delete、modifyDN は go-authn/ldap に存在しますが、意図的に接続していません (server.go)。ライブラリは modify を順序付きのリストとして保持し (RFC 4511 4.6)、エントリ読み取りコントロール (RFC 4527) にも応答するので、土台はあります。欠けているのは、誰が何を書いてよいかというポリシーです。
  • Kerberos 内での第二要素: FAST (RFC 6113) 内の OTP 事前認証 (RFC 6560)。これが実現するまでは、kerberos ブロックと mfa ブロックを両方設定することはできません。
  • RC4-HMAC: レルムは aes256-cts-hmac-sha1-96 だけを発行するため、NT ハッシュしか知られていない人にはチケットを発行できません。これは (RC4 は RFC 8429 で非推奨)選択であり、埋められるのを待つ欠落ではありません。
