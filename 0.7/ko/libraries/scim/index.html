scim — 신원 공급자로부터 사람과 그룹 프로비저닝하기

go-authn/scim은 SCIM 2.0 서비스 공급자(RFC 7643, RFC 7644)입니다: 직접 작성하는 Backend 위의 Users와 Groups, Entra ID와 Okta 페이로드로 테스트됨. 표준 라이브러리만 사용.

신원 공급자가 방금 누구를 생성, 변경, 삭제했는가? 신원 공급자(Entra ID, Okta,Keycloak, …)는 HTTP로 애플리케이션의 사람과 그룹을 생성, 갱신, 삭제합니다. 이 패키지가 Users와 Groups(RFC 7643, RFC 7644)를 위한 그 HTTP 엔드포인트이며, 직접 작성하는Backend 위에 있습니다. 순수 Go, CGO_ENABLED=0, 표준 라이브러리만 사용합니다.

go get github.com/go-authn/scim@v0.2.0

예제 

srv := &scim.Server{
	Backend: scim.NewMemory(),                     // or your database
	BaseURL: "https://app.example.org/scim/v2",    // for meta.location
}
mux.Handle("/scim/v2/", http.StripPrefix("/scim/v2", scim.BearerAuth(token, srv)))

Server는 id, 타임스탬프, 버전을 부여하고, 입력을 검증하고, PATCH를 적용합니다.Backend는 받은 것을 보관하고 자신만 볼 수 있는 것을 강제합니다. 이미 사용 중인userName에는 ErrConflict(409 uniqueness), 존재하지 않는 구성원에는InvalidValue(400 invalidValue), 저장된 버전이 읽은 버전이 아닐 때는ErrPrecondition. NewMemory()는 참조 구현입니다.

/Users와 /Groups(filter, startIndex, count, attributes,excludedAttributes가 있는 목록, 생성, ETag와 If-Match가 있는 id별 조회, PUT,PATCH, DELETE), /Users/.search와 /Groups/.search, 그리고 디스커버리 엔드포인트 /ServiceProviderConfig, /ResourceTypes, /Schemas를 제공합니다.필터는 RFC 7644 §3.4.2.2의 문법 전체를 다루며, PATCH는 원자적입니다. 실패한 작업은 리소스를 그대로 둡니다.

거부하는 것과 그 이유

여기의 모든 것은 외부에서 오므로 한계가 API의 일부입니다.

MaxBodyBytes(1 MiB)를 넘는 본문, MaxOperations(100)를 넘는 PATCH, 또는 리소스를 본문 한계 이상으로 키우는 PATCH413
MaxMembers(10 000)를 넘는 그룹400 invalidValue
4 KiB를 넘거나, 32보다 깊게 중첩되었거나, 알 수 없는 연산자가 있거나, 불리언에 gt를 쓴 필터400 invalidFilter
id, meta, schemas, 또는 사용자의 groups에 쓰기400 mutability
핵심 스키마가 없는 리소스, 비어 있거나 256바이트를 넘거나 제어 문자를 가진 userName, 기본 이메일 두 개400
없거나 잘못된 베어러 토큰 (BearerAuth, 상수 시간. 빈 토큰은 아무도 들이지 않음)401
센티널이 아닌 모든 Backend 오류아무것도 알려 주지 않는 본문과 함께 500. 오류는 ErrorLog로 감

지원하지 않음: 벌크 작업, 정렬, 비밀번호 변경, /Me(/ServiceProviderConfig에 그렇게 공지됨).

v0.2.0에서 바뀐 것

감사, 퍼징과 카오스, 성능 개선을 거쳐. 호출자에게 보이는 것:

  • Server.ReadTimeout(신규, 기본 30초): 도착하는 데 더 오래 걸리는 요청 본문은 400으로 잘립니다. 그 요청에 대해http.Server 자체의 ReadTimeout을 대체합니다. 음수 값이면 http.Server의 것이 그대로 쓰입니다.
  • ConditionalDeleter: Backend가 구현할 수 있는 새 선택 인터페이스(DeleteUserIf, DeleteGroupIf)이며Memory가 구현합니다. If-Match가 있는 DELETE는 버전을 확인한 뒤 두 단계로 삭제했으므로, 그 사이에 들어온 쓰기가 보이지 않은 채 삭제되었습니다.
  • 진 경합은 다시 수행됩니다. If-Match 없는 PATCH나 PUT이 다른 쓰기와의 경합에서 지면, 클라이언트가 전제 조건을 요구하지 않았는데도 412로 응답했습니다. 이제 더 새로운 버전에서 최대 32번 다시 수행됩니다.If-Match가 있으면 응답은 여전히 412입니다. If-Match 없는 동시 PATCH 24개 중 이전에는 9개가 412로 실패했고 지금은 0개입니다.
  • 아무것도 일치하지 않는 필터로 멤버(또는 임의의 요소)를 제거하면 성공합니다. 이전에는 400 noTarget이었습니다(RFC 7644 §3.5.2.2).
  • 경로 없는 PATCH는 키를 정렬된 순서로 적용합니다. 이전에는 맵 순서여서, 한 객체의 name과 name.givenName이 실행마다 다른 리소스를 만들었습니다.
  • BearerAuth는 스킴 이름을 대소문자 구분 없이 받아들입니다(bearer <token>, RFC 7235 §2.1).
  • startIndex와 count는 int의 크기와 상관없이 상한으로 잘립니다. 이전에는 32비트 대상에서는 400, 64비트에서는 잘린 페이지였습니다.
  • Filter.Equality()는 Backend에 디코딩된 문자열을 넘깁니다. 이것은 데이터입니다. 데이터베이스에 매개변수로 넘기고, 쿼리에 끼워 넣지 마십시오.

대량 작업, 정렬, 비밀번호 변경은 계속 지원되지 않습니다.

Memory에서 사용자 10,000명과 그룹 200개에 대한 목록 요청 한 번의 할당. go test -bench의 정확한 값,Apple M4 Max:

목록 요청이전이후
100개 페이지789,417회, 47.7 MB14,952회, 6.0 MB
userName eq797,979회, 47.7 MB90회, 12.6 KB
모든 사용자를 훑는 필터(name.givenName eq와 emails[...])818,847회, 48 MB361,098회, 29.7 MB

실제 시간은 측정하지 않았습니다. 부하가 65였고 규칙은 9 미만입니다. 잡음이 많은 단발 실행(훑는 필터에서 약 1.7초 대 0.06초)은 결과가 아닙니다. FuzzPatchPath, FuzzPatchThenDecode, FuzzFilter, FuzzServer를 각각 45초, 워커 16개로 실행했으며 130만에서 240만 회 실행에서 실패를 찾지 못했습니다.

무엇과 대조해 검사하는가

신원 공급자가 실제로 보내는 것을 그들의 페이로드로 테스트합니다. Entra ID의"Replace", 문자열 불리언("active": "False"), 값 목록에 의한 구성원 제거, 이메일을 생성하는 필터링된 추가. Okta의 id를 반복하는 경로 없는 replace. 필터, PATCH, 핸들러 전체를 퍼징하며(FuzzFilter, FuzzPatch, FuzzServer), 커버리지 레인의 하한은 92%입니다.
