站点模式

站点模式，以及来源声明的类

提供 SUPANN、eduPerson 或站点自己的属性：schema_files 和 schema 块添加定义，object_classes 声明某个来源的人员和组所带的辅助类，check 则说明哪些被丢弃。从 v0.13.0 起，DIT 内容规则、名称形式和 DIT 结构规则会被强制执行。

除非条目的某个类允许，否则 SUPANN 或 eduPerson 属性会被丢弃。 authnd 只发布它所提供的模式允许的内容（参见条目），而标准模式对 supannEtablissement 或eduPersonAffiliation 一无所知。自 v0.12.0 起，站点按以下顺序说明三件事：

  1. 要添加哪些定义：schema_files，即其 slapd 已经加载的文件，以及用于纯本地内容的 schema { } 块；
  2. 其人员和组带哪些辅助类：object_classes；
  3. 仅此而已。类是声明出来的，从不推断：数据库中出现某个属性，不会改变条目发布为什么。

本页的示例只是示例

下面的 example.schema 是为本页编写的。它的 OID 位于1.3.6.1.4.1.99999 之下，这是一个没有分配给任何人的弧：请使用你自己的，切勿照抄这些。关于 SUPANN，请参见本页末尾。

一个示例：模式、数据库、配置

一份 OpenLDAP .schema 形式的模式：一个来源可以声明的类（exampleStaff，AUXILIARY，带一个 MUST），和一个不能声明的类（exampleUnit，STRUCTURAL）。

objectidentifier exampleRoot  1.3.6.1.4.1.99999
objectidentifier exampleAttr  exampleRoot:1
objectidentifier exampleClass exampleRoot:2

attributetype ( exampleAttr:1 NAME 'exampleBadge'
	DESC 'the number on a badge'
	EQUALITY caseIgnoreMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

attributetype ( exampleAttr:2 NAME 'exampleEmployeeId'
	DESC 'a staff number'
	EQUALITY caseExactMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

# AUXILIARY: it can be declared. exampleStaff has a MUST.
objectclass ( exampleClass:1 NAME 'exampleStaff' SUP top AUXILIARY
	DESC 'somebody employed: has a staff number'
	MUST exampleEmployeeId
	MAY exampleBadge )

# STRUCTURAL: it cannot be declared (an entry has one structural chain).
objectclass ( exampleClass:2 NAME 'exampleUnit' SUP top STRUCTURAL
	MUST cn )

一个包含三个人的 SQLite 数据库，带有 sn、工牌和员工编号（sqlite3 var/people.db < people.sql）：

create table staff (login text primary key, secret text);
create table person_attrs (login text primary key, sn text, badge text, empid text, locker text);
insert into staff values ('ann', 'ann-password'), ('ben', 'ben-password'), ('cat', 'cat-password');
insert into person_attrs values ('ann', 'Archer', 'B-0001', 'E-1001', 'L-12'), ('ben', 'Brook', 'B-0002', null, null), ('cat', 'Cole', null, 'E-1003', null);

以及配置：

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

# Files first, then the blocks: a definition may use anything before it.
schema_files = ["etc/authnd/example.schema"]

schema {
  attribute_type "exampleLocker" {
    oid    = "1.3.6.1.4.1.99999.1.3"
    syntax = "1.3.6.1.4.1.1466.115.121.1.15"
  }
  object_class "exampleLockerHolder" {
    oid  = "1.3.6.1.4.1.99999.2.3"
    kind = "auxiliary"
    may  = ["exampleLocker"]
  }
}

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret from staff"
  users_attributes = "select login, sn, badge as exampleBadge, empid as exampleEmployeeId, locker as exampleLocker from person_attrs"
  object_classes   = ["exampleStaff", "exampleLockerHolder"]   # declared, never inferred
}

schema_files

schema_files 是 OpenLDAP .schema 文件或 cn=config LDIF 文件的列表。它们按发布时的原样，依次加载到标准模式之上（如果有samba 块，还有 Samba 的三个定义），由 go-authn/ldap 的 slapd 兼容读取器处理：支持任意的项顺序、slapd 和 RFC 2849 的续行、base64、{N} 长度前缀，以及 objectidentifier 宏——一个文件可以定义，下一个文件可以使用，如同跨越 slapd 的 include。事先不做任何转换，所以站点的 slapd 加载的文件，就是 authnd 加载的文件。这些定义由cn=Subschema 提供。

  • 相对路径相对于工作目录，与配置中的其他每个路径一样。在服务中请使用绝对路径：systemd 单元的工作目录是 /。

  • 每个文件必须是不超过 4 MiB 的普通文件，并且只在启动时读取一次。

  • 这些文件决定每个条目可以包含什么。它们不是机密，但请与配置的其余部分放在一起：root:authnd，权限 0640，位于只有 root 可写的目录中（安装）。

  • 无法构建的文件会使启动以及 check 被拒绝，并给出文件、行和定义起始的列，信息末尾是拒绝的类型：未知的父类、属性、匹配规则或语法（unknown reference），由辅助类派生的结构类（kind violation），重复定义的 OID 或名称（duplicate OID、duplicate name）。自 v0.12.1 起，位置和类型来自 go-authn/ldap 的类型化*schema.BuildError，而不是通过解析它的错误信息。从文件读取的定义从第 1 列开始，即使其文本折叠成多行也一样。重复定义会指出它的第一个定义在哪里，重新定义则会指出原件在哪个标准文件，或更早文件的哪一行。两个示例：

    cases/unknown.schema 有一个在任何地方都未定义的 MAY：

    # exampleB has a MAY that is defined nowhere.
objectclass ( 1.3.6.1.4.1.99999.2.9 NAME 'exampleB' SUP top AUXILIARY
	MAY noSuchAttribute )
    $ authnd check cases/unknown.hcl
authnd: schema_files: cases/unknown.schema:2:1: the object class exampleB has MAY noSuchAttribute, which is not a defined attribute type (unknown reference)

    cases/twice.schema 给两个属性类型赋予同一个 OID：

    attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleA'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )

attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleB'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )
    $ authnd check cases/twice.hcl
authnd: schema_files: cases/twice.schema:4:1: the attribute type 1.3.6.1.4.1.99999.1.9 is defined twice (first defined at cases/twice.schema:1:1) (duplicate OID)

重新定义会被拒绝，即使完全相同

文件不得定义已经存在的内容：标准模式的定义、Samba 的定义，或更早的文件的定义。即使逐字相同也会被拒绝，这正是 slapd 自己的规则：模式文件的定义要经过parse_at 和 parse_oc，对于已被索引的 OID 或名称，slapd 会回答Duplicate attributeType（OID 和名称都相同）或 Inconsistent duplicate attributeType（servers/slapd/at.c、oc.c）。只有 slapd 自己硬编码的模式才允许前一种情形。slapd 拒绝的文件，authnd 也拒绝。

另一种解读则必须挑出一个胜者，而这会悄悄改变每个客户端被告知的某个标准属性的内容；拒绝则会指出具体的行。拒绝信息会说明文本是否相同。下面是一个用自己的定义重新定义 cn（2.5.4.3）的文件：

$ authnd check cases/dup.hcl
authnd: schema_files: cases/cn-copy.schema:1:1: the attribute type cn (2.5.4.3) is already defined by the standard schema (rfc4519.schema:42:1), and this is a different definition: a schema file adds definitions and never replaces one -- slapd refuses this too ("Duplicate attributeType", servers/slapd/at.c and oc.c). Remove it from this file

schema { } 块

对于纯本地的定义，schema 块以 HCL2 保存它们，采用 hclschema 的形态：attribute_type、object_class、object_identifier、matching_rule 和ldap_syntax。它在文件之后读取，因此可以使用文件中的定义，并且可以有多个。

值必须是字面量：不能有变量、函数，也不能有 ${...} 或%{...}。该块由读取 .hcl 模式文件的同一个解码器解码，使用相同的界限，每个错误都会指明配置自己的行和列。不是 HCL 原生语法的块会被拒绝。

object_classes

模式中的定义允许某个属性；它并不会把类加到任何人身上。来源声明 其人员和组发布时所带的辅助类：

位置键它声明什么
users 块，任意种类object_classes该块给出的每个人员的类
users 块，任意种类group_object_classes每个组的类
user 块object_classes该人员的类
group 块object_classes该组的类
users "sql" {
  # ...
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

user  "alice" { object_classes = ["siteMember"] }
group "staff" { object_classes = ["supannGroupe"] }

这些键属于 go-authn/directory，自 v0.15.0 起（库）。名称比较时忽略大小写，并且只保留一次，按书写顺序。

authnd 如何处理已声明的类：

  • 它连同其父类一起发布，排在 authnd 派生的类之后（RFC 4512 §3.3：所指名的类的全部父类都被隐式加入）。该类允许的属性会被保留，而不是丢弃。
  • 它从不推断。 来源不声明任何类的人员，无论数据库中保存了什么，都会继续失去其所有类都不允许的属性。
  • 缺少已声明类的某个 MUST 的人员，发布时不带该类。 其属性像任何没有类允许的属性一样被丢弃，两者都会被报告。这就是authnd 处处遵循的规则：人员仍然发布，问题被说明，不会悄悄改变任何东西。扣留该人员，会使其因为缺少一个属性而从每次搜索中消失；而发布不带 MUST 的类，则会提供一个不通过所提供模式检查的条目。
  • 两个来源可以为同一个组声明不同的类。 第一个为某个组声明类的来源整体决定，后面的列表会被忽略：既不合并也不报错。check 会说明这一点。

什么会被拒绝，以及原因

已声明的类会在启动时由 check 对照所提供的模式进行检查。它必须是：

  • 已定义的，由标准模式、文件或块定义；
  • AUXILIARY（RFC 4512 §4.1.1）。一个条目恰好有一条结构链（§2.4.2），由 authnd 根据此人所具有的内容选择；声明不能再添加第二条；
  • 不是 authnd 自行派生的类：account、inetOrgPerson 及其父类、posixAccount、posixGroup、ldapPublicKey、uidObject、sambaSamAccount、groupOfNames 和 organizationalRole，无论用其哪个名称。这些类取决于人员或组所具有的内容，而声明不能推翻 check。

否则启动会被拒绝，并指明块、其位置和类。exampleUnit 是 STRUCTURAL：

$ authnd check cases/structural.hcl
authnd: cases/structural.hcl:10:20: users "sql" object_classes: exampleUnit is STRUCTURAL, and an entry has exactly one structural chain (RFC 4512 §2.4.2), which authnd chooses: only an AUXILIARY class (§4.1.1) can be declared

go-authn/directory 会在此之前检查拼写：类是描述符，绝不是 OID、空格、引号或括号。

同样被拒绝的，出于同样保持模式诚实的理由：

被拒绝的原因
重新定义某个定义的文件，即使逐字相同slapd 的规则：见上文
不是普通文件，或超过 4 MiB 的文件FIFO 会阻塞启动，/dev/zero 永远不会结束
含有变量、函数或 ${...} 的 schema 块只允许字面值，与 .hcl 模式文件相同
object_classes 中未定义的类一个无法检验的承诺
STRUCTURAL 类，或 authnd 派生的类上面的列表

check 会输出什么

四类行，附加在通常的那些之上；启动日志带有同样的行：

  • schema: <file> adds … 和 schema: the schema block at <file>:<line>:<column> adds …：每个文件和每个块添加了什么，按对象标识符宏、属性类型和对象类计数；
  • <file>:<line>:<column>: users "sql" declares … for its people（user 或 group 块则说 user "ann" declares … for this person 和group "staff" declares … for this group）：每个来源声明了什么；
  • <name> is published without <class>, which its source declares: …，指明此人缺少的 MUST；
  • group staff: the configuration file declares supannGroupe and a postgres database declares eduMember; the first is published and the second is ignored (the first source that declares classes for a group decides)：两个来源对某个组存在分歧，否则这会悄无声息。

因缺少类而被丢弃的属性，就是条目已经描述过的is published without <attribute>: no class of the entry allows it; <classes> would 这些行：有了声明之后，它们指明的是你尚未声明的类。

DIT 内容规则、名称形式和 DIT 结构规则

从 v0.13.0 起，schema_files 和 schema { } 块还接受 RFC 4512 §4.1.6 和 §4.1.7为类和属性所增加的三类定义，并且 authnd 强制执行它们（go-authn/ldap v0.11.0读取、构建并检查它们；库页面 说明了方式）：

定义RFC 4512它说明什么authnd 如何处理
DIT 内容规则§4.1.6针对一个结构类：可以添加哪些辅助类（AUX），哪些属性是必需的（MUST）、允许的（MAY）或被排除的（NOT）为每个条目塑形（数据）
名称形式§4.1.7.2某个结构类的条目由哪些属性命名（RDN）约束树（配置）
DIT 结构规则§4.1.7.1名称形式可以放在哪里：在由其 SUP 所指名的规则所管辖的条目之下约束树（配置）

它们只有在存在时才会在 cn=Subschema 发布（dITContentRules、nameForms、dITStructureRules）。没有时，此页面的内容都不适用，与 v0.12.4 相比也没有任何变化。

同一个示例弧

下面的 rules.schema 与上面的 example.schema 一样，是为此页面编写的，位于 1.3.6.1.4.1.99999 之下。请使用你自己的弧。内容规则的 OID 与inetOrgPerson 的 OID 按定义是相同的：内容规则以它所针对的结构类命名。

每类各一条的模式，及其 HCL

采用 OpenLDAP 的 .schema 形式。ditcontentrule 是 slapd.conf(5) 的指令；nameform 和 ditstructurerule 是 go-authn/ldap 的，因为 slapd 没有它们（见下文）。authnd 还会检查它所发布的树（后缀、ou=people、ou=groups，以及其下的账户、人员和组），因此该文件包含五个名称形式和五条结构规则，而不是每类各一个：

# Rules for the tree authnd publishes. 1.3.6.1.4.1.99999 is an example arc:
# nobody is assigned it, use your own.

# A content rule belongs to a structural class and takes that class's OID.
# inetOrgPerson (2.16.840.1.113730.3.2.2): posixAccount and uidObject may be
# added, ldapPublicKey may not; telephoneNumber is required; description is
# precluded.
ditcontentrule ( 2.16.840.1.113730.3.2.2 NAME 'examplePersonRule'
	AUX ( posixAccount $ uidObject )
	MUST telephoneNumber
	NOT description )

# A name form says which attribute names an entry of a structural class.
nameform ( 1.3.6.1.4.1.99999.9.1 NAME 'exampleDomainForm' OC domain MUST dc )
nameform ( 1.3.6.1.4.1.99999.9.2 NAME 'exampleUnitForm' OC organizationalUnit MUST ou )
nameform ( 1.3.6.1.4.1.99999.9.3 NAME 'exampleAccountForm' OC account MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.4 NAME 'examplePersonForm' OC inetOrgPerson MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.5 NAME 'examplePosixGroupForm' OC posixGroup MUST cn )

# A structure rule gives a name form a place: the rule ID is a number, SUP
# names the rule of the parent entry.
ditstructurerule ( 1 NAME 'exampleSuffix' FORM exampleDomainForm )
ditstructurerule ( 2 NAME 'exampleUnit' FORM exampleUnitForm SUP 1 )
ditstructurerule ( 3 NAME 'exampleAccounts' FORM exampleAccountForm SUP 2 )
ditstructurerule ( 4 NAME 'examplePersons' FORM examplePersonForm SUP 2 )
ditstructurerule ( 5 NAME 'examplePosixGroups' FORM examplePosixGroupForm SUP 2 )

同样的定义用 HCL 写出，即 ldapschema v0.11.0 所写的形式（ldapschema to-hcl rules.schema）。每个块是一个定义，以其第一个 NAME 作标签；结构规则有 id、它所放置的 form，以及它位于其下的 sup 规则：

}

  must = ["uid"]

  oid  = "1.3.6.1.4.1.99999.9.5"
  oc   = "posixGroup"

  id   = 1

规则适用于条目的结构类，它做了什么，会在启动时以及由 check 逐个条目说明：

规则说条目表述为
AUX 没有列出某个辅助类，无论是已声明的还是 authnd 派生的（posixAccount、ldapPublicKey、sambaSamAccount、uidObject）该类被去掉，连同只有它才允许的属性（以及 authnd 为它添加的 sshPublicKey、sambaSID 和 sambaNTPassword）；其超类被去掉的已声明类随之去掉<name> is published without <class>: the DIT content rule <rule> does not allow it (not in its AUX)
NOT 指名某个属性该属性被丢弃，无论由谁提供<name> is published without <attribute>: the DIT content rule <rule> precludes it (NOT)
MUST 指名条目所缺少的属性该条目被排除在外：规则适用于整个条目，没有哪个类可以去掉而使它有效<name> is NOT published: … <attribute> is required by the DIT content rule <rule> and is missing (RFC 4512 4.1.6)

结构规则对树做了什么

只要有至少一条有效的 DIT 结构规则，authnd 就会在启动时和 check 中遍历它将要发布的树：

  • 后缀（base_dn），按其 RDN 所指名的类处理：dc 对应domain，o 对应 organization，ou 对应 organizationalUnit，c 对应country，l 对应 locality。以任何其他属性命名的后缀都会被拒绝；
  • ou=people 和 ou=groups，作为 organizationalUnit；
  • authnd 用来命名人员的 RDN 属性（uid）和命名组的 RDN 属性（cn）。

没有规则放置的容器、没有任何规则有名称形式与之对应的那种后缀、拒绝 uid 或 cn 的名称形式，或者其下无法放置 authnd 所发布的任何内容的容器，都会拒绝启动，也使 check 失败：每一项拒绝一并给出，指明 DN、规则或名称形式以及子句，并且绝不回显机密。结构类取决于其数据（sn、gidNumber）且其容器之下没有规则的人员或组，则会被排除在外并加以说明，如上面的 team：服务器照常启动。没有有效的结构规则时，一切不变。

一个模式，其人员唯一的结构规则 peopleByCN 放置了一个需要 cn 的名称形式（accountByCN：OC account MUST cn）：

$ authnd check cases/bad.hcl
authnd: DIT structure rules: authnd names its people uid=<name>,ou=people,dc=example,dc=org, and an account named so is refused: the RDN (uid) is allowed by the name form of no DIT structure rule that places account under an entry governed by the rule 2: accountByCN needs cn

authnd 以 uid=<name> 命名其人员：规则必须允许这一点。再看一个模式，其 organizationalUnit 的规则没有 SUP，因此organizationalUnit 只能位于根部，于是 ou=people 和ou=groups 都没有位置，并且两者一并给出：

$ authnd check cases/root.hcl
authnd: DIT structure rules: ou=people,dc=example,dc=org, where authnd publishes its people, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)
DIT structure rules: ou=groups,dc=example,dc=org, where authnd publishes its groups, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)

两者都以状态 1 退出。它们背后的文件（cases/bad.schema 和cases/root.schema）包含相同的五个名称形式，以及只用于说明问题的结构规则。

authnd 与 slapd 的不同之处

go-authn/ldap 读取 OpenLDAP 的文件，其中有些规则是 OpenLDAP 的。这些是不同之处，是明确说明的，而不是事后发现的：

  • slapd 只实现内容规则。 它没有用于名称形式或结构规则的指令。Format 写出 nameform 和 ditstructurerule 关键字，它们是本库的，slapd 会拒绝它们：请把这些保留在HCL 中，或只由 authnd 读取的文件中。ditcontentrule 是 slapd 的。
  • OBSOLETE 规则无效（RFC 4512 §4.1.6），其名称形式或结构规则也是如此。slapd 反而会拒绝该条目。
  • 没有内容规则时，允许辅助类。 这是 slapd 的行为（它的 SLAP_DISALLOW_AUX_WO_CR 标志不会被任何 disallow 关键字设置），也是 authnd 的行为。RFC 4512 §2.4.3 的说法相反；本库把它提供为 ValidateOptions{StrictAuxiliary: true}，而 authnd 并未设置它。
  • libldap 无法读取结构规则的 SUP。 带 SUP 的结构规则在这里可以读取，libldap 则不行，因此 libldap 拒绝这样的文件并不是对该文件的裁决。
  • 重新定义某条规则的文件会被拒绝，即使逐字相同，与其他所有定义一样（见上文）。

它的代价

于 2026-10-30 在内嵌 go-authn/ldap v0.11.3 的 authnd v0.13.3 上，用 BenchmarkPublish10k（go-authn/authnd，rules_bench_test.go，-cpu 1）测得：发布 10,000 个人员，使用 testdata/rules.schema 的规则时每个条目 97 次分配，不使用时为 69 次（v0.13.2：128 和 85 次；v0.13.0：416 和 265 次），一次运行使用规则时占用 42.6 MiB，不使用时占用 25.7 MiB（v0.13.2：54.8 和 33.7；v0.13.0：147.5 和 88.0）。这包括丢弃被排除的描述并再次验证。耗时约为 66 ms 对 36 ms，是在负载 4.8 下交替运行五次的中位数：使用规则仍然约多花 1.8 倍。丢弃描述所需的第二次验证，以及结构规则对 DN 的第二次读取，是已查明的差异中较大的部分。

升级

没有规则的模式不会有任何变化：v0.12.4 拒绝这三类定义，因此在它上面启动过的配置不含任何规则。有一个例外。不是有效 UTF-8 的schema { } 字符串（HCL 放行的一种过长编码）曾在 v0.12.4 上启动，现在会被拒绝，因为它无法按所写的内容发布。

SUPANN，作为真实的示例

SUPANN 是法国高等教育与研究领域的属性集（supannPerson、supannEtablissement、supannEntite……），旁边还有 eduPerson。RENATER 在其文档页面上与其他模式一起发布了技术模式：

https://services.renater.fr/documentation/supann/supann2021/recommandations/tables_references/schemas_techniques_supann

请从那里下载文件。 本站不转载它：它没有声明许可证，所以本页不复制它，而且 RENATER 修订之后，这里的副本会过时。然后：

sudo install -o root -g authnd -m 0640 supann.schema eduperson.ldif /etc/authnd/
schema_files = ["/etc/authnd/supann.schema", "/etc/authnd/eduperson.ldif"]

users "sql" {
  # ...
  users_attributes     = "select login, sn, etab as \"supannEtablissement\" from staff"
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

运行 authnd check，先读 schema: 这些行：slapd能加载的文件，在这里也能加载，而重新定义标准定义的文件会被拒绝，并给出其所在行。然后读 published without 这些行：缺少supannPerson 或 eduPerson 的某个 MUST 的人员，发布时不带该类，check 会指明该 MUST。当别名的拼写很重要时，请给它加引号（PostgreSQL 会把不带引号的别名转为小写；参见条目）。
