状态

这些页面描述哪些版本、每个版本新增了什么，以及哪些功能尚未实现。

这些页面是文档版本 0.6，描述的内容如下：

程序版本模块
authndv0.14.0github.com/go-authn/authnd
authn-bridgev0.23.4github.com/go-authn/bridge
authn-revokdv0.6.6github.com/go-authn/revocation
sshcert-authorizev0.1.9github.com/go-authn/sshcert

各个库的版本见其自己的页面；ldap 为 v0.11.3，可读取、强制执行并发布 DIT 内容规则、名称形式和 DIT 结构规则，带有针对无法构建的模式的类型化 BuildError、HCL2 模式和 ldapschema 转换器，directory 为 v0.15.0，带有已声明的对象类。authnd v0.14.0 内嵌 ldap v0.11.3 和 directory v0.15.0。上述任何程序的新次版本号都对应一个新的文档版本，因此读者在 /docs/0.6/ 下找到的页面始终描述其所安装的版本；之前各版本的页面保留在 /docs/0.1/、/docs/0.2/、/docs/0.3/、/docs/0.4/ 和 /docs/0.5/ 之下。

安全：请使用 authnd v0.12.0，而不是 v0.11.1

authnd 要验证证书（x509.Certificate.Verify，据 govulncheck 可从 main 到达），而 Go 1.27.2 的 crypto/x509 不会不信任GO-2026-6809 所指明的已被攻破的中间证书。v0.11.1 的发布二进制文件由 Go 1.27.2 构建，受此影响。 v0.12.0 由 Go 1.27.3构建，其 go 指令为 1.27.3，因此 go install 会自动切换到已修复的工具链；在 1.27.3 下运行 govulncheck 不报告任何漏洞。它的发布二进制文件在 go version -m 中报告 go1.27.3。参见升级说明。

安全：请使用 authn-bridge v0.23.3 和 authn-revokd v0.6.5

在 Go 1.27.2 下，govulncheck 在这两个程序中都报告了 GO-2026-6809：crypto/x509 的 Certificate.Verify 未拒绝已知被攻破的中间证书。该问题已在 Go 1.26.10 和 1.27.3 中修复。用较旧版本的 Go 构建的发布二进制文件受到影响。 v0.23.3 和 v0.6.5 使用 Go 1.27.3 构建，其 go 指令为 1.27.3，因此 go install 会自行切换到已修复的工具链；它们的发布二进制文件在 go version -m 中显示 go1.27.3。sshcert 不受影响，也没有新版本。

每个版本新增了什么

每一行都是发布该版本所针对的变更。仅更新依赖项的版本不列出，但本文档版本所描述的除外。

authnd

v0.1.0一个面向存放在别处的人员的 LDAP 服务器：文件、SQL 数据库、另一个目录
v0.2.0第二因素，通过只有一个字段的协议实现
v0.5.0密码变更只涉及恰好一个身份；重新加载不存在竞态；KDC 可以看到变更
v0.6.0oidc、directory、ldap、totp 和 mfa 的安全修复
v0.7.0更改密码必须提供旧密码；机密以定长摘要进行比较
v0.8.2代码只有在密码正确时才算数；reader 以其配置的 DN 作为键
v0.9.0使用 Go 1.27.1 构建和测试，固定版本而非 stable
v0.9.2每个标签都发布二进制文件、SHA256SUMS 和构建溯源信息
v0.9.3二进制文件在检出目录之外构建；每个都必须准确报告标签
v0.9.4SIGHUP 不再终止 authnd：它会被记录，但不会重新加载任何内容
v0.9.5发布时检查每一个二进制文件的构建信息，而不是只检查一个
v0.9.6check 说明每个人为何无法获得票据
v0.10.0check 像服务器一样打开证书和 keytab；它指出谁无法用密码绑定，以及令牌仍然放行谁；监听行在域打开之后输出
v0.10.1go-authn/kdc v0.4.2：till 为 19700101000000Z 时获得最长的票据，而不是一张在 1970 年就已过期的票据
v0.10.2go-authn/directory v0.12.0：空组发布为不带 memberUid 的 posixGroup
v0.11.0标准模式条目，每个条目都受 cn=Subschema 所提供的模式约束；attributes、users_attributes 和 groups_attributes；(uidNumber>=1000) 按整数比较。⛔ publish_nt_hash 需要一个 samba 块，并且按 posixAccount 或 posixGroup 过滤的使用方看到的条目会变少
v0.11.1启动行只列出有人从中获得服务的来源：没有 user 块时，不再列出配置文件
v0.12.0站点模式：schema_files（OpenLDAP .schema 和 cn=config LDIF，按发布时的原样；重新定义会被拒绝，即使完全相同，如同 slapd 那样）和 schema { } 块；用 object_classes 按来源声明辅助类，在启动时验证，并连同其父类一起发布；check 报告这些文件、这些声明、因缺少 MUST 而未加到某个人员上的类，以及两个来源存在分歧的组。⛔ 由 Go 1.27.3 构建：v0.11.1 的二进制文件（Go 1.27.2）受 GO-2026-6809 影响
v0.12.1无法构建的模式文件或块，会在 go-authn/ldap v0.10.0 的 BuildError 所携带的位置被拒绝，并带有列（site.schema:6: 变为 site.schema:6:1:）；信息以拒绝的类型结尾，重复定义会指出它的第一个定义在哪里
v0.12.2发布的二进制文件改用 -ldflags="-w" 链接，不再用 -s -w：符号表得以保留，因此 govulncheck -mode binary 是精确的，不会报告未链接代码中的漏洞；约大 9 %（darwin/arm64 上从 18.8 MB 到 20.5 MB）
v0.12.3go-authn/ldap v0.10.1：schema_files 以线性时间读取。⛔ 直到 v0.12.2，由短续行组成的大型模式文件（4 MiB：约三分钟）会使启动停滞：由一个不受你控制的文件造成的拒绝服务
v0.12.4go-authn/ldap v0.10.2:cn=Subschema 中 13 个 RFC 2307 定义(uidNumber、gidNumber、ipHostNumber、ipNetworkNumber、ipNetmaskNumber、macAddress,以及类 ipService、ipProtocol、oncRpc、ipHost、ipNetwork、ieee802Device、bootableDevice)的 DESC 值不再带有 RFC 页面排版的缩进:是 DESC 'An integer uniquely identifying a user in an administrative domain',而不是 ... in an administrative domain'
v0.13.0DIT 内容规则、名称形式和 DIT 结构规则（go-authn/ldap v0.11.0）：schema_files 和 schema { } 块接受这三类定义，authnd 会强制执行它们。内容规则为每个条目塑形：其 AUX 未列出的辅助类被去掉（连同只有它才允许的属性），NOT 属性被丢弃，缺少 MUST 的条目被排除在外；每一项都会记入日志并由 check 报告。只要有一条有效的结构规则，树（后缀、ou=people、ou=groups、uid 或 cn RDN）就会在启动时和由 check 检查，违规会拒绝启动，所有拒绝一并给出，且绝不回显机密；没有规则可放置的条目被排除在外。⛔ 不是有效 UTF-8 的 schema { } 字符串现在会被拒绝。发布 10,000 个人员时，有规则的每个条目 416 次分配，无规则则为 265 次（耗时是在负载下测得的，不可靠）
v0.13.1仅优化性能，内嵌 go-authn/ldap v0.11.1：发布 10,000 个人员（BenchmarkPublish10k，-cpu 1）时，有规则的每个条目 364 次分配，无规则为 239 次（v0.13.0 为 416 和 265 次），一次运行使用规则时占用 102.5 MiB（v0.13.0 为 147.5 MiB）。耗时是在负载 10 到 16 时测得的，不可靠
v0.13.2仅优化性能，内嵌 go-authn/ldap v0.11.2：对含十个属性的条目，Validate 的分配从 76 次降为 12 次；发布 10,000 个人员（BenchmarkPublish10k，-cpu 1）时，有规则的每个条目 128 次分配，无规则为 85 次（v0.13.1 为 364 和 239 次），一次运行使用规则时占用 54.8 MiB（v0.13.1 为 102.5 MiB）。耗时（负载 8 到 11）：有规则时约从 158 ms 降到 90 ms
v0.13.3仅优化性能，内嵌 go-authn/ldap v0.11.3：unmet 刚验证过的条目，如果没有变化，validated 不再重新验证；发布 10,000 个人员（BenchmarkPublish10k，-cpu 1）时，有规则的每个条目 97 次分配，无规则为 69 次（v0.13.2 为 128 和 85 次，分别降低 24 % 和 19 %）。耗时：有规则时约 66 ms，无规则时约 36 ms（负载 4.8）
v0.13.4一次混沌测试。组与人员一样，在启动时只读取一次：在 SQLite 上，对 500 人、200 个各 50 人的组做一次搜索原本要 4.13 秒（每次搜索都重新查询组），现在只要 1.2 毫秒；搜索期间失败的组查询也不再把组从仍返回 Success 的应答中悄悄丢掉。启动时无法读取的来源（无法执行的组查询、多个数据库中有一个宕机）会拒绝启动和 check。超过约 3 MiB 的条目（一个 10 MB 的属性值）不会发布。发布内容按人员集合只构建一次。已用测试验证：在每个字节处截断的模式文件、被删除或损坏的数据库、恶意的行、空闲连接、过大的 BER 长度、嵌套 20,000 层的过滤器
v0.14.0变更：v0.13.4 修改组需要重启，因此从数据库中移除的成员会一直保有访问权限，直到有人重启 authnd。v0.14.0 恢复了及时撤销。refresh（默认 60 秒，0 表示关闭）会把每个来源（人员和组）重新读入一份在服务路径之外构建的新快照，并整体替换；刷新失败时保留最近一份良好的快照，且每一轮连续失败只记录一次日志，并点名来源。设置 max_age（默认不设置）后，一旦所提供的数据比它更旧，搜索、人员的 bind 和密码修改都会应答 unavailable。通过 authnd 写入的密码同样经过这一替换。实测：在 SQLite 上，对 500 人、200 个各 50 人的组做一次刷新约占一个核心 2 秒，一次搜索 0.5 毫秒

v0.2.0设备授权、SSH 证书、应用密码、OpenPubkey

v0.16.0max_age 仅在上次认证过旧时才要求重新认证

v0.18.0不含个人声明的 ID 令牌；go-authn/saml v0.4.0

各个库

本文档版本所针对的库版本；每个库的页面都说明了更早的版本改变了什么。

directory v0.13.0属性：除凭据之外，描述某人但不证明任何事的内容，以及永远不能作为属性的名称；user 和 group 块中的 attributes、users_attributes 和 groups_attributes 查询、ldapdir 的 attributes 和 group_attributes
directory v0.14.0⛔ ldapdir 的默认值读取 account 和 uidObject 人员以及 groupOfNames 组，这扩大了机构目录所提供的内容；member DN 只映射到来源已导入的人员
directory v0.15.0对象类，声明出来而从不推断：users 块中的 object_classes 和 group_object_classes，user 和 group 块中的 object_classes，sqldir 的 WithObjectClasses 和 ldapdir 的 Config.ObjectClasses；第一个声明某组的类的来源决定；sqldir.ClosesDB
kdc v0.4.3仅依赖项：以 go-authn/directory v0.12.0 为最低版本
keyfactor v0.4.2仅依赖项：以 go-authn/fido v0.6.2 和 golang.org/x/crypto v0.58.0 为最低版本

尚未实现

  • 通过 LDAP 写入，除了用户更改自己的密码之外。authnd应答对自己 userPassword 的 modify 操作，以及 RFC 3062 密码修改操作（ldappasswd 所发送的），两者都只在提供当前密码时才有效，除此之外不支持任何其他操作：add、delete 和 modifyDN 存在于 go-authn/ldap 中，但有意没有接入（server.go）。该库将 modify 表示为有序列表（RFC 4511 4.6），并应答读取条目控制（RFC 4527），因此基础已经具备；缺少的是谁可以写什么的策略。
  • Kerberos 内部的第二因素：FAST（RFC 6113）中的 OTP预认证（RFC 6560）。在它出现之前，kerberos 块与 mfa 块不能同时配置。
  • RC4-HMAC：该域只签发 aes256-cts-hmac-sha1-96，因此仅以 NT 哈希为人所知的用户无法获得票据。这是一个选择（RC4 已被 RFC 8429弃用），而不是有待填补的缺口。
