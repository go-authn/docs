authn-bridge
トークン

トークン、パスワード、鍵

アプリケーションが authn-bridge から得るもの: ID トークンとアクセストークン、デバイスグラント、SMB と S3 のためのアプリケーションパスワード、そして WireGuard 鍵。

ここでのすべての認証情報は、その人の所属機関での同じログインから始まります。違うのは、その認証情報が誰のためのものか、そしてどう取り消されるかです。証明書は専用のページにあります。

認可コードフローで、すべてのクライアントに PKCE S256 が必須です。code_challenge_method のないリクエストは、S256 として読まれずに拒否されます。RFC 7636 では plain が既定だからです。pkce = "or_nonce" と設定された機密クライアントは、代わりに OpenID の nonce を送れます。

ID トークン

クライアントのため、そしてログインについてのもので、人についてのものではありません。RS256、aud はクライアント ID、sub、auth_time、at_hash、リクエストに nonce があればそれ、IdP がどの認証コンテキストを使ったかを述べた場合は acr を含みます。有効期間はid_token_lifetime で、既定は五分です。

人についての情報は何も含まれません。 スコープが公開するクレームは /userinfo にあります。OIDC Core 5.4 が、アクセストークンが発行されるときについて述べているとおりで、それは常に発行されます。ID トークン自体が認証情報であるクライアント、たとえば opkssh は、id_token_claims = true を設定してそれらをコピーさせます。ID トークンは openid スコープのあるリクエストにのみ発行されます。

アクセストークン

RFC 9068 が述べるとおり、クライアントの audience にあるリソースサーバー向けです。signing_key_file (RS256) または access_token_key_file (ES256) で署名され、typ: at+jwt、有効期間は token_lifetime (既定は一時間) です。リソースサーバーが誰にも尋ねずに判断するために必要なものを運びます。preferred_username、groups、idp (保証した IdP のエンティティ ID)、scope、client_id、そして IdP がセッションの終了時刻を述べた場合は session_end です。グループはクライアントごとに省けます: 後述。

audience が複数のリソースサーバーを指すクライアントは、RFC 8707 の resource を使って、そのうち一つ宛てのトークンを要求できます。複数のリソースサーバーを参照してください。

何を含めないか、そしてその理由

auth_time も acr もありません。RFC 9068 はどちらも許していますが、それらは OIDC Core が置く場所である ID トークンに残ります。アクセストークンからそれを読むものはありません。jti でトークンを検索するこのプロバイダーも、go-fileshare も読みません。ところがアクセストークンは、SSH の keyboard-interactive の回答としても貼り付けられ (ssh-oidc の mccli、motley-cue が /userinfo で検証)、OpenSSH はそのうち 1023 文字を読みます。IdP の acr だけでも、urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport は約 90 文字になります。v0.22.0 より前は、アクセストークンは両方を運んでいました。

長い eppn と三つの AARC エンタイトルメントを持つ ES256 アクセストークン(access_token_key_file) の長さを、authn-bridge の TestES256AccessTokens で、実際の長さの発行者を用いて、RENATER のメタデータの shibmd:Scope の長さ (743 スコープ) に対して測定しました。

スコープの長さ文字数
13中央値885
2295 パーセンタイル945
2999 パーセンタイル992
44最長1092: 超過

v0.22.0 より前は、同じトークンは 1014 / 1074 / 1121 / 1221 文字で、95 パーセンタイル以降は超過していました。今も収まらないのは、最長のスコープと、とりわけ多数のグループです。すべてのエンタイトルメントがその URN 全体を追加し、IdP が送る数に上限はありません。3072 ビット鍵で署名された RS256 のアクセストークンは、グループが一つもなくても約 1150 文字なので、SSH 向けのトークンは ES256 で署名されます。1023 文字を超えると、mccli は代わりに motley-cue にワンタイムパスワードを求めますが、これは motley-cue が既定で許可しています。素の ssh に貼り付けるトークンは、収まらなければなりません。

求めるクライアントにはグループを含めない (v0.23.0)。すべてのグループがその URN 全体を追加し、IdP が送る数に上限がないので、どの鍵も署名アルゴリズムも、グループを運ぶトークンが確実に収まるようにはしません。access_token_groups = false のクライアントは、その人の groups を含まないアクセストークンを得ます。

client "oidc-agent" {
  device              = true
  audience            = ["ssh"]
  access_token_groups = false
}

これは ssh-oidc のためのものです。oidc-agent がトークンを取得し、mccli が keyboard-interactive の回答としてそれを貼り付け、motley-cue が /userinfo で検証して、そこでグループを読みます。authn-bridge の TestAccessTokenWithoutGroups で測定した、50 のグループに属する人の ES256トークンは、最長の RENATER スコープ (44) と実際の長さの発行者で、732 文字です。

テスト用フェデレーションで、三つのグループに属する人が、デバイスグラントでそのクライアント経由でログインします。

既定値は true のままです。 go-fileshare のように、トークンだけで判断するリソースサーバーには、トークンにグループが必要です。/userinfo を読むサーバーにトークンが渡るクライアントについてだけ、省いてください。

証明書とは併用不可。 SSH と X.509 の証明書は、その人のグループをアクセストークンから取るので、access_token_groups = false と ssh_certificates または x509_certificates を併せ持つクライアントはグループを持たない証明書を発行してしまい、グループで認可するサーバーは、理由をどこにも示さずにその人を拒否します。check は、起動時のサーバーと同様に、この組み合わせを拒否します。

client "oidc-agent" {
  device              = true
  audience            = ["ssh"]
  access_token_groups = false
  ssh_certificates    = true
}
$ authn-bridge check --config etc/bridge.hcl
authn-bridge: client "oidc-agent": access_token_groups = false with ssh_certificates or x509_certificates: the certificates take the groups from the access token, and would carry none -- use one client for the certificates and another for tokens pasted into ssh
$ echo $?
1

証明書用に一つのクライアントを、ssh に貼り付けるトークン用に別のクライアントを用意してください。

プロバイダー自身のスコープ (ssh、nfs、app_password、wireguard、wireguard_peers) を持つトークンはプロバイダーのみ宛てです。その aud は発行者で、それらのエンドポイントは他のものを拒否します。リソースサーバーが受け取ったトークンは、ここでリプレイできません。

$ curl -s -X POST http://127.0.0.1:28473/ssh/certificate -d x -D - -o -
HTTP/1.1 401 Unauthorized
Content-Type: text/plain; charset=utf-8
Www-Authenticate: Bearer error="invalid_token"
X-Content-Type-Options: nosniff
Date: Mon, 26 Oct 2026 11:36:20 GMT
Content-Length: 23

the token is not valid

すでに渡されたアクセストークンは、リソースサーバーが単独で検証する署名付きの表明です。RevokePersonが終了させるのは、それとともにここへ戻ってくるすべてで、リソースサーバーはShared Signalsから知ります。

トークン署名鍵のローテーション

すべてのリライングパーティは、/jwks で公開された鍵でトークンを検証します。鍵をその場で差し替えると、彼らが持つすべてのトークンが無効になり、取得される前に使われた鍵は拒否されます。retired_signing_key_files はこの両方を安全にします。そこに載せた鍵は公開されるだけで、署名には使われません。ローテーションには再起動が 2 回必要です。プロバイダーは設定を再読み込みせず、SIGHUP は無視されるためです。このセクションは、bridge の pull request #80（2026-10-26 にマージ、タグ v0.23.4 の後）以降の README に基づきます。

  1. 次の鍵を作る（現在の鍵の隣に）。このコマンドは既存のファイルを上書きしません。

    authn-bridge keygen --key /var/lib/authn-bridge/oidc-2026-10.key

  2. 署名に使う前に公開する。 retired_signing_key_files に追加し、signing_key_file はそのままにして、authn-bridge check を実行し、再起動します。

    signing_key_file          = "/var/lib/authn-bridge/oidc-2026-04.key"   # still signing
retired_signing_key_files = ["/var/lib/authn-bridge/oidc-2026-10.key"] # published only

    /jwks は両方の kid を列挙し、新しいトークンはまだ古い kid を持ちます。リライングパーティが鍵セットをキャッシュする最長の時間以上待ちます。未知の kid で再取得するもの（go-authn/oidc はMinRefresh あたり最大 1 回行います）は待つ必要がなく、固定時間キャッシュするものはその時間が必要です。

  3. 入れ替える。 新しい鍵を signing_key_file にし、古い鍵を retired_signing_key_files に移します。その後 authn-bridge check を実行して再起動します。

    signing_key_file          = "/var/lib/authn-bridge/oidc-2026-10.key"
retired_signing_key_files = ["/var/lib/authn-bridge/oidc-2026-04.key"]

    /jwks は引き続き両方の kid を列挙し、新しいトークンは新しい kid を持ちます。古い鍵で署名されたトークンも検証され続けます。

  4. 古い鍵を退役させる。 それで署名されたトークンが提示されなくなってから行います。token_lifetime（既定 1 時間）と id_token_lifetime（5 分）のうち長い方に、リライングパーティのクロックスキューと鍵セットのキャッシュを加えた時間が目安です。opkssh の場合は代わりに PK Token の有効期間（既定 1 日、最長 1 週間）を待ちます。その後リストから外して再起動すると、/jwks の kid は 1 つになります。

各ステップで、curl -s https://login.example.org/jwks で公開されている kid を確認できます。新しいトークンのkid は、アクセストークンまたは ID トークンの最初のセグメントを base64url デコードしたものです。

access_token_key_file（ES256）も同様にローテーションします。次の鍵は authn-bridge keygen --access-token-key で作り、退役させた鍵は他の鍵と同じく retired_signing_key_files に入れます。state ブロックがないと、リフレッシュトークンと/userinfo がメモリ上にあるため、再起動のたびに全員がログアウトされます。すでに発行されたアクセストークンはリソースサーバーで引き続き検証されます。

README によれば、これは llmflow-gateway をリライングパーティとして go-llmflow/bench（e2e/oidc、TestBridge/c/key-rotation）でエンドツーエンドに検証されています。ステップ 2 の後は、トークンがまだ古い kid を持つ間に /jwks が両方の kid を列挙し、ステップ 3 の後は、入れ替え前に署名されたトークンと後に署名されたトークンの両方が、鍵セットの取得 1 回で受け入れられ、入れ替え直後の SSO ログインも機能します。

ブラウザーなしで: デバイスグラント

WebDAV クライアント、スクリプト、ターミナルには、大学へ送り出すブラウザーがありません。device = true のクライアントはコードを求め (RFC 8628)、人は別のデバイスでログインします。

client "rclone" {
  device           = true
  audience         = ["fileshare"]
  refresh_lifetime = "720h"     # refresh tokens, off unless set
  name             = "rclone (WebDAV)"
}

authn-bridge token --issuer https://login.example.org --client rclone はアクセストークンを出力します。初回はログインし、それ以降は更新します。これは golang.org/x/oauth2 のデバイスクライアントであり、ここで書いたものではありません。

ユーザーコードBCDFGHJKLMNPQRSTVWXZ からの八文字 (母音も数字もなし)、有効期間十分。その間にホストごと (IPv4 アドレス、IPv6 は /64) に間違ったコード十回まで。その周囲の /24 または /48 には十倍まで
ポーリング五秒ごと。それより速いポーリングは slow_down を受ける
待機中のデバイス最大 20,000。それを超えると、全員を拒否せず、最も古いものが押し出される
リフレッシュトークン使用のたびにローテーションされる。ファミリーの終了は refresh_lifetime によってログイン時に固定される。廃止されたものが再度使われると、ファミリーとそれが得たアクセストークンが失効する

アプリケーションパスワード

NTLMv2 と SigV4 は、サーバーがすでに保持していなければならないシークレットを証明するので、SMB やS3 ではトークンでは足りません。app_passwords = true のクライアントは、app_password スコープのトークンで、一度だけ生成して表示されるパスワードを設定できるようにします。authn-bridge app-password --issuer ... --client files (--remove で削除)。

app_passwords {
  driver   = "sqlite"          # sqlite, postgres or mysql
  dsn_file = "/etc/authn-bridge/apppw.dsn"
  store    = ["nt_hash"]       # the default, SMB only; add "password" for S3
  lifetime = "2160h"           # the default, 90 days
  # table  = "app_passwords"   # the default
}

テーブルはなければ作成されます: login, password, nt_hash, expires, idp。プロトコルが必要とするものだけが保存されます。SMB 用の NT ハッシュと、store が求める場合に限りパスワード自体です。go-fileshare は users "sql" ブロックでそれを読みます。クエリでは列名を指定し、* は決して使わないでください。

人を無効化するとそのパスワードが削除され、機関を無効化するとその機関の人々のものが削除されます。削除されたパスワードは、go-fileshare が次にディレクトリを読み込むときに使えなくなります。

WireGuard 鍵

WireGuard はピアを公開鍵だけで認証します。証明書も、有効期限も、失効もありません。そのためプロバイダーは、この鍵は誰のもので、まだ接続してよいかへの答えを保持します。デバイスの VPNクライアントが公開鍵をリースとして登録し、秘密鍵はデバイスから決して出ず、ゲートウェイは有効な鍵を、そのゲートウェイだけに宛てて署名されたリストとして読みます。

certificates_file = "/var/lib/authn-bridge/certificates.json"   # keys are recorded beside the certificates

wireguard {
  lifetime = "24h"              # the default: how long a key is listed; registering again renews it
  max_keys = 10                 # the default: devices per person
}

client "vpn" {                  # what people log in with
  device         = true
  wireguard_keys = true
}

client "vpn-gw" {               # the gateway's own client
  secret_file     = "/etc/authn-bridge/vpn-gw.secret"
  wireguard_peers = ["vpn"]     # the clients whose keys it reads
  ssf_receiver    = true        # optional: told at once when somebody is disabled
}
POST /wireguard/key{"public_key": "...", "device": "laptop"}。wireguard スコープのトークンを伴う。リースの終了時刻を返す
DELETE /wireguard/key{"public_key": "..."}: 所有者が鍵を取り下げる
GET /wireguard/peersゲートウェイ自身の client_credentials トークン、スコープ wireguard_peers 用: そのゲートウェイ宛ての wireguard-peers+jwt 型の署名付き JWT。有効期間五分

他の誰かが保持している鍵、取り下げられた鍵、そして上限を超える鍵は 409 で拒否されます。ゲートウェイのクライアントは機密クライアントでなければならず、wireguard_keys を持つクライアントを指名しなければなりません。リストの形式とゲートウェイ側は go-authn/wireguard のものです。

OpenPubkey と opkssh

opkssh は ID トークンを、CA なしで SSH ログインに変えます。そして作られるトークン (PK Token) は、内包する ID トークンより長生きします。プロバイダーは、コードフローとデバイスフローで nonce をそのまま返し、RS256 で署名し、廃止された鍵を retired_signing_key_files が指名する限り公開 し続けるので、ローテーション前に署名された PK Token も検証できます。

retired_signing_key_files = ["/var/lib/authn-bridge/oidc-2026-03.key"]

opkssh には id_token_claims = true の専用クライアントを与えてください。opkssh は PK Token のクレームで人を照合し、その ID トークンはログインするすべてのサーバーに渡るからです。
