authnd
Personnes

D'où viennent les personnes

Blocs user et group, une base de données SQL, un autre annuaire LDAP : comment chacun s'écrit, l'ordre dans lequel ils sont interrogés, et ce que chacun permet à une personne.

Un bloc user est l’annuaire entier d’un petit site, ou les comptes de service qu’un grand site garde hors de sa base de données. Un site dont les personnes sont déjà dans une base de données ou dans LDAP ne devrait pas les copier dans un second endroit qui devient périmé : un bloc users les lit là où elles sont. Le bloc users est le hcldir de go-authn/directory, le même que litgo-fileshare : un même annuaire est décrit de la même façon aux deux.

Écrites dans la configuration 

user "alice" { password_file = "/etc/authnd/passwords/alice.pw" }

user "carol" {
  nt_hash         = "…"                                   # MD4(UTF16LE(password)), 32 hex
  authorized_keys = ["ssh-ed25519 AAAA… carol@laptop"]    # published as sshPublicKey
}

group "staff" { members = ["alice", "carol"] }
champce que c’est
passwordle mot de passe, en ligne
password_filele même, lu depuis un fichier (blancs en début et fin retirés)
nt_hashMD4(UTF16LE(password)), 32 caractères hexadécimaux — pour un site qui détient cela et non le mot de passe
totp_secretun secret de code à usage unique en base32, d’au moins 128 bits ; voir un second facteur
authorized_keysdes lignes authorized_keys, publiées comme sshPublicKey
authorized_keys_fileles mêmes, depuis un fichier
attributesdepuis la v0.11.0, ce qui décrit la personne sans rien prouver — sn, uidNumber, gidNumber, homeDirectory, mail… — sous forme d’une table de chaînes ou de listes de chaînes ; un bloc group le prend aussi. Ils décident de ce sous quoi l’entrée est publiée : voir les entrées
object_classesdepuis la v0.12.0, les classes auxiliaires sous lesquelles cette personne (ou, dans un bloc group, ce groupe) est publiée, comme ["siteMember"] : déclarées, jamais déduites, et définies dans un schéma de site

Refusés au démarrage, en nommant la personne :

  • password et password_file ensemble — dites lequel ;
  • password et nt_hash ensemble — l’empreinte est dérivée du mot de passe,donc les deux peuvent être en désaccord ;
  • authorized_keys et authorized_keys_file ensemble ;
  • un nt_hash qui ne fait pas 32 caractères hexadécimaux, une ligne authorized_keys qui ne s’analyse pas, un totp_secret de moins de 128 bits ;
  • le même user ou group deux fois, et un group sans membres.

Un membre de groupe qu’aucune source ne connaît est refusé aussi, ce qui attrape une faute de frappe avant qu’elle n’accorde silencieusement rien du tout :

$ authnd check cases/typo.hcl
authnd: group "staff" has "alise" in it, who is not in the configuration file

Un nt_hash seul ne peut pas se lier

Une personne écrite avec seulement nt_hash est publiée, peut être transmise à un serveur SMB par sambaNTPassword, et ne peut pas se lier à authnd lui-même : une liaison simple LDAP envoie le mot de passe, et une empreinte NT n’est pas un moyen de le vérifier ici. bob, ci-dessous, n’a qu’une empreinte NT, et cette empreinte est celle du mot de passe envoyé :

$ ldapwhoami -x -H ldap://127.0.0.1:3893 -D uid=bob,ou=people,dc=example,dc=org -y bob.pwin
ldap_bind: Invalid credentials (49)

check le dit, après les tableaux :

bob and eli cannot bind with a password: their sources hold only what an SMB server needs (an NT hash), which a bind cannot be checked against

Pourquoi c’est refusé, par conception. Une empreinte NT estMD4(UTF16LE(password)), sans sel et rapide à calculer (MS-NLMP §3.3.1,NTOWFv1). L’accepter pour vérifier des liaisons LDAP élargirait ce qu’une empreinte divulguée ouvre, de SMB à toutes les applications qui se lient par authnd. Kerberos refuse ces personnes pour une raison voisine : l’empreinte NT est la clé RC4-HMAC (RFC 4757 §2), et le royaume n’émet que de l’AES. C’est une décision délibérée, non une fonction manquante, et aucune option ne la change.

Que faire à la place. En migrant depuis un annuaire qui ne détient que des empreintes NT (Samba, un AD exporté), donnez à chaque personne un vrai mot de passe ou une vérification du mot de passe dans sa source : une réinitialisation du mot de passe, ou une source users "ldap" dont l’annuaire amont vérifie lui-même le mot de passe. Ne gardez pas l’empreinte NT comme seul identifiant.

Dans une base de données SQL 

users "sql" {
  driver   = "postgres"                      # or mysql (mariadb), or sqlite
  dsn_file = "/etc/authnd/pg.dsn"            # required: a DSN may hold a password
  users    = "select login, secret, nt_hash from staff"   # required
  groups   = "select team, member from team_members"      # optional
}

Les requêtes sont les vôtres, parce que les personnes d’un site ont déjà la forme de ce site. Les colonnes de la requête users sont lues par position : un nom,puis l’un quelconque d’un mot de passe, d’une empreinte NT, de clés SSH (une par ligne) et d’un secret de code à usage unique, dans cet ordre — jusqu’à cinq colonnes. Un NULL est un identifiant que cette personne n’a pas. Une colonne de mot de passe est comparée telle qu’elle est stockée : authnd n’a pas de réglage pour une colonne d’empreintes. La requête groups renvoie un nom de groupe et un membre, une ligne par appartenance.

Deux autres requêtes, facultatives, lisent des attributs par alias de colonne plutôt que par position : users_attributes (un nom, puis une colonne par attribut) et groups_attributes (un groupe, puis de même). Un alias sans guillemets est mis en minuscules par PostgreSQL. Voirles entrées.

Les classes de ce que donne un bloc users se déclarent à côté de ses requêtes (à partir de la v0.12.0, les mêmes deux clés dans un bloc users "ldap") :

users "sql" {
  # ...
  object_classes       = ["supannPerson", "eduPerson"]   # every person this block gives
  group_object_classes = ["supannGroupe"]                # every group
}

Chacune doit être une classe AUXILIARY que définit le schéma servi (le schéma standard, ou schema_files et un bloc schema),et pas une classe qu’authnd déduit lui-même. Une personne à qui manque un MUST d’une classe déclarée est publiée sans elle, et check le dit.

driver accepte postgres (ou postgresql, pgx), mysql (ou mariadb)et sqlite (ou sqlite3). La base de données est contactée au démarrage, avant que quoi que ce soit n’écoute, si bien qu’une base qui ne répond pas arrête le serveur là où quelqu’un regarde :

$ authnd check cases/nodb
authnd: users "sql": the postgres database is not answering: failed to connect to `user=authnd database=authnd`:
	127.0.0.1:1 (127.0.0.1): dial error: dial tcp 127.0.0.1:1: connect: connection refused
	127.0.0.1:1 (127.0.0.1): dial error: dial tcp 127.0.0.1:1: connect: connection refused

PostgreSQL sur la même machine, par son socket et l’authentification peer,n’a pas besoin de mot de passe dans le DSN : host=/run/postgresql dbname=authnd user=authnd.SQLite dans le répertoire d’état : file:/var/lib/authnd/people.db.

Une clé qui appartient à l’autre sorte de bloc est refusée plutôt qu’ignorée :

$ authnd check cases/sqlwrongkey.hcl
authnd: users "sql" has base_dn in it, which belongs to an ldap block

Dans un autre annuaire LDAP 

users "ldap" {
  url                = "ldaps://ldap.example.org"
  base_dn            = "ou=people,dc=example,dc=org"
  bind_dn            = "cn=reader,dc=example,dc=org"
  bind_password_file = "/etc/authnd/upstream.pw"
}

url et base_dn sont obligatoires. Où se trouvent les personnes et les groupes, et quels attributs les nomment :

clédéfaut
user_filter(|(objectClass=posixAccount)(objectClass=account)(objectClass=uidObject))
user_attributeuid
group_base_dnbase_dn
group_filter(|(objectClass=posixGroup)(objectClass=groupOfNames))
group_attributecn
group_member_attributeaucun : memberUid (des noms) et member (des DN) ; s’il est défini, c’est le seul attribut lu
totp_attributeaucun : il n’existe pas d’attribut standard, et une supposition ne lirait rien tout en ayant l’air d’avoir cherché
attributes, group_attributesaucun : les attributs à copier depuis l’entrée de chaque personne et celle de chaque groupe, comme ["mail", "uidNumber", "homeDirectory"] et ["gidNumber"] (les entrées)
object_classes, group_object_classesaucun : à partir de la v0.12.0, les classes auxiliaires sous lesquelles est publiée chaque personne et chaque groupe lu depuis cet annuaire (schémas de site) ; les classes que portent les entrées en amont ne sont jamais copiées
start_tlsfalse

Un DN member ne compte que lorsqu’il est le DN d’une entrée qu’a renvoyée la recherche des personnes : un DN en dehors d’elles, ou qui ne nomme personne, ne correspond à personne, et le nom n’est jamais lu dans le DN.sambaNTPassword et sshPublicKey sont lus sous ces noms.

Depuis la v0.11.0, les valeurs par défaut lisent davantage de l’annuaire d’un établissement

Le bloc est celui de go-authn/directory, et directory v0.14.0, qu’embarque authnd v0.11.0, a élargi ses valeurs par défaut : jusqu’à la v0.10.2,user_filter valait (objectClass=posixAccount), group_filter (objectClass=posixGroup) et group_member_attribute memberUid. Un annuaire qui contient des entrées account ou uidObject qui ne sont pas des posixAccounts — comptes de service, hôtes nommés par uid, personnes importées d’ailleurs — les donne désormais à authnd, et chacune peut être vérifiée par une liaison ; ses groupes groupOfNames deviennent des groupes ici. Pour garder exactement l’ancien ensemble, écrivez les anciennes valeurs :

users "ldap" {
  # ...
  user_filter            = "(objectClass=posixAccount)"
  group_filter           = "(objectClass=posixGroup)"
  group_member_attribute = "memberUid"
}

Deux choses sont refusées avant que quoi que ce soit ne soit ouvert :

$ authnd check cases/ldap-clear.hcl
authnd: users "ldap" would send every password to "ldap.example.org" in the clear: use ldaps://, or start_tls = true (RFC 4513 §5.1.3)

$ authnd check cases/ldap-cred.hcl
authnd: users "ldap" has credentials in its url, and a url is printed: use bind_dn with bind_password_file

ldap:// vers une adresse de bouclage et ldapi:// sont acceptés : personne n’est sur le chemin.

Un annuaire derrière celui-ci vérifie les mots de passe en s’y liant ; il ne les transmet pas. Ici, un authnd se place devant un autre, sous une base différente ;celui de derrière est l’exemple de check,servi sur le 3893 :

listen  = "127.0.0.1:3894"
base_dn = "dc=example,dc=net"

users "ldap" {
  url                = "ldap://127.0.0.1:3893"
  base_dn            = "ou=people,dc=example,dc=org"
  group_base_dn      = "ou=groups,dc=example,dc=org"
  bind_dn            = "cn=reader,dc=example,dc=org"
  bind_password_file = "etc/authnd/reader.pw"
}

user "svc-backup" { password_file = "etc/authnd/svc-backup.pw" }

Chaque personne que publie l’annuaire de derrière est un account et chaque groupe un groupOfNames, puisqu’aucun n’a d’attributs POSIX : les valeurs par défaut les lisent, et les DN member des groupes correspondent aux personnes importées. Avec les valeurs par défaut en vigueur jusqu’à la v0.10.2,(objectClass=posixAccount) n’aurait trouvé aucune d’elles.

A password check suffit pour une liaison, et ne suffit jamais pour unticket Kerberos ni pour SMB.

L’ordre, et l’unique exception

Les sources sont interrogées dans l’ordre où elles sont écrites, et la première qui connaît un nom le possède. Les blocs user viennent toujours en premier, si bien qu’un compte de service écrit localement n’est pas supplanté par quelqu’un du même nom dans la base de données. L’appartenance aux groupes est l’union de toutes les sources : un groupe que nomment à la fois un bloc group et la requête groups d’une base de données a les membres des deux.

Deux noms qui ne diffèrent que par la casse sont refusés

Un uid est comparé sans tenir compte de la casse (RFC 4519 §2.39), et tout DN aussi, si bien queDora dans le fichier et dora dans une base de données sont un seul nom pour LDAP et deux personnes pour tout ce qui compare des octets — un changement de mot de passe par l’une atterrirait sur l’autre. Une telle configuration ne démarre pas :

$ authnd check cases/case.hcl
authnd: "Dora" (from the configuration file) and "dora" (from a sqlite database) differ only by case, and an LDAP name does not tell them apart: a uid is compared ignoring case. Rename one of them

Lues une fois

Chaque source est lue une fois, au démarrage. Une personne ajoutée à la base de données, ou une appartenance modifiée dans l’annuaire derrière celui-ci, est servie après un redémarrage, pas avant. Cela inclut une colonne de mot de passe dans une base de données : elle est lue avec le reste de la ligne. Un annuaire derrière celui-ci ne diffère qu’en ce qu’une liaison est vérifiée en s’y liant, si bien qu’un mot de passe changé là-bas est celui qui fonctionne. L’autre exception est un mot de passe qu’une personne change par authnd lui-même, qui est appliqué aussitôt.Il n’y a pas de rechargement ; voir le faire tourner.
