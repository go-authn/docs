Tokens

Tokens, contraseñas y claves

Lo que una aplicación obtiene de authn-bridge: tokens de ID y tokens de acceso, la concesión de dispositivo, contraseñas de aplicación para SMB y S3, y claves WireGuard.

Cada credencial de esta página empieza con el mismo inicio de sesión en la institución de la persona. Lo que cambia es para quién es la credencial, y cómo se retira. Los certificados tienen su propia página.

El flujo de código de autorización, con PKCE S256 obligatorio para todos los clientes. Una petición sin code_challenge_method se rechaza en lugar de leerse como S256, ya que el RFC 7636 hace de plain el valor por defecto. Un cliente confidencial configurado con pkce = "or_nonce" puede enviar en su lugar unnonce de OpenID.

El token de ID

Para el cliente, y sobre el inicio de sesión, no sobre la persona: RS256, aud el ID del cliente, sub, auth_time, at_hash, el nonce cuando la petición lo llevaba, y acr cuando el IdP indicó qué contexto de autenticación usó. Duraciónid_token_lifetime, cinco minutos por defecto.

No contiene nada sobre la persona. Los claims que entregan los scopes están en/userinfo, como indica OIDC Core 5.4 cuando se emite un token de acceso, y siempre se emite uno. Un cliente cuyo token de ID es en sí mismo la credencial,como opkssh, establece id_token_claims = true para que se copien en él. Un token de ID solo se emite para una petición con el scope openid.

El token de acceso

Para los servidores de recursos de la audience del cliente, como describe el RFC 9068: firmado con signing_key_file (RS256) o access_token_key_file (ES256), typ: at+jwt, válido durante token_lifetime (una hora por defecto).Lleva lo que un servidor de recursos necesita para decidir sin preguntar a nadie:preferred_username, groups, idp (el entity ID del IdP que lo avaló),scope, client_id, y session_end cuando el IdP indicó cuándo termina su sesión.Los grupos pueden dejarse fuera, cliente por cliente: más abajo.

Un cliente cuya audience nombra varios servidores de recursos puede pedir un token dirigido a uno de ellos, con el resource del RFC 8707: véasevarios servidores de recursos.

Lo que deja fuera, y por qué

Ni auth_time ni acr, aunque el RFC 9068 permite ambos. Siguen en el token de ID, donde los pone OIDC Core. Nada los lee de un token de acceso: ni este proveedor, que busca un token por su jti, ni go-fileshare. En cambio, un token de acceso también se pega como respuesta SSH keyboard-interactive (mccli de ssh-oidc, que motley-cue comprueba en /userinfo), y OpenSSH lee 1023 caracteres de ella; solo el acr de un IdP,urn:oasis:names:tc:SAML:2.0:ac:classes:PasswordProtectedTransport, ocupa unos 90. Antes de la v0.22.0, el token de acceso llevaba ambos.

La longitud de un token de acceso ES256 (access_token_key_file) para un eppn largo y tres entitlements AARC, medida por TestES256AccessTokens de authn-bridge con un emisor de longitud real, frente a las longitudes de losshibmd:Scope de los metadatos de RENATER (743 scopes):

Antes de la v0.22.0, el mismo token tenía 1014 / 1074 / 1121 / 1221 caracteres:se pasaba desde el percentil 95. Lo que sigue sin caber son los scopes más largos y, sobre todo, muchos grupos: cada entitlement añade su URN entera, y nada limita cuántos envía un IdP. Un token de acceso RS256, firmado con una clave de 3072 bits, tiene unos 1150 caracteres antes de cualquier grupo, así que un token destinado a SSH se firma con ES256. Por encima de 1023 caracteres,mccli pide a motley-cue una contraseña de un solo uso en su lugar, algo que motley-cue permite por defecto; un token pegado en un ssh normal tiene que caber.

Sin grupos, para un cliente que lo pida (v0.23.0). Cada grupo añade su URN entera, y nada limita cuántos envía un IdP, así que ninguna clave ni ningún algoritmo de firma garantiza que quepa un token que lleve grupos. Un cliente conaccess_token_groups = false recibe tokens de acceso sin los groups de la persona:

client "oidc-agent" {
  device              = true
  audience            = ["ssh"]
  access_token_groups = false
}

Está pensado para ssh-oidc: oidc-agent obtiene el token, mccli lo pega como respuesta keyboard-interactive, y motley-cue lo comprueba en /userinfo y lee allí los grupos. Medido por TestAccessTokenWithoutGroups de authn-bridge, un token ES256 para alguien que está en 50 grupos, con el scope más largo de RENATER (44) y un emisor de longitud real, tiene 732 caracteres.

Frente a una federación de prueba, una persona que está en tres grupos inicia sesión a través de ese cliente, con el device grant:

Rechazado con certificados. Los certificados SSH y X.509 toman los grupos de la persona del token de acceso, así que un cliente conaccess_token_groups = false y ssh_certificates o x509_certificates emitiría certificados sin ninguno, y un servidor que autoriza por grupo rechazaría a la persona sin que nada en ninguna parte dijera por qué. check,como el servidor al arrancar, rechaza la combinación:

client "oidc-agent" {
  device              = true
  audience            = ["ssh"]
  access_token_groups = false
  ssh_certificates    = true
}
$ authn-bridge check --config etc/bridge.hcl
authn-bridge: client "oidc-agent": access_token_groups = false with ssh_certificates or x509_certificates: the certificates take the groups from the access token, and would carry none -- use one client for the certificates and another for tokens pasted into ssh
$ echo $?
1

Los certificados tienen entonces su propio cliente, y los tokens que se pegan en ssh, otro.

Un token que tiene uno de los scopes propios del proveedor (ssh, nfs,app_password, wireguard, wireguard_peers) va dirigido solo al proveedor: su aud es el emisor, y esos endpoints rechazan cualquier otro. Un token que ha recibido un servidor de recursos no se puede reutilizar aquí:

the token is not valid

Un token de acceso ya entregado es una declaración firmada que un servidor de recursos comprueba por su cuenta. Lo que RevokePerson termina es todo lo que vuelve aquí con él; el servidor de recursos se entera mediante Shared Signals.

Rotar la clave de firma de los tokens

Cada parte confiante verifica los tokens con las claves publicadas en /jwks. Una clave cambiada en el sitio invalida todos los tokens que tienen, y una clave usada antes de que la hayan obtenido es rechazada. retired_signing_key_files hace seguras ambas cosas: una clave listada ahí se publica y nunca firma. La rotación requiere dos reinicios, porque el proveedor no recarga su configuración y un SIGHUP se ignora. Esta sección sigue el README del bridge tras su pull request #80 (fusionada el 2026-10-26, después de la etiqueta v0.23.4).

  1. Crear la clave siguiente, junto a la actual. El comando se niega a sobrescribir un archivo:

    authn-bridge keygen --key /var/lib/authn-bridge/oidc-2026-10.key

  2. Publicarla antes de que firme. Añadirla a retired_signing_key_files, dejarsigning_key_file como está, ejecutar authn-bridge check y reiniciar:

    signing_key_file          = "/var/lib/authn-bridge/oidc-2026-04.key"   # still signing
retired_signing_key_files = ["/var/lib/authn-bridge/oidc-2026-10.key"] # published only

    /jwks lista ahora ambos kid, y los tokens nuevos aún llevan el antiguo. Esperar al menos lo que tarda en cachearse el conjunto de claves la parte confiante más lenta. La que lo vuelve a pedir ante un kid desconocido (go-authn/oidc lo hace, como mucho una vez porMinRefresh) no necesita esperar; la que cachea un tiempo fijo necesita ese tiempo.

  3. Intercambiar. Hacer de la clave nueva el signing_key_file y mover la antigua aretired_signing_key_files. Después authn-bridge check y reiniciar:

    signing_key_file          = "/var/lib/authn-bridge/oidc-2026-10.key"
retired_signing_key_files = ["/var/lib/authn-bridge/oidc-2026-04.key"]

    /jwks sigue listando ambos kid, y los tokens nuevos llevan el nuevo. Los tokens firmados con la clave antigua siguen verificándose.

  4. Retirar la clave antigua cuando ya no pueda presentarse ningún token firmado con ella:al menos el mayor de token_lifetime (1 h por defecto) e id_token_lifetime (5 min),más el desfase de reloj de las partes confiantes y su caché de claves. Para opkssh, esperar en su lugar la vida del PK Token (un día por defecto, hasta una semana). Luego quitarla de la lista y reiniciar: /jwks lista un solo kid.

En cada paso, curl -s https://login.example.org/jwks muestra los kid publicados, y elkid de un token recién emitido es el primer segmento de cualquier token de acceso o de ID,decodificado en base64url.

Un access_token_key_file (ES256) rota igual: escribir el siguiente conauthn-bridge keygen --access-token-key, y una retirada va en retired_signing_key_files como cualquier otra. Sin un bloque state, cada reinicio desconecta a todo el mundo, porque los tokens de actualización y /userinfo viven en memoria; los tokens de acceso ya emitidos siguen verificándose en los servidores de recursos.

El README informa de que esto se verificó de extremo a extremo con llmflow-gateway como parte confiante, en go-llmflow/bench (e2e/oidc, TestBridge/c/key-rotation): tras el paso 2,/jwks lista ambos kid mientras los tokens llevan aún el antiguo; tras el paso 3, un token firmado antes del intercambio y otro firmado después se aceptan, con una sola obtención del conjunto de claves; y un inicio de sesión SSO justo después del intercambio funciona.

Sin navegador: la concesión de dispositivo

Un cliente WebDAV, un script o un terminal no tienen ningún navegador que enviar a una universidad. Un cliente con device = true pide un código (RFC 8628), y la persona inicia sesión en cualquier otro dispositivo:

client "rclone" {
  device           = true
  audience         = ["fileshare"]
  refresh_lifetime = "720h"     # refresh tokens, off unless set
  name             = "rclone (WebDAV)"
}

authn-bridge token --issuer https://login.example.org --client rclone imprime un token de acceso, iniciando sesión la primera vez y actualizándolo a partir de entonces; es el cliente de dispositivo de golang.org/x/oauth2, no uno escrito aquí.

códigos de usuarioocho letras de BCDFGHJKLMNPQRSTVWXZ (sin vocales, sin dígitos), válidos diez minutos; diez códigos erróneos por host en ese tiempo (una dirección IPv4, un /64 IPv6), y diez veces más para el /24 o /48 que lo rodea
sondeocada cinco segundos; sondear más deprisa provoca slow_down
dispositivos en espera20 000 como máximo; por encima, se expulsa al más antiguo en lugar de rechazar a todos
tokens de actualizaciónrotados en cada uso, dentro de una familia cuyo final se fija en el inicio de sesión mediante refresh_lifetime; uno retirado que se vuelve a usar revoca la familia y los tokens de acceso obtenidos con ella

Contraseñas de aplicación

NTLMv2 y SigV4 prueban un secreto que el servidor ya debe tener, así que ningún token sirve para SMB o S3. Un cliente con app_passwords = true permite que un token con el scope app_password establezca una, generada y mostrada una sola vez: authn-bridge app-password --issuer ... --client files (--remove la borra).

app_passwords {
  driver   = "sqlite"          # sqlite, postgres or mysql
  dsn_file = "/etc/authn-bridge/apppw.dsn"
  store    = ["nt_hash"]       # the default, SMB only; add "password" for S3
  lifetime = "2160h"           # the default, 90 days
  # table  = "app_passwords"   # the default
}

La tabla se crea si no existe: login, password, nt_hash, expires, idp. Solo se guarda lo que necesitan los protocolos: el hash NT para SMB, y la propia contraseña solo cuando store lo pide. go-fileshare la lee con un bloqueusers "sql"; nombre las columnas en su consulta, nunca *.

Desactivar a una persona elimina su contraseña; desactivar una institución elimina las de sus personas. Una contraseña eliminada deja de funcionar en go-fileshare cuando este vuelve a leer su directorio.

Claves WireGuard

WireGuard autentica a un par por su clave pública y nada más: sin certificado, sin caducidad, sin revocación. Por eso el proveedor guarda la respuesta a ¿de quién es esta clave, y puede seguir conectándose? El cliente VPN del dispositivo registra la clave pública, por un tiempo de concesión; la clave privada nunca sale del dispositivo; una pasarela lee las claves activas como una lista firmada solo para ella.

certificates_file = "/var/lib/authn-bridge/certificates.json"   # keys are recorded beside the certificates

wireguard {
  lifetime = "24h"              # the default: how long a key is listed; registering again renews it
  max_keys = 10                 # the default: devices per person
}

client "vpn" {                  # what people log in with
  device         = true
  wireguard_keys = true
}

client "vpn-gw" {               # the gateway's own client
  secret_file     = "/etc/authn-bridge/vpn-gw.secret"
  wireguard_peers = ["vpn"]     # the clients whose keys it reads
  ssf_receiver    = true        # optional: told at once when somebody is disabled
}
POST /wireguard/key{"public_key": "...", "device": "laptop"}, con un token del scope wireguard; responde con el final de la concesión
DELETE /wireguard/key{"public_key": "..."}: el propietario retira una clave
GET /wireguard/peerspara el token client_credentials propio de la pasarela, scope wireguard_peers: un JWT firmado de tipo wireguard-peers+jwt, dirigido a esa pasarela, válido cinco minutos

Una clave que tiene otra persona, una clave que se ha retirado y una clave de más se rechazan con 409. Un cliente de pasarela debe ser confidencial, y debe nombrar clientes que tengan wireguard_keys. El formato de la lista, y el lado de la pasarela, son los de go-authn/wireguard.

OpenPubkey y opkssh

opkssh convierte un token de ID en inicios de sesión SSH sin ninguna CA, y el token que crea (un PK Token) sobrevive al token de ID que contiene. El proveedor devuelve el nonce literalmente en el flujo de código y en el flujo de dispositivo, firma en RS256, y mantiene una clave retirada publicada mientrasretired_signing_key_files la nombre, para que un PK Token firmado antes de una rotación siga verificándose:

retired_signing_key_files = ["/var/lib/authn-bridge/oidc-2026-03.key"]

Dé a opkssh un cliente propio con id_token_claims = true: identifica a las personas por los claims del PK Token, y su token de ID viaja a cada servidor en el que inicia sesión.
