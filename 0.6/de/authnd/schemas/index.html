Standort-Schemata

Standort-Schemata und die Klassen, die eine Quelle deklariert

SUPANN, eduPerson oder die eigenen Attribute eines Standorts bereitstellen: schema_files und der schema-Block fügen Definitionen hinzu, object_classes deklariert, welche Hilfsklassen die Personen und Gruppen einer Quelle tragen, und check sagt, was weggelassen wurde. Ab v0.13.0 werden DIT-Content-Rules, Name Forms und DIT-Structure-Rules durchgesetzt.

Ein SUPANN- oder eduPerson-Attribut wird weggelassen, sofern keine Klasse seines Eintrags es erlaubt. authnd veröffentlicht nur, was das Schema zulässt, das es bereitstellt (siehedie Einträge),und das Standardschema kennt weder supannEtablissement nocheduPersonAffiliation. Ab v0.12.0 sagt ein Standort drei Dinge, in dieser Reihenfolge:

  1. welche Definitionen hinzukommen: schema_files, die Dateien, die sein slapd bereits lädt, und ein schema { }-Block für das, was nur lokal gilt;
  2. welche Hilfsklassen (AUXILIARY) seine Personen und Gruppen tragen: object_classes;
  3. nichts weiter. Eine Klasse wird deklariert, nie abgeleitet: Ein Attribut, das in einer Datenbank auftaucht, ändert nicht, als was ein Eintrag veröffentlicht wird.

Ein Beispiel: ein Schema, eine Datenbank, eine Konfiguration

Ein Schema in der .schema-Form von OpenLDAP: eine Klasse, die eine Quelle deklarieren kann(exampleStaff, AUXILIARY, mit einem MUST), und eine, die sie nicht kann(exampleUnit, STRUCTURAL).

objectidentifier exampleRoot  1.3.6.1.4.1.99999
objectidentifier exampleAttr  exampleRoot:1
objectidentifier exampleClass exampleRoot:2

attributetype ( exampleAttr:1 NAME 'exampleBadge'
	DESC 'the number on a badge'
	EQUALITY caseIgnoreMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

attributetype ( exampleAttr:2 NAME 'exampleEmployeeId'
	DESC 'a staff number'
	EQUALITY caseExactMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

# AUXILIARY: it can be declared. exampleStaff has a MUST.
objectclass ( exampleClass:1 NAME 'exampleStaff' SUP top AUXILIARY
	DESC 'somebody employed: has a staff number'
	MUST exampleEmployeeId
	MAY exampleBadge )

# STRUCTURAL: it cannot be declared (an entry has one structural chain).
objectclass ( exampleClass:2 NAME 'exampleUnit' SUP top STRUCTURAL
	MUST cn )

Und die Konfiguration:

schema_files = ["etc/authnd/example.schema"]

schema {
  attribute_type "exampleLocker" {
    oid    = "1.3.6.1.4.1.99999.1.3"
    syntax = "1.3.6.1.4.1.1466.115.121.1.15"
  }
  object_class "exampleLockerHolder" {
    oid  = "1.3.6.1.4.1.99999.2.3"
    kind = "auxiliary"
    may  = ["exampleLocker"]
  }
}

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret from staff"
  users_attributes = "select login, sn, badge as exampleBadge, empid as exampleEmployeeId, locker as exampleLocker from person_attrs"
  object_classes   = ["exampleStaff", "exampleLockerHolder"]   # declared, never inferred

schema_files

schema_files ist eine Liste von OpenLDAP-.schema-Dateien oder cn=config-LDIF-Dateien.Sie werden wie veröffentlicht geladen, der Reihe nach, auf dem Standardschema (und den drei Definitionen von Samba, mit dem samba-Block), durch dieslapd-kompatiblen Reader von go-authn/ldap:beliebige Reihenfolge der Terme, Fortsetzungszeilen nach slapd und RFC 2849, Base64, Längenpräfixe{N} und objectidentifier-Makros, die eine Datei definieren und die nächste verwenden kann, wie über das include von slapd hinweg. Nichts wird vorher umgewandelt, also ist die Datei, die der slapd eines Standorts lädt, die Datei, die authnd lädt. Die Definitionen werden untercn=Subschema bereitgestellt.

  • Ein relativer Pfad ist relativ zum Arbeitsverzeichnis, wie jeder andere Pfad in der Konfiguration. Verwenden Sie in einem Dienst absolute Pfade: Das Arbeitsverzeichnis einer systemd-Unit ist /.

  • Jede Datei muss eine reguläre Datei von höchstens 4 MiB sein und wird einmal gelesen, beim Start.

  • Die Dateien entscheiden, was jeder Eintrag enthalten darf. Sie sind keine Geheimnisse, aber halten Sie sie bei der übrigen Konfiguration: root:authnd, Modus 0640, in einem Verzeichnis, in das nur root schreibt (Installation).

  • Eine Datei, die sich nicht aufbauen lässt, verweigert den Start und check, mit der Datei, der Zeile und der Spalte, in der die Definition beginnt, und der Art der Ablehnung am Ende der Meldung:eine unbekannte Oberklasse, ein unbekanntes Attribut, eine unbekannte Matching-Regel oder Syntax (unknown reference), eine STRUCTURAL-Klasse, die von einer AUXILIARY-Klasse abgeleitet ist(kind violation), eine OID oder ein Name, der doppelt definiert ist (duplicate OID,duplicate name). Seit v0.12.1 stammen Stelle und Art aus dem typisierten*schema.BuildError von go-authn/ldap, nicht aus dem Lesen seiner Meldung. Eine aus einer Datei gelesene Definition beginnt in Spalte 1, auch wenn ihr Text über mehrere Zeilen umgebrochen ist. Ein Duplikat sagt, wo seine erste Definition steht, und eine Neudefinition sagt, welche Standarddatei oder welche Zeile einer früheren Datei das Original enthält. Zwei Beispiele:

    cases/unknown.schema hat ein MAY, das nirgends definiert ist:

    # exampleB has a MAY that is defined nowhere.
objectclass ( 1.3.6.1.4.1.99999.2.9 NAME 'exampleB' SUP top AUXILIARY
	MAY noSuchAttribute )
    $ authnd check cases/unknown.hcl
authnd: schema_files: cases/unknown.schema:2:1: the object class exampleB has MAY noSuchAttribute, which is not a defined attribute type (unknown reference)

    cases/twice.schema gibt zwei Attributtypen dieselbe OID:

    attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleA'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )

attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleB'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )
    $ authnd check cases/twice.hcl
authnd: schema_files: cases/twice.schema:4:1: the attribute type 1.3.6.1.4.1.99999.1.9 is defined twice (first defined at cases/twice.schema:1:1) (duplicate OID)

Eine Neudefinition wird abgelehnt, selbst eine identische

Eine Datei darf nicht definieren, was schon da ist: die Definitionen des Standardschemas,die von Samba oder die einer früheren Datei. Sie wird selbst wortgleich abgelehnt, was die eigene Regel von slapd ist: Die Definitionen einer Schemadatei laufen durchparse_at und parse_oc, und slapd beantwortet eine bereits indizierte OID oder einen bereits indizierten Namen mit Duplicate attributeType (gleiche OID und Namen) oder Inconsistent duplicate attributeType (servers/slapd/at.c, oc.c). Nur das fest einprogrammierte Schema von slapd selbst darf Ersteres. Eine Datei, die slapd ablehnt, ist eine Datei, die authnd ablehnt.

Die andere Lesart müsste einen Gewinner auswählen, und das wäre eine stille Änderung dessen,was jedem Client über ein Standardattribut gesagt wird; die Ablehnung nennt stattdessen die Zeile.Die Ablehnung sagt, ob der Text derselbe war. Eine Datei, die cn (2.5.4.3) mit einer eigenen Definition neu definiert:

$ authnd check cases/dup.hcl
authnd: schema_files: cases/cn-copy.schema:1:1: the attribute type cn (2.5.4.3) is already defined by the standard schema (rfc4519.schema:42:1), and this is a different definition: a schema file adds definitions and never replaces one -- slapd refuses this too ("Duplicate attributeType", servers/slapd/at.c and oc.c). Remove it from this file

Der schema { }-Block

Für Definitionen, die nur lokal gelten, hält ein schema-Block sie in HCL2, in der Form von hclschema:attribute_type, object_class, object_identifier, matching_rule undldap_syntax. Er wird nach den Dateien gelesen, darf also deren Definitionen verwenden, und es kann mehrere geben.

Werte müssen Literale sein: keine Variablen, keine Funktionen, kein ${...} oder%{...}. Der Block wird vom selben Decoder gelesen wie eine .hcl-Schemadatei,mit denselben Grenzen, und jeder Fehler nennt die eigene Zeile und Spalte der Konfiguration.Ein Block, der nicht in der nativen Syntax von HCL steht, wird abgelehnt.

object_classes

Eine Definition im Schema erlaubt ein Attribut; sie setzt die Klasse niemandem auf. Eine Quelledeklariert die Hilfsklassen (AUXILIARY), mit denen ihre Personen und Gruppen veröffentlicht werden:

woSchlüsselwas er deklariert
users-Block, jede Artobject_classesdie Klassen jeder Person, die der Block liefert
users-Block, jede Artgroup_object_classesdie Klassen jeder Gruppe
user-Blockobject_classesdie Klassen dieser Person
group-Blockobject_classesdie Klassen dieser Gruppe
users "sql" {
  # ...
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

user  "alice" { object_classes = ["siteMember"] }
group "staff" { object_classes = ["supannGroupe"] }

Diese Schlüssel sind die von go-authn/directory, ab v0.15.0(Bibliothek). Namen werden ohne Beachtung der Groß- und Kleinschreibung verglichen und je einmal in der geschriebenen Reihenfolge gehalten.

Was authnd mit einer deklarierten Klasse macht:

  • Sie wird mit ihren Oberklassen veröffentlicht, nach den Klassen, die authnd ableitet(RFC 4512 §3.3: Alle Oberklassen der genannten Klassen werden implizit hinzugefügt). Die Attribute, die die Klasse erlaubt, bleiben erhalten, statt weggelassen zu werden.
  • Sie wird nie abgeleitet. Eine Person, deren Quelle nichts deklariert, verliert weiterhin die Attribute, die keine ihrer Klassen erlaubt, was auch immer die Datenbank enthält.
  • Einer Person, der ein MUST einer deklarierten Klasse fehlt, wird diese Klasse vorenthalten. Ihre Attribute werden weggelassen wie jedes Attribut, das keine Klasse erlaubt, und beides wird gemeldet. Das ist die Regel, der authnd überall folgt: Die Person bleibt veröffentlicht, das Problem wird gesagt, nichts wird stillschweigend geändert.Die Person zurückzuhalten würde sie wegen eines fehlenden Attributs aus jeder Suche nehmen;die Klasse ohne ihr MUST zu veröffentlichen würde einen Eintrag liefern,der das bereitgestellte Schema nicht besteht.
  • Zwei Quellen können unterschiedliche Klassen für eine Gruppe deklarieren. Die erste Quelle, die Klassen für eine Gruppe deklariert, entscheidet, ganz, und eine spätere Liste wird ignoriert: weder zusammengeführt noch ein Fehler. check sagt es.

Was abgelehnt wird, und warum

Eine deklarierte Klasse wird beim Start und von check gegen das bereitgestellte Schema geprüft. Sie muss sein:

  • definiert, vom Standardschema, einer Datei oder einem Block;
  • AUXILIARY (RFC 4512 §4.1.1). Ein Eintrag hat genau eine STRUCTURAL-Kette(§2.4.2), die authnd aus dem wählt, was die Person hat; eine Deklaration kann keine zweite hinzufügen;
  • keine, die authnd selbst ableitet: account, inetOrgPerson und seine Oberklassen, posixAccount, posixGroup, ldapPublicKey, uidObject,sambaSamAccount, groupOfNames und organizationalRole, unter jedem ihrer Namen. Diese ergeben sich aus dem, was eine Person oder Gruppe hat, und eine Deklaration kann check nicht überstimmen.

Andernfalls wird der Start abgelehnt, mit Nennung des Blocks, seiner Position und der Klasse.exampleUnit ist STRUCTURAL:

$ authnd check cases/structural.hcl
authnd: cases/structural.hcl:10:20: users "sql" object_classes: exampleUnit is STRUCTURAL, and an entry has exactly one structural chain (RFC 4512 §2.4.2), which authnd chooses: only an AUXILIARY class (§4.1.1) can be declared

go-authn/directory prüft davor die Schreibweise: Eine Klasse ist ein Deskriptor, nie eine OID, ein Leerzeichen, ein Anführungszeichen oder eine Klammer.

Ebenfalls abgelehnt, und aus demselben Grund, das Schema ehrlich zu halten:

abgelehntwarum
eine Datei, die eine Definition neu definiert, selbst wortgleichdie Regel von slapd: oben
eine Datei, die keine reguläre Datei ist oder über 4 MiB hateine FIFO würde den Start blockieren, /dev/zero würde nie enden
ein schema-Block mit einer Variablen, einer Funktion oder ${...}nur Literalwerte, wie in einer .hcl-Schemadatei
eine undefinierte Klasse in object_classesein Versprechen, das nichts prüfen kann
eine STRUCTURAL-Klasse oder eine, die authnd ableitetdie Liste oben

Was check ausgibt

Vier Arten von Zeilen, zusätzlich zu den üblichen; das Startprotokoll trägt dieselben:

  • schema: <file> adds … und schema: the schema block at <file>:<line>:<column> adds …:was jede Datei und jeder Block hinzugefügt hat, gezählt als Object-Identifier-Makros,Attributtypen und Objektklassen;
  • <file>:<line>:<column>: users "sql" declares … for its people (einuser- oder group-Block sagt user "ann" declares … for this person undgroup "staff" declares … for this group): was jede Quelle deklariert;
  • <name> is published without <class>, which its source declares: …,mit Nennung des MUST, das der Person fehlt;
  • group staff: the configuration file declares supannGroupe and a postgres database declares eduMember; the first is published and the second is ignored (the first source that declares classes for a group decides):zwei Quellen, die sich über eine Gruppe uneins sind, was sonst stumm bliebe.

Attribute, die mangels einer Klasse weggelassen werden, sind die Zeilen is published without <attribute>: no class of the entry allows it; <classes> would, diedie Einträge bereits beschreiben: Mit einer Deklaration nennen sie die Klasse, die Sie nicht deklariert haben.

DIT-Content-Rules, Name Forms und DIT-Structure-Rules

Ab v0.13.0 akzeptieren schema_files und der schema { }-Block auch die drei Arten von Definitionen, die RFC 4512 §4.1.6 und §4.1.7 zu Klassen und Attributen hinzufügen, und authnd setzt sie durch (go-authn/ldap v0.11.0 liest,baut und prüft sie; die Bibliotheksseite sagt, wie):

DefinitionRFC 4512was sie sagtwas authnd damit tut
DIT-Content-Rule§4.1.6für eine strukturelle Klasse: welche Hilfsklassen (AUX) hinzugefügt werden dürfen, welche Attribute verlangt (MUST), erlaubt (MAY) oder ausgeschlossen (NOT) sindformt jeden Eintrag (Daten)
Name Form§4.1.7.2aus welchen Attributnamen (dem RDN) ein Eintrag einer strukturellen Klasse bestehthält den Baum (Konfiguration)

Sie werden unter cn=Subschema veröffentlicht (dITContentRules, nameForms,dITStructureRules), nur wenn es welche gibt. Gibt es keine, gilt nichts auf dieser Seite, und gegenüber v0.12.4 ändert sich nichts.

Ein Schema mit je einer, und sein HCL

In der .schema-Form von OpenLDAP. ditcontentrule ist die Direktive von slapd.conf(5);nameform und ditstructurerule sind die von go-authn/ldap, da slapd keine hat(unten). authnd prüft außerdem den Baum, den es veröffentlicht(Suffix, ou=people, ou=groups, Accounts, Personen und Gruppen darunter), sodass die Datei fünf Name Forms und fünf Structure-Rules enthält, nicht je eine:

# Rules for the tree authnd publishes. 1.3.6.1.4.1.99999 is an example arc:
# nobody is assigned it, use your own.

# A content rule belongs to a structural class and takes that class's OID.
# inetOrgPerson (2.16.840.1.113730.3.2.2): posixAccount and uidObject may be
# added, ldapPublicKey may not; telephoneNumber is required; description is
# precluded.
ditcontentrule ( 2.16.840.1.113730.3.2.2 NAME 'examplePersonRule'
	AUX ( posixAccount $ uidObject )
	MUST telephoneNumber
	NOT description )

# A name form says which attribute names an entry of a structural class.
nameform ( 1.3.6.1.4.1.99999.9.1 NAME 'exampleDomainForm' OC domain MUST dc )
nameform ( 1.3.6.1.4.1.99999.9.2 NAME 'exampleUnitForm' OC organizationalUnit MUST ou )
nameform ( 1.3.6.1.4.1.99999.9.3 NAME 'exampleAccountForm' OC account MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.4 NAME 'examplePersonForm' OC inetOrgPerson MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.5 NAME 'examplePosixGroupForm' OC posixGroup MUST cn )

# names the rule of the parent entry.

ditstructurerule ( 2 NAME 'exampleUnit' FORM exampleUnitForm SUP 1 )

ditstructurerule ( 4 NAME 'examplePersons' FORM examplePersonForm SUP 2 )

Die Regel gilt für die strukturelle Klasse des Eintrags, und was sie bewirkt, wird beim Start und von check Eintrag für Eintrag gesagt:

die Regel sagtder Eintraggesagt als
AUX führt eine Hilfsklasse nicht auf, ob deklariert oder von authnd abgeleitet (posixAccount, ldapPublicKey, sambaSamAccount, uidObject)die Klasse wird weggelassen, mit den Attributen, die nur sie erlaubte (und dem sshPublicKey, sambaSID und sambaNTPassword, die authnd für sie hinzufügen würde); eine deklarierte Klasse, deren Oberklasse weggelassen wird, geht mit ihr<name> is published without <class>: the DIT content rule <rule> does not allow it (not in its AUX)
NOT nennt ein Attributdas Attribut wird verworfen, von wem auch immer es stammt<name> is published without <attribute>: the DIT content rule <rule> precludes it (NOT)
MUST nennt ein Attribut, das dem Eintrag fehltder Eintrag wird ausgelassen: Die Regel gilt für den Eintrag als Ganzes, und keine Klasse kann weggelassen werden, um ihn gültig zu machen<name> is NOT published: … <attribute> is required by the DIT content rule <rule> and is missing (RFC 4512 4.1.6)

Was die Structure-Rules mit dem Baum machen

Mit mindestens einer aktiven DIT-Structure-Rule geht authnd beim Start und incheck den Baum durch, den es veröffentlichen wird:

  • der Suffix (base_dn), mit der Klasse, die sein RDN nennt: dc einedomain, o eine organization, ou eine organizationalUnit, c eincountry, l eine locality. Ein Suffix, der von einem anderen Attribut benannt wird,wird abgelehnt;
  • ou=people und ou=groups, als organizationalUnits;
  • das RDN-Attribut, mit dem authnd seine Personen (uid) und seine Gruppen (cn) benennt.

Ein Container, den keine Regel platziert, ein Suffix einer Art, für die keine Regel eine Name Form hat, eine Name Form, die uid oder cn ablehnt, oder ein Container, unter dem nichts von dem, was authnd veröffentlicht, platziert werden könnte, verweigert den Start, undcheck: alle Ablehnungen auf einmal, mit Nennung des DN, der Regel oder Name Form und der Klausel, und ohne je ein Geheimnis zu wiederholen. Eine Person oder Gruppe, deren strukturelle Klasse von ihren Daten abhängt (ein sn, eine gidNumber) und die unter ihrem Container keine Regel hat, wird stattdessen ausgelassen und gesagt, wie team oben: Der Server startet. Ohne aktive Structure-Rule ändert sich nichts.

Ein Schema, dessen einzige Structure-Rule für Personen, peopleByCN, eine Name Form platziert, die cn will (accountByCN: OC account MUST cn):

$ authnd check cases/bad.hcl
authnd: DIT structure rules: authnd names its people uid=<name>,ou=people,dc=example,dc=org, and an account named so is refused: the RDN (uid) is allowed by the name form of no DIT structure rule that places account under an entry governed by the rule 2: accountByCN needs cn

authnd benennt seine Personen uid=<name>: Die Regeln müssen das erlauben. Und ein Schema, dessen Regel für organizationalUnit kein SUP hat, sodass eineorganizationalUnit nur an der Wurzel stehen kann, lässt sowohl ou=people als auchou=groups ohne Platz und sagt beides auf einmal:

$ authnd check cases/root.hcl

DIT structure rules: ou=groups,dc=example,dc=org, where authnd publishes its groups, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)

Beide enden mit Status 1. Die Dateien dahinter (cases/bad.schema undcases/root.schema) enthalten dieselben fünf Name Forms und nur die Structure-Rules,die den Punkt machen.

Wo authnd und slapd sich unterscheiden

go-authn/ldap liest die OpenLDAP-Dateien, und einige der Regeln sind die von OpenLDAP.Das sind die Unterschiede, gesagt statt entdeckt:

  • slapd implementiert nur Content-Rules. Es hat keine Direktive für Name Forms oder Structure-Rules. Format schreibt die Schlüsselwörter nameform undditstructurerule, die die dieser Bibliothek sind, und slapd lehnt sie ab: Halten Sie sie im HCL oder in einer Datei, die nur authnd liest. ditcontentrule ist die von slapd.
  • Eine OBSOLETE-Regel ist inaktiv (RFC 4512 §4.1.6), ebenso ihre Name Form oder Structure-Rule. slapd lehnt stattdessen den Eintrag ab.
  • Ohne Content-Rule sind Hilfsklassen erlaubt. Das ist das Verhalten von slapd(sein Flag SLAP_DISALLOW_AUX_WO_CR wird von keinem disallow-Schlüsselwort gesetzt)und das von authnd. RFC 4512 §2.4.3 sagt etwas anderes; die Bibliothek bietet es alsValidateOptions{StrictAuxiliary: true} an, und authnd setzt es nicht.
  • libldap kann das SUP einer Structure-Rule nicht lesen. Eine Structure-Rule mitSUP wird hier gelesen und von libldap nicht, sodass die Ablehnung einer solchen Datei durch libldap kein Urteil über die Datei ist.
  • Eine Datei, die eine Regel neu definiert, wird abgelehnt, selbst wortgleich, wie jede andere Definition (oben).

Was es kostet

Upgrade

Für ein Schema ohne Regeln ändert sich nichts: v0.12.4 lehnte alle drei Arten ab, sodass eine Konfiguration, die darauf gestartet ist, keine enthält. Es gibt eine Ausnahme. Einschema { }-String, der kein gültiges UTF-8 ist (eine überlange Kodierung, die HCL durchlässt), startete auf v0.12.4 und wird jetzt abgelehnt, weil er nicht so veröffentlicht werden könnte, wie er geschrieben wurde.

SUPANN, als das echte Beispiel

SUPANN ist der Attributsatz der französischen Hochschulbildung und Forschung(supannPerson, supannEtablissement, supannEntite …), mit eduPerson daneben. RENATER veröffentlicht das technische Schema, mit den anderen, auf seiner Dokumentationsseite:

https://services.renater.fr/documentation/supann/supann2021/recommandations/tables_references/schemas_techniques_supann

Laden Sie die Datei von dort herunter. Sie wird auf dieser Seite nicht wiedergegeben: Sie nennt keine Lizenz, also kopiert diese Seite sie nicht, und eine Kopie hier würde veralten, wenn RENATER sie überarbeitet. Dann:

sudo install -o root -g authnd -m 0640 supann.schema eduperson.ldif /etc/authnd/
schema_files = ["/etc/authnd/supann.schema", "/etc/authnd/eduperson.ldif"]

users "sql" {
  # ...
  users_attributes     = "select login, sn, etab as \"supannEtablissement\" from staff"
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

Führen Sie authnd check aus und lesen Sie zuerst die schema:-Zeilen: Eine Datei, die slapd lädt, lädt auch hier, und eine, die eine Standarddefinition neu definiert, wird mit ihrer Zeile abgelehnt. Lesen Sie dann die Zeilen published without: Eine Person, der ein MUST von supannPerson oder eduPerson fehlt, wird ohne die Klasse veröffentlicht, undcheck nennt das MUST. Setzen Sie einen Alias in Anführungszeichen, wo es auf seine Schreibweise ankommt(PostgreSQL wandelt einen Alias ohne Anführungszeichen in Kleinbuchstaben um; siehedie Einträge).
