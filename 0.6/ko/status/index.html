상태

이 문서가 설명하는 릴리스, 각 릴리스에서 추가된 것, 그리고 아직 구현되지 않은 것.

이 문서는 문서 버전 0.6이며 다음을 설명합니다.

프로그램릴리스모듈
authndv0.13.2github.com/go-authn/authnd
authn-bridgev0.23.4github.com/go-authn/bridge
authn-revokdv0.6.6github.com/go-authn/revocation
sshcert-authorizev0.1.9github.com/go-authn/sshcert

라이브러리의 버전은 해당 페이지에 있습니다. ldap은 DIT 콘텐츠 규칙, 이름 형식, DIT 구조 규칙의 읽기, 적용, 게시와 빌드되지 않는 스키마를 위한 타입이 있는 BuildError, HCL2 스키마, ldapschema 변환기를 갖춘 v0.11.2이고,directory는 선언된 오브젝트 클래스를 갖춘 v0.15.0입니다. authnd v0.13.2는 ldap v0.11.2와 directory v0.15.0을 내장합니다.위 프로그램 중 어느 것이든 새 마이너 버전이 나오면 새 문서 버전이 됩니다. 따라서 독자가 /docs/0.6/에서 찾는 페이지는 설치한 것을 계속 설명하며, 이전 릴리스의 페이지는 /docs/0.1/, /docs/0.2/, /docs/0.3/, /docs/0.4/, /docs/0.5/에 남아 있습니다.

보안: v0.11.1이 아니라 authnd v0.12.0을 사용하십시오

authnd는 인증서를 검증하며(x509.Certificate.Verify, govulncheck에 따르면main에서 도달 가능), Go 1.27.2의 crypto/x509는 GO-2026-6809가 지목하는 침해된 중간 인증서들을 신뢰 해제하지 않았습니다. v0.11.1의 릴리스 바이너리는 Go 1.27.2로 빌드되었으며 영향을 받습니다. v0.12.0은 Go 1.27.3으로 빌드되었고 go 지시문이 1.27.3이므로, go install이 수정된 툴체인으로 알아서 전환합니다. Go 1.27.3에서의 govulncheck는 취약점이 없다고 보고합니다. 릴리스 바이너리는go version -m에서 go1.27.3을 보고합니다.업그레이드 안내를 참조하십시오.

보안: authn-bridge v0.23.3과 authn-revokd v0.6.5를 사용하세요

Go 1.27.2에서 govulncheck는 두 프로그램 모두에서 GO-2026-6809를 보고합니다. crypto/x509의 Certificate.Verify가 알려진 침해된 중간 인증서를 거부하지 않았습니다. Go 1.26.10과 1.27.3에서 수정되었습니다. 더 오래된 Go로 빌드한 릴리스 바이너리는 영향을 받습니다. v0.23.3과 v0.6.5는 Go 1.27.3으로 빌드되고 go 지시어도 1.27.3이므로, go install이 스스로 수정된 툴체인으로 전환합니다. 두 릴리스 바이너리는 go version -m에서 go1.27.3을 보고합니다. sshcert는 영향을 받지 않으며 새 릴리스가 없습니다.

각 릴리스에서 추가된 것

각 줄은 해당 릴리스를 만든 이유가 된 변경입니다. 의존성만 갱신한 릴리스는, 이 문서 버전이 설명하는 것을 제외하고 생략했습니다.

authnd

v0.1.0다른 곳(파일, SQL 데이터베이스, 다른 디렉터리)에 있는 사람들을 위한 LDAP 서버
v0.2.0필드가 하나뿐인 프로토콜 위의 두 번째 인증 요소
v0.5.0정확히 하나의 신원만 건드리는 비밀번호 변경, 경쟁 상태 없는 다시 불러오기, KDC가 변경을 인식함
v0.6.0oidc, directory, ldap, totp, mfa의 보안 수정
v0.7.0비밀번호를 변경하려면 이전 비밀번호가 필요함, 비밀 값을 고정 길이 다이제스트로 비교함
v0.8.2코드는 올바른 비밀번호 뒤에서만 인정됨, 리더는 구성된 DN으로 키가 지정됨
v0.9.0stable이 아니라 고정된 Go 1.27.1로 빌드하고 테스트함
v0.9.2모든 태그에 릴리스 바이너리, SHA256SUMS, 빌드 출처 증명
v0.9.3체크아웃 밖에서 빌드한 바이너리, 각각이 태그를 정확히 보고해야 함
v0.9.4SIGHUP이 더 이상 authnd를 종료하지 않음: 기록만 하고 아무것도 다시 불러오지 않음
v0.9.5릴리스가 바이너리 하나가 아니라 모든 바이너리의 빌드 정보를 확인함
v0.9.6check가 각 사람에게 티켓을 발급할 수 없는 이유를 알려 줌
v0.10.0check가 서버처럼 인증서와 keytab을 열어 봄, 비밀번호로 바인드할 수 없는 사람과 토큰으로 여전히 허용되는 사람을 알려 줌, 수신 대기 줄이 렐름을 연 뒤에 나옴
v0.10.1go-authn/kdc v0.4.2: till이 19700101000000Z이면 1970년에 만료된 티켓이 아니라 가장 긴 티켓을 받음
v0.10.2go-authn/directory v0.12.0: 빈 그룹은 memberUid 없는 posixGroup으로 게시됨
v0.11.0표준 스키마 엔트리, 각각 cn=Subschema에서 제공하는 스키마에 맞춰짐, attributes, users_attributes, groups_attributes, (uidNumber>=1000)이 정수로 비교함. ⛔ publish_nt_hash에는 samba 블록이 필요하며, posixAccount나 posixGroup으로 필터링하는 소비자는 더 적은 엔트리를 봄
v0.11.1시작 줄이 실제로 사람들을 제공하는 소스만 지정함: user 블록이 없으면 더 이상 구성 파일을 지정하지 않음
v0.12.0사이트 스키마: schema_files(OpenLDAP .schema와 cn=config LDIF를 게시된 그대로, 재정의는 slapd처럼 동일하더라도 거부됨)와 schema { } 블록, 소스별로 object_classes로 선언하는 보조 클래스(시작 시 검증되고 상위 클래스와 함께 게시됨), check가 파일, 선언, MUST가 없어 사람에게서 빠진 클래스, 두 소스가 일치하지 않는 그룹을 보고함. ⛔ Go 1.27.3으로 빌드됨: v0.11.1의 바이너리(Go 1.27.2)는 GO-2026-6809의 영향을 받음
v0.12.1빌드되지 않는 스키마 파일이나 블록은 go-authn/ldap v0.10.0의 BuildError가 담고 있는 위치에서 열 번호와 함께 거부됨(site.schema:6:이 site.schema:6:1:이 됨). 메시지는 거부의 종류로 끝나며, 중복은 첫 번째 정의의 위치를 알려 줌
v0.12.2릴리스 바이너리를 -s -w 대신 -ldflags="-w"로 링크함. 심볼 테이블이 남으므로 govulncheck -mode binary가 링크되지 않은 코드의 취약점을 보고하는 대신 정확해짐. 약 9 % 커짐(darwin/arm64에서 18.8 MB에서 20.5 MB)
v0.12.3go-authn/ldap v0.10.1: schema_files를 선형 시간에 읽음. ⛔ v0.12.2까지는 짧은 이어짐 줄로 된 큰 스키마 파일(4 MiB: 약 3분)이 시작을 멈추게 했음: 통제할 수 없는 파일에 의한 서비스 거부
v0.12.4go-authn/ldap v0.10.2: cn=Subschema 의 RFC 2307 정의 13개(uidNumber, gidNumber, ipHostNumber, ipNetworkNumber, ipNetmaskNumber, macAddress 와 클래스 ipService, ipProtocol, oncRpc, ipHost, ipNetwork, ieee802Device, bootableDevice)의 DESC 값에 더 이상 RFC 쪽 나눔의 들여쓰기가 들어 있지 않습니다. ... in an administrative domain' 이 아니라 DESC 'An integer uniquely identifying a user in an administrative domain' 입니다
v0.13.0DIT 콘텐츠 규칙, 이름 형식, DIT 구조 규칙(go-authn/ldap v0.11.0): schema_files와 schema { } 블록이 세 종류를 받아들이고 authnd가 이를 적용합니다. 콘텐츠 규칙은 각 엔트리의 형태를 정합니다. AUX에 나열되지 않은 보조 클래스는 (그 클래스만 허용하던 속성과 함께) 빠지고, NOT 속성은 제거되며, MUST가 빠진 엔트리는 게시에서 제외됩니다. 각각 로그에 남고 check가 보고합니다. 활성 구조 규칙이 있으면 트리(접미사, ou=people, ou=groups, uid 또는 cn RDN)를 시작 시와 check에서 검사하며, 위반은 시작을 거부합니다. 거부 사유는 한꺼번에 모두 보고되고 비밀 값은 절대 출력되지 않습니다. 어떤 규칙도 자리를 주지 않는 엔트리는 제외됩니다. ⛔ UTF-8이 아닌 schema { } 문자열은 이제 거부됩니다. 10,000명을 게시할 때 엔트리당 할당은 규칙이 있으면 416회, 없으면 265회입니다(시간은 부하 상태에서 측정되어 신뢰할 수 없음)
v0.13.1성능만 개선, go-authn/ldap v0.11.1 내장: 10,000명을 게시할 때(BenchmarkPublish10k, -cpu 1) 엔트리당 할당은 규칙이 있으면 364회, 없으면 239회이며(v0.13.0은 416회와 265회), 한 번 실행에 규칙이 있으면 102.5 MiB를 씁니다(v0.13.0은 147.5 MiB). 시간은 부하 10~16에서 측정되어 신뢰할 수 없음
v0.13.2성능만 개선, go-authn/ldap v0.11.2 내장: 속성 열 개짜리 엔트리에서 Validate의 할당이 76회에서 12회로 줄었습니다. 10,000명을 게시할 때(BenchmarkPublish10k, -cpu 1) 엔트리당 할당은 규칙이 있으면 128회, 없으면 85회이며(v0.13.1은 364회와 239회), 한 번 실행에 규칙이 있으면 54.8 MiB를 씁니다(v0.13.1은 102.5 MiB). 시간(부하 8~11): 규칙이 있을 때 약 158 ms에서 약 90 ms

아직 구현되지 않은 것

  • LDAP을 통한 쓰기, 사람이 자신의 비밀번호를 바꾸는 경우는 제외합니다. authnd는 자기 자신의 userPassword에 대한 modify와 RFC 3062 비밀번호 변경 작업(ldappasswd가 보내는 것)에만 응답하며, 둘 다 현재 비밀번호가 있어야 합니다.그 밖에는 아무것도 하지 않습니다. add, delete, modifyDN은 go-authn/ldap에 존재하지만 의도적으로 연결하지 않았습니다(server.go). 라이브러리는 modify를 순서 있는 목록으로 다루고(RFC 4511 4.6) 읽기 엔트리 컨트롤(RFC 4527)에 응답하므로 형태는 갖추어져 있습니다. 부족한 것은 누가 무엇을 쓸 수 있는가라는 정책입니다.
  • Kerberos 안의 두 번째 인증 요소: FAST(RFC 6113) 안에서의 OTP 사전 인증(RFC 6560). 이것이 생기기 전까지는 kerberos 블록과 mfa 블록을 함께 구성할 수 없습니다.
  • RC4-HMAC: 렐름은 aes256-cts-hmac-sha1-96만 발급하므로 NT 해시로만 알려진 사람에게는 티켓을 발급할 수 없습니다. 이것은 채워지기를 기다리는 빈틈이 아니라 선택입니다(RC4는 RFC 8429에서 사용 중단되었습니다).
