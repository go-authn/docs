authnd, 다른 곳에 있는 사람들을 위한 LDAP 서버

구성 파일, SQL 데이터베이스 또는 다른 디렉터리에 있는 사람들을 위한 LDAP 디렉터리이며, 선택적으로 Kerberos 렐름도 제공합니다.

사이트의 사람들은 이미 데이터베이스, 파일 또는 다른 디렉터리에 있습니다. 이들을 인증하려는 것들은 LDAP을 사용합니다. authnd는 그 앞단입니다.go-authn/directory의 소스 위에서 바인드와 검색을 처리하므로, 데이터베이스에 있는 내용을 디렉터리에 질의할 줄 아는 어떤 것이든 읽을 수 있습니다. 순수 Go, CGO_ENABLED=0, 바이너리 하나입니다. 이 문서는 v0.13.0을 설명하며, 이 버전의 엔트리는 표준 스키마를 따르고 cn=Subschema에서 제공하는 스키마를 통과합니다. 사이트는 이 스키마를 자신의 스키마로 확장할 수 있고(SUPANN, eduPerson),DIT 콘텐츠 규칙, 이름 형식, 구조 규칙으로 엔트리의 형태까지 정할 수 있습니다. 그 아래에는 go-authn/ldap v0.11.0과 go-authn/directory v0.15.0이 있습니다. 무엇이 검증되었고 무엇이 아닌지는 상태 페이지에 있습니다.

v0.11.x에서 업그레이드하는 경우

  • ⛔ 보안: v0.11.1이 아니라 v0.12.0을 사용하십시오. v0.11.1의 릴리스 바이너리는 Go 1.27.2로 빌드되었는데, 이 버전의 crypto/x509는 GO-2026-6809가 지목하는 침해된 중간 인증서들을 신뢰 해제하지 않으며, authnd는 인증서를 검증합니다.v0.12.0은 Go 1.27.3으로 빌드되었고 go 지시문도 1.27.3이므로, go install이 수정된 툴체인으로 알아서 전환합니다.
  • 새 키를 사용하지 않는 구성은 v0.11.1이 게시하던 것을 그대로 게시합니다. 클래스는 선언되는 것이지 추론되지 않으므로, object_classes가 없으면 아무것도 바뀌지 않습니다.
  • 모두 선택 사항인 새 기능: schema_files와 schema 블록은 제공하는 스키마에 사이트의 정의를 추가하고, object_classes와group_object_classes는 소스의 사람과 그룹이 갖는 보조 클래스를 선언합니다.이미 있는 정의를 다시 정의하는 정의는, slapd가 거부하는 것과 마찬가지로, 한 글자도 다르지 않더라도 거부됩니다.
  • check와 시작 로그는 어떤 파일과 블록을 불러왔는지, 각 소스가 무엇을 선언하는지,MUST가 없어서 사람에게서 빠진 클래스가 무엇인지, 두 소스가 서로 다르게 선언하는 그룹이 무엇인지 알려 줍니다.

다시 시작하기 전에 설치가 안내하는 대로 새 바이너리로 authnd check를 실행하십시오.

v0.10.x에서 업그레이드하는 경우

  • publish_nt_hash = true에는 이제 samba 블록이 필요하며, 없으면 authnd가 시작하지 않습니다.
  • uidNumber, gidNumber, homeDirectory가 없는 사람은 더 이상posixAccount가 아니고, gidNumber가 없는 그룹은 더 이상 posixGroup이 아니므로, 해당 클래스로 필터링하는 소비자는 더 적은 엔트리를 봅니다.엔트리를 참조하십시오.
  • users "ldap" 블록은 이제 기본적으로 그 뒤의 디렉터리를 더 많이 읽습니다.사람들을 참조하십시오.

새 바이너리의 authnd check는 다시 시작하기 전에 이 세 가지를 모두 알려 줍니다.

authnd --config /etc/authnd      # serve
authnd check /etc/authnd         # say what would be served, without listening

가장 작은 구성 

listen  = "127.0.0.1:3893"            # the default
base_dn = "dc=example,dc=org"         # required

reader "cn=reader,dc=example,dc=org" { password_file = "/etc/authnd/reader.pw" }

user "alice" { password_file = "/etc/authnd/passwords/alice.pw" }

group "staff" { members = ["alice"] }

사람은 uid=<name>,ou=people,<base_dn>로, 그룹은cn=<name>,ou=groups,<base_dn>로 게시됩니다. 각 엔트리가 무엇인지는 소스가 제공한 것에 따라 정해집니다. 사람은 account이거나, sn이 있으면inetOrgPerson이고, uidNumber, gidNumber, homeDirectory가 있어야만posixAccount입니다. 모든 사람은 uidObject입니다. 그룹은 gidNumber가 있으면posixGroup(memberUid 포함)이고, 없으면 groupOfNames(member DN 포함)이며,비어 있기까지 하면 organizationalRole입니다. 사람에게 키가 있으면sshPublicKey가 추가되고, publish_nt_hash가 허용하고 SID를 줄 수 있으면 sambaNTPassword가 추가됩니다. 모든 엔트리는 게시되기 전에 cn=Subschema에서 제공하는 스키마를 통과합니다.엔트리와 스키마를 참조하십시오. v0.10.2까지는 무엇을 가졌든 모든 사람이 posixAccount였고 모든 그룹이 posixGroup이었습니다.

--config(-c)는 파일 또는 디렉터리를 받으며 여러 번 지정할 수 있습니다.디렉터리는 그 안의 모든 .hcl 파일을 이름 순으로 읽어 하나의 구성으로 병합합니다. base_dn이 없거나 사람이 아무도 없는 구성은 시작하지 않습니다.

누가 바인드할 수 있고 누가 읽을 수 있는가

LDAP 서버는 사람을 증명하도록 요청받으므로, 거부가 곧 설계입니다. 다음은 v0.12.3 릴리스 바이너리가 OpenLDAP의 클라이언트에 대해 낸 응답입니다.

$ ldapwhoami -x -H ldap://127.0.0.1:3893 -D uid=alice,ou=people,dc=example,dc=org -y alice.pwin
dn:uid=alice,ou=people,dc=example,dc=org

$ ldapwhoami -x -H ldap://127.0.0.1:3893 -D uid=alice,ou=people,dc=example,dc=org -y wrong.pwin
ldap_bind: Invalid credentials (49)

$ ldapwhoami -x -H ldap://127.0.0.1:3893 -D uid=alice,ou=people,dc=example,dc=org -w ''
ldap_bind: Server is unwilling to perform (53)
	additional info: an unauthenticated bind proves nothing, and this server does not accept one

$ ldapsearch -x -LLL -H ldap://127.0.0.1:3893 -D uid=alice,ou=people,dc=example,dc=org -y alice.pwin -b dc=example,dc=org '(uid=alice)'
Insufficient access (50)
Additional information: only a reader may search
요청응답이유
빈 이름, 빈 비밀번호 (RFC 4513 §5.1.1, 익명)성공“나는 아무도 아니다"라는 뜻이며 이는 사실이고, 클라이언트는 아무것도 알아내기 전에 이것을 보냅니다
이름이 있고 비밀번호가 빈 경우 (§5.1.2, 비인증)unwillingToPerform누군가를 지목하면서 아무것도 증명하지 않습니다. §5.1.2가 바로 이 코드를 요구합니다. invalidCredentials라고 하면 사람에게 비밀번호가 틀렸다고 알려 주는 셈입니다
틀린 비밀번호, 또는 여기에 없는 이름invalidCredentials둘을 구분하지 않습니다
reader가 아닌 누군가의 검색insufficientAccessRights바인드는 당신이 누구인지를 증명할 뿐이며, 모든 사람을 읽도록 허용되는 것은 별개의 문제입니다
add, delete, modifyDNunwillingToPerform연결된 핸들러가 없습니다. 유일한 쓰기는 사람 자신의 비밀번호입니다

reader는 바인드 DN과 password 또는 password_file을 가진 서비스 계정입니다.둘 다 없는 reader는 시작 시 거부됩니다(아무것도 증명하지 않는 reader는 단계만 늘어난 익명 검색입니다). reader가 하나도 없으면 아무도 검색할 수 없으며,check가 이를 알려 줍니다.

루트 DSE는 디스커버리에 필요하므로 익명 클라이언트에게 응답합니다.

$ ldapsearch -x -LLL -H ldap://127.0.0.1:3893 -s base -b '' '+' '*'
dn:
objectClass: top
objectClass: OpenLDAProotDSE
supportedLDAPVersion: 3
namingContexts: dc=example,dc=org
supportedExtension: 1.3.6.1.4.1.4203.1.11.3
supportedExtension: 1.3.6.1.4.1.4203.1.11.1
supportedControl: 1.2.840.113556.1.4.319
supportedControl: 1.3.6.1.1.13.1
supportedControl: 1.3.6.1.1.13.2
supportedFeatures: 1.3.6.1.4.1.4203.1.5.1
supportedFeatures: 1.3.6.1.4.1.4203.1.5.3
subschemaSubentry: cn=Subschema
vendorName: go-authn/authnd
vendorVersion: v0.13.0

1.3.6.1.4.1.4203.1.11.1은 RFC 3062 비밀번호 변경 작업입니다.subschemaSubentry는 스키마를 가리키며, 이것도 익명 클라이언트에게 응답합니다.supportedSASLMechanisms: OAUTHBEARER는 oidc 블록이 있을 때만 나타납니다.

트랜스크립트에 대하여

이 문서에 보이는 모든 명령은 2026-10-26에 배포된 릴리스 바이너리로 다시 실행한 것이며, 손으로 다시 쓴 것이 아닙니다. authnd v0.12.3(authnd-darwin-arm64, relverify로 SHA256SUMS 및 그 증명(attestation)과 대조함; go version -m: go1.27.3, mod github.com/go-authn/authnd v0.12.3, vcs.modified=false), authn-bridge v0.23.4, authn-revokd v0.6.6, sshcert-authorize v0.1.9, ldapschema v0.10.1입니다. 명령이 출력한 것이 그대로 여기에 실려 있습니다. 예외는 두 개의 트랜스크립트이며, 각각 그것이 있는 자리에 그렇게 밝혀 두었습니다. 토큰 페이지의 oidctool 클라이언트는 이 문서를 위해 작성한 테스트 클라이언트로 어떤 릴리스에도 포함되지 않으며, 그 트랜스크립트와 함께 보이는 서버 줄은 v0.10.0 릴리스 바이너리가 출력한 것입니다. 다른 하나는 연합 페이지의 RENATER 만료 메타데이터로, 이 파일은 더 이상 공개되지 않습니다. 모두 macOS에 포함된 OpenLDAP 및 Heimdal 클라이언트로, 127.0.0.1의 비특권 포트에서 임시 디렉터리 안에서 요청했습니다. 그래서 그 뒤의 구성이 etc/authnd/passwords/alice.pw 같은 상대 경로로 파일을 지정하고, 비밀번호 파일의 이름이 alice.pwin 같은 것입니다. 예제의 /etc/authnd 경로는 설치된 서버가 사용하는 경로입니다. authnd 의 버전을 출력하는 트랜스크립트는 v0.13.0(authnd-darwin-arm64, relverify 로 SHA256SUMS 와 증명에 대해 확인; go version -m: go1.27.3, mod github.com/go-authn/authnd v0.13.0)으로 다시 실행했습니다. 여기와 운영 페이지의 root DSE, 그리고 authnd --version 입니다. 엔트리 페이지의 스키마는 v0.12.4(mod github.com/go-authn/authnd v0.12.4, vcs.modified=false)가 출력한 것이며, v0.13.0은 규칙이 없는 스키마에 대해 dITContentRules, nameForms, dITStructureRules 의 값을 출력하지 않는다는 것을 확인했습니다. 사이트 스키마 페이지의 규칙 절에 그 절을 무엇으로 실행했는지 적혀 있습니다.
