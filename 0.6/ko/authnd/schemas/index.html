authnd
사이트 스키마

사이트 스키마와 소스가 선언하는 클래스

SUPANN, eduPerson 또는 사이트 고유의 속성을 제공합니다. schema_files와 schema 블록은 정의를 추가하고, object_classes는 소스의 사람과 그룹이 갖는 보조 클래스를 선언하며, check는 무엇이 빠졌는지 알려 줍니다. v0.13.0부터 DIT 콘텐츠 규칙, 이름 형식, DIT 구조 규칙이 적용됩니다.

SUPANN이나 eduPerson 속성은 엔트리의 어떤 클래스도 허용하지 않으면 제외됩니다. authnd는 제공하는 스키마가 허용하는 것만 게시하며(엔트리를 참조),표준 스키마는 supannEtablissement나 eduPersonAffiliation을 알지 못합니다.v0.12.0부터 사이트는 다음 세 가지를 이 순서로 지정합니다.

  1. 추가할 정의: schema_files, 즉 사이트의 slapd가 이미 불러오는 파일과,로컬에서만 쓰는 것을 위한 schema { } 블록
  2. 사람과 그룹이 갖는 보조 클래스: object_classes
  3. 그 밖에는 없습니다. 클래스는 선언되는 것이지 추론되지 않습니다. 데이터베이스에 속성이 나타난다고 해서 엔트리가 무엇으로 게시되는지가 바뀌지는 않습니다.

이 페이지의 예제는 예제입니다

아래의 example.schema는 이 페이지를 위해 작성되었습니다. OID는 아무에게도 할당되지 않은 1.3.6.1.4.1.99999 아래에 있으므로, 여러분 자신의 것을 사용하고 이것을 절대 복사하지 마십시오. SUPANN은 페이지 끝을 참조하십시오.

예제: 스키마, 데이터베이스, 구성

OpenLDAP의 .schema 형식으로 작성한 스키마입니다. 소스가 선언할 수 있는 클래스 하나(exampleStaff, AUXILIARY, MUST 있음)와 선언할 수 없는 클래스 하나(exampleUnit, STRUCTURAL)가 있습니다.

objectidentifier exampleRoot  1.3.6.1.4.1.99999
objectidentifier exampleAttr  exampleRoot:1
objectidentifier exampleClass exampleRoot:2

attributetype ( exampleAttr:1 NAME 'exampleBadge'
	DESC 'the number on a badge'
	EQUALITY caseIgnoreMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

attributetype ( exampleAttr:2 NAME 'exampleEmployeeId'
	DESC 'a staff number'
	EQUALITY caseExactMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

# AUXILIARY: it can be declared. exampleStaff has a MUST.
objectclass ( exampleClass:1 NAME 'exampleStaff' SUP top AUXILIARY
	DESC 'somebody employed: has a staff number'
	MUST exampleEmployeeId
	MAY exampleBadge )

# STRUCTURAL: it cannot be declared (an entry has one structural chain).
objectclass ( exampleClass:2 NAME 'exampleUnit' SUP top STRUCTURAL
	MUST cn )

sn, 배지, 직원 번호를 가진 세 사람의 SQLite 데이터베이스입니다(sqlite3 var/people.db < people.sql).

create table staff (login text primary key, secret text);
create table person_attrs (login text primary key, sn text, badge text, empid text, locker text);
insert into staff values ('ann', 'ann-password'), ('ben', 'ben-password'), ('cat', 'cat-password');
insert into person_attrs values ('ann', 'Archer', 'B-0001', 'E-1001', 'L-12'), ('ben', 'Brook', 'B-0002', null, null), ('cat', 'Cole', null, 'E-1003', null);

그리고 구성입니다.

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

# Files first, then the blocks: a definition may use anything before it.
schema_files = ["etc/authnd/example.schema"]

schema {
  attribute_type "exampleLocker" {
    oid    = "1.3.6.1.4.1.99999.1.3"
    syntax = "1.3.6.1.4.1.1466.115.121.1.15"
  }
  object_class "exampleLockerHolder" {
    oid  = "1.3.6.1.4.1.99999.2.3"
    kind = "auxiliary"
    may  = ["exampleLocker"]
  }
}

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret from staff"
  users_attributes = "select login, sn, badge as exampleBadge, empid as exampleEmployeeId, locker as exampleLocker from person_attrs"
  object_classes   = ["exampleStaff", "exampleLockerHolder"]   # declared, never inferred
}

schema_files

schema_files는 OpenLDAP .schema 파일 또는 cn=config LDIF 파일의 목록입니다.이 파일들은 표준 스키마(그리고 samba 블록을 쓰는 경우 Samba의 정의 세 개) 위에 게시된 그대로 순서대로 로드되며,go-authn/ldap의 slapd 호환 리더가 읽습니다. 용어의 순서는 자유이고, slapd와 RFC 2849 연속 줄, base64, {N} 길이 접두사, 그리고 한 파일이 정의하고 다음 파일이 사용할 수 있는 objectidentifier 매크로(slapd의 include를 가로지르는 것과 같습니다)를 지원합니다. 미리 변환하는 것은 없으므로, 사이트의 slapd가 로드하는 파일이 곧 authnd가 로드하는 파일입니다. 정의는cn=Subschema에서 제공됩니다.

  • 상대 경로는 구성의 다른 모든 경로와 마찬가지로 작업 디렉터리를 기준으로 합니다.서비스에서는 절대 경로를 사용하십시오. systemd 유닛의 작업 디렉터리는 /입니다.

  • 각 파일은 최대 4 MiB의 일반 파일이어야 하며, 시작 시 한 번 읽습니다.

  • 파일은 모든 엔트리가 가질 수 있는 것을 결정합니다. 비밀은 아니지만 나머지 구성과 함께 보관하십시오. root:authnd, 모드 0640, root만 쓸 수 있는 디렉터리입니다(설치).

  • 빌드되지 않는 파일은 시작과 check를 거부하며, 파일, 정의가 시작되는 줄과 열, 그리고 메시지 끝에 거부의 종류를 알려 줍니다. 알 수 없는 상위 클래스, 속성,매칭 규칙 또는 구문(unknown reference), AUXILIARY 클래스에서 파생된 STRUCTURAL 클래스(kind violation), 두 번 정의된 OID 또는 이름(duplicate OID,duplicate name)이 그 예입니다. v0.12.1부터 위치와 종류는 메시지를 읽어서가 아니라 go-authn/ldap의 타입이 있는*schema.BuildError에서 옵니다.파일에서 읽은 정의는 여러 줄에 걸쳐 접혀 있어도 1열에서 시작합니다. 중복은 첫 번째 정의가 어디 있는지 알려 주고, 재정의는 원본이 어느 표준 파일에, 또는 앞선 파일의 어느 줄에 있는지 알려 줍니다. 두 가지 예입니다.

    cases/unknown.schema에는 어디에도 정의되지 않은 MAY가 있습니다.

    # exampleB has a MAY that is defined nowhere.
objectclass ( 1.3.6.1.4.1.99999.2.9 NAME 'exampleB' SUP top AUXILIARY
	MAY noSuchAttribute )
    $ authnd check cases/unknown.hcl
authnd: schema_files: cases/unknown.schema:2:1: the object class exampleB has MAY noSuchAttribute, which is not a defined attribute type (unknown reference)

    cases/twice.schema는 하나의 OID를 두 속성 타입에 부여합니다.

    attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleA'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )

attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleB'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )
    $ authnd check cases/twice.hcl
authnd: schema_files: cases/twice.schema:4:1: the attribute type 1.3.6.1.4.1.99999.1.9 is defined twice (first defined at cases/twice.schema:1:1) (duplicate OID)

재정의는 동일하더라도 거부됩니다

파일은 이미 있는 것을 정의할 수 없습니다. 표준 스키마의 정의, Samba의 정의, 앞선 파일의 정의가 그렇습니다. 한 글자도 다르지 않더라도 거부되며, 이는 slapd 자신의 규칙입니다. 스키마 파일의 정의는 parse_at과 parse_oc를 거치고, slapd는 이미 색인된 OID나 이름에 대해 Duplicate attributeType(OID와 이름이 같은 경우) 또는Inconsistent duplicate attributeType으로 답합니다(servers/slapd/at.c, oc.c).앞의 것은 slapd 자신의 하드코딩된 스키마에만 허용됩니다. slapd가 거부하는 파일은 authnd도 거부합니다.

다른 해석이라면 승자를 골라야 하는데, 그것은 모든 클라이언트가 표준 속성에 대해 듣는 내용을 조용히 바꾸는 일입니다. 거부하면 해당 줄을 알려 줄 수 있습니다. 거부 메시지는 텍스트가 같았는지도 알려 줍니다. cn(2.5.4.3)을 자체 정의로 재정의하는 파일은 다음과 같습니다.

$ authnd check cases/dup.hcl
authnd: schema_files: cases/cn-copy.schema:1:1: the attribute type cn (2.5.4.3) is already defined by the standard schema (rfc4519.schema:42:1), and this is a different definition: a schema file adds definitions and never replaces one -- slapd refuses this too ("Duplicate attributeType", servers/slapd/at.c and oc.c). Remove it from this file

schema { } 블록

로컬에서만 쓰는 정의를 위해, schema 블록은 이를 HCL2로hclschema의 형태에 맞춰 담습니다. attribute_type, object_class, object_identifier, matching_rule,ldap_syntax입니다. 파일 뒤에 읽히므로 파일의 정의를 사용할 수 있으며, 여러 개를 둘 수 있습니다.

값은 리터럴이어야 합니다. 변수도, 함수도, ${...}나 %{...}도 안 됩니다. 블록은.hcl 스키마 파일을 읽는 것과 같은 디코더로, 같은 한도로 디코딩되며, 모든 오류는 구성 자체의 줄과 열을 알려 줍니다. HCL의 네이티브 구문이 아닌 블록은 거부됩니다.

object_classes

스키마의 정의는 속성을 허용할 뿐이며, 클래스를 누군가에게 붙이지는 않습니다. 소스는 자신의 사람과 그룹이 함께 게시되는 보조 클래스를 선언합니다.

위치키선언하는 것
users 블록, 모든 종류object_classes블록이 제공하는 모든 사람의 클래스
users 블록, 모든 종류group_object_classes모든 그룹의 클래스
user 블록object_classes그 사람의 클래스
group 블록object_classes그 그룹의 클래스
users "sql" {
  # ...
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

user  "alice" { object_classes = ["siteMember"] }
group "staff" { object_classes = ["supannGroupe"] }

이 키들은 v0.15.0부터의 go-authn/directory의 것입니다(라이브러리). 이름은 대소문자를 무시하고 비교되며, 쓴 순서대로 한 번씩만 유지됩니다.

authnd가 선언된 클래스로 하는 일은 다음과 같습니다.

  • 상위 클래스와 함께 게시됩니다. authnd가 도출하는 클래스 뒤에 옵니다(RFC 4512§3.3: 지정된 클래스의 모든 상위 클래스가 암묵적으로 추가됨). 클래스가 허용하는 속성은 제외되지 않고 유지됩니다.
  • 결코 추론되지 않습니다. 소스가 아무것도 선언하지 않는 사람은, 데이터베이스에 무엇이 있든 자신의 어떤 클래스도 허용하지 않는 속성을 계속 잃습니다.
  • 선언된 클래스의 MUST가 없는 사람은 그 클래스 없이 게시됩니다. 그 속성은 어떤 클래스도 허용하지 않는 속성처럼 제외되며, 둘 다 보고됩니다. 이것이 authnd가 어디서나 따르는 규칙입니다. 사람은 계속 게시되고, 문제는 알려지며, 아무것도 조용히 바뀌지 않습니다. 속성 하나가 없다고 사람을 보류하면 그 사람이 모든 검색에서 빠지게 되고,MUST 없이 클래스를 게시하면 제공하는 스키마를 통과하지 못하는 엔트리를 제공하게 됩니다.
  • 두 소스가 한 그룹에 대해 서로 다른 클래스를 선언할 수 있습니다. 그룹의 클래스를 처음 선언하는 소스가 전체를 결정하고, 이후의 목록은 병합되지도 오류가 되지도 않고 무시됩니다. check가 이를 알려 줍니다.

거부되는 것과 그 이유

선언된 클래스는 시작 시, 그리고 check에서 제공하는 스키마와 대조해 검사됩니다.다음을 만족해야 합니다.

  • 표준 스키마, 파일 또는 블록에 의해 정의되어 있을 것
  • AUXILIARY일 것(RFC 4512 §4.1.1). 엔트리에는 정확히 하나의 구조 체인이 있으며(§2.4.2), 이는 사람이 가진 것을 보고 authnd가 고릅니다. 선언으로 두 번째 체인을 추가할 수는 없습니다.
  • authnd가 스스로 도출하는 클래스가 아닐 것: account, inetOrgPerson과 그 상위 클래스, posixAccount, posixGroup, ldapPublicKey, uidObject,sambaSamAccount, groupOfNames, organizationalRole이며, 어떤 이름으로 쓰든 마찬가지입니다. 이것들은 사람이나 그룹이 가진 것으로부터 정해지며, 선언이 check를 뒤집을 수는 없습니다.

그렇지 않으면 시작이 거부되며, 블록과 그 위치와 클래스를 알려 줍니다.exampleUnit은 STRUCTURAL입니다.

$ authnd check cases/structural.hcl
authnd: cases/structural.hcl:10:20: users "sql" object_classes: exampleUnit is STRUCTURAL, and an entry has exactly one structural chain (RFC 4512 §2.4.2), which authnd chooses: only an AUXILIARY class (§4.1.1) can be declared

go-authn/directory는 그에 앞서 철자를 검사합니다. 클래스는 디스크립터이며, OID도,공백도, 따옴표도, 괄호도 아닙니다.

스키마의 정직함을 지키려는 같은 이유로 다음도 거부됩니다.

거부되는 것이유
정의를 재정의하는 파일, 한 글자도 다르지 않더라도slapd의 규칙: 위
일반 파일이 아니거나 4 MiB를 넘는 파일FIFO는 시작을 막고, /dev/zero는 끝나지 않음
변수, 함수 또는 ${...}가 있는 schema 블록.hcl 스키마 파일처럼 리터럴 값만
object_classes의 정의되지 않은 클래스아무것도 검사할 수 없는 약속
STRUCTURAL 클래스, 또는 authnd가 도출하는 클래스위의 목록

check가 출력하는 것

평소의 줄 위에 네 종류의 줄이 더해지며, 시작 로그에도 같은 줄이 나옵니다.

  • **schema: <file> adds …**와 schema: the schema block at <file>:<line>:<column> adds …:각 파일과 각 블록이 추가한 것을 오브젝트 식별자 매크로, 속성 타입, 오브젝트 클래스로 센 것
  • <file>:<line>:<column>: users "sql" declares … for its people(user 또는group 블록은 user "ann" declares … for this person, group "staff" declares … for this group이라고 함): 각 소스가 선언하는 것
  • <name> is published without <class>, which its source declares: …: 그 사람에게 없는 MUST를 지정함
  • group staff: the configuration file declares supannGroupe and a postgres database declares eduMember; the first is published and the second is ignored (the first source that declares classes for a group decides):그룹에 대해 두 소스가 일치하지 않는 경우이며, 그렇지 않으면 조용히 지나갈 것입니다.

클래스가 없어서 제외된 속성은 is published without <attribute>: no class of the entry allows it; <classes> would 줄이며엔트리가 이미 설명한 것입니다. 선언이 있으면 이 줄은 아직 선언하지 않은 클래스를 알려 줍니다.

DIT 콘텐츠 규칙, 이름 형식, DIT 구조 규칙

v0.13.0부터 schema_files와 schema { } 블록은 RFC 4512 §4.1.6과 §4.1.7이 클래스와 속성에 더하는 세 종류의 정의도 받아들이며, authnd는 이를 적용합니다 (go-authn/ldap v0.11.0이 이를 읽고, 빌드하고, 검사합니다.라이브러리 페이지에 방법이 있습니다).

정의RFC 4512내용authnd가 하는 일
DIT 콘텐츠 규칙§4.1.6구조 클래스 하나에 대해: 추가할 수 있는 보조 클래스(AUX), 필수(MUST), 허용(MAY), 금지(NOT) 속성각 엔트리의 형태를 정함(데이터)
이름 형식§4.1.7.2구조 클래스의 엔트리를 이름 짓는 속성(RDN)은 무엇인가트리를 지킴(구성)
DIT 구조 규칙§4.1.7.1이름 형식을 어디에 놓을 수 있는가: SUP이 지정하는 규칙이 다스리는 엔트리 아래트리를 지킴(구성)

이들은 있을 때만 cn=Subschema(dITContentRules, nameForms,dITStructureRules)에 게시됩니다. 하나도 없으면 이 페이지의 어떤 내용도 적용되지 않으며, v0.12.4와 달라지는 것이 없습니다.

같은 예제 아크

아래의 rules.schema는 위의 example.schema처럼 이 페이지를 위해 작성했으며1.3.6.1.4.1.99999 아래에 있습니다. 여러분의 아크를 사용하십시오. 콘텐츠 규칙의 OID와 inetOrgPerson의 OID는 정의상 같습니다. 콘텐츠 규칙은 그것이 대상으로 하는 구조 클래스의 이름을 따르기 때문입니다.

각각 하나씩 있는 스키마와 그 HCL

OpenLDAP의 .schema 형식입니다. ditcontentrule은 slapd.conf(5)의 지시어이고,nameform과 ditstructurerule은 slapd에 없어서 go-authn/ldap의 것입니다(아래). authnd는 게시하는 트리(접미사, ou=people, ou=groups, 그 아래의 계정, 사람, 그룹)도 검사하므로, 파일에는 각각 하나가 아니라 이름 형식 다섯 개와 구조 규칙 다섯 개가 있습니다.

# Rules for the tree authnd publishes. 1.3.6.1.4.1.99999 is an example arc:
# nobody is assigned it, use your own.

# A content rule belongs to a structural class and takes that class's OID.
# inetOrgPerson (2.16.840.1.113730.3.2.2): posixAccount and uidObject may be
# added, ldapPublicKey may not; telephoneNumber is required; description is
# precluded.
ditcontentrule ( 2.16.840.1.113730.3.2.2 NAME 'examplePersonRule'
	AUX ( posixAccount $ uidObject )
	MUST telephoneNumber
	NOT description )

# A name form says which attribute names an entry of a structural class.
nameform ( 1.3.6.1.4.1.99999.9.1 NAME 'exampleDomainForm' OC domain MUST dc )
nameform ( 1.3.6.1.4.1.99999.9.2 NAME 'exampleUnitForm' OC organizationalUnit MUST ou )
nameform ( 1.3.6.1.4.1.99999.9.3 NAME 'exampleAccountForm' OC account MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.4 NAME 'examplePersonForm' OC inetOrgPerson MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.5 NAME 'examplePosixGroupForm' OC posixGroup MUST cn )

# A structure rule gives a name form a place: the rule ID is a number, SUP
# names the rule of the parent entry.
ditstructurerule ( 1 NAME 'exampleSuffix' FORM exampleDomainForm )
ditstructurerule ( 2 NAME 'exampleUnit' FORM exampleUnitForm SUP 1 )
ditstructurerule ( 3 NAME 'exampleAccounts' FORM exampleAccountForm SUP 2 )
ditstructurerule ( 4 NAME 'examplePersons' FORM examplePersonForm SUP 2 )
ditstructurerule ( 5 NAME 'examplePosixGroups' FORM examplePosixGroupForm SUP 2 )

같은 정의를 ldapschema v0.11.0이 쓰는 HCL로 나타낸 것입니다(ldapschema to-hcl rules.schema). 블록 하나가 정의 하나이며 첫 번째 NAME이 레이블입니다. 구조 규칙에는 id, 그것이 배치하는 form, 그리고 그 아래에 놓이는sup 규칙이 있습니다.

dit_content_rule "examplePersonRule" {
  oid  = "2.16.840.1.113730.3.2.2"
  aux  = ["posixAccount", "uidObject"]
  must = ["telephoneNumber"]
  not  = ["description"]
}

name_form "exampleDomainForm" {
  oid  = "1.3.6.1.4.1.99999.9.1"
  oc   = "domain"
  must = ["dc"]
}

name_form "exampleUnitForm" {
  oid  = "1.3.6.1.4.1.99999.9.2"
  oc   = "organizationalUnit"
  must = ["ou"]
}

name_form "exampleAccountForm" {
  oid  = "1.3.6.1.4.1.99999.9.3"
  oc   = "account"
  must = ["uid"]
}

name_form "examplePersonForm" {
  oid  = "1.3.6.1.4.1.99999.9.4"
  oc   = "inetOrgPerson"
  must = ["uid"]
}

name_form "examplePosixGroupForm" {
  oid  = "1.3.6.1.4.1.99999.9.5"
  oc   = "posixGroup"
  must = ["cn"]
}

dit_structure_rule "exampleSuffix" {
  id   = 1
  form = "exampleDomainForm"
}

dit_structure_rule "exampleUnit" {
  id   = 2
  form = "exampleUnitForm"
  sup  = [1]
}

dit_structure_rule "exampleAccounts" {
  id   = 3
  form = "exampleAccountForm"
  sup  = [2]
}

dit_structure_rule "examplePersons" {
  id   = 4
  form = "examplePersonForm"
  sup  = [2]
}

dit_structure_rule "examplePosixGroups" {
  id   = 5
  form = "examplePosixGroupForm"
  sup  = [2]
}

이것이 schema { } 블록 안에 그대로 들어가는 내용이며, .schema 파일은schema_files가 받는 것입니다. ldapschema to-schema rules.hcl은 이를 같은 정의의.schema 파일로 되돌리고, ldapschema check는 표준 스키마 위에 이를 빌드합니다.

콘텐츠 규칙이 엔트리에 하는 일

구성은 사람 둘과 그룹 둘이며, 규칙은 schema_files에서 불러옵니다. dave에게는sn(그래서 inetOrgPerson), 전화번호, 설명, SSH 공개 키가 있고, erin에게는sn만 있고 다른 것은 없으며, staff에게는 gidNumber가 있고, team에게는 없습니다.

규칙의 내용엔트리표시
AUX가 보조 클래스를 나열하지 않음. 선언된 것이든 authnd가 파생한 것(posixAccount, ldapPublicKey, sambaSamAccount, uidObject)이든 마찬가지그 클래스는 그것만 허용하던 속성(그리고 authnd가 그 클래스를 위해 추가했을 sshPublicKey, sambaSID, sambaNTPassword)과 함께 빠집니다. 상위 클래스가 빠진 선언된 클래스도 함께 빠집니다<name> is published without <class>: the DIT content rule <rule> does not allow it (not in its AUX)
NOT이 속성을 지정함그 속성은 누가 주었든 제거됩니다<name> is published without <attribute>: the DIT content rule <rule> precludes it (NOT)
MUST가 엔트리에 없는 속성을 지정함그 엔트리는 제외됩니다. 규칙은 엔트리 전체에 적용되며, 클래스를 빼서 유효하게 만들 수는 없습니다<name> is NOT published: … <attribute> is required by the DIT content rule <rule> and is missing (RFC 4512 4.1.6)

$ ldapsearch -x -LLL -o ldif-wrap=no -H ldap://127.0.0.1:3893 -D cn=reader,dc=example,dc=org -y reader.pwin -b dc=example,dc=org '(|(uid=*)(cn=*))' dn objectClass description sshPublicKey

구조 규칙이 트리에 하는 일

활성 DIT 구조 규칙이 하나 이상 있으면, authnd는 게시할 트리를 시작할 때와check에서 훑어봅니다.

  • 접미사(base_dn)는 그 RDN이 지정하는 클래스로 봅니다. dc는 domain, o는organization, ou는 organizationalUnit, c는 country, l은 locality입니다.다른 속성으로 이름 지은 접미사는 거부됩니다.
  • ou=people과 ou=groups는 organizationalUnit으로 봅니다.
  • authnd가 사람을 이름 짓는 RDN 속성(uid)과 그룹을 이름 짓는 속성(cn).

어떤 규칙도 자리를 주지 않는 컨테이너, 이름 형식을 가진 규칙이 하나도 없는 종류의 접미사, uid나 cn을 거부하는 이름 형식, 또는 authnd가 게시하는 어떤 것도 놓일 수 없는 컨테이너는 시작을 거부하며, check도 마찬가지입니다. 모든 거부가 한꺼번에 DN, 규칙 또는 이름 형식, 조항을 밝히며 보고되고, 비밀 값은 절대 출력되지 않습니다.구조 클래스가 데이터(sn, gidNumber)에 달려 있고 그 컨테이너 아래에 규칙이 없는 사람이나 그룹은 대신 제외되고 알려집니다. 위의 team처럼 서버는 시작됩니다.활성 구조 규칙이 없으면 달라지는 것이 없습니다.

사람을 위한 유일한 구조 규칙 peopleByCN이 cn을 요구하는 이름 형식(accountByCN:OC account MUST cn)을 배치하는 스키마입니다.

$ authnd check cases/bad.hcl
authnd: DIT structure rules: authnd names its people uid=<name>,ou=people,dc=example,dc=org, and an account named so is refused: the RDN (uid) is allowed by the name form of no DIT structure rule that places account under an entry governed by the rule 2: accountByCN needs cn

authnd는 사람을 uid=<name>으로 이름 짓습니다. 규칙이 이를 허용해야 합니다. 그리고organizationalUnit의 규칙에 SUP이 없어서 organizationalUnit이 루트에만 있을 수 있는 스키마는 ou=people과 ou=groups 둘 다 자리가 없게 되며, 둘을 한꺼번에 알립니다.

$ authnd check cases/root.hcl
authnd: DIT structure rules: ou=people,dc=example,dc=org, where authnd publishes its people, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)
DIT structure rules: ou=groups,dc=example,dc=org, where authnd publishes its groups, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)

둘 다 종료 상태 1로 끝납니다. 그 뒤의 파일(cases/bad.schema와cases/root.schema)에는 같은 이름 형식 다섯 개와, 요점을 보여 주는 구조 규칙만 들어 있습니다.

authnd와 slapd가 다른 점

go-authn/ldap은 OpenLDAP 파일을 읽으며, 규칙의 일부는 OpenLDAP의 것입니다. 차이는 발견하게 두지 않고 밝혀 둡니다.

  • slapd는 콘텐츠 규칙만 구현합니다. 이름 형식이나 구조 규칙을 위한 지시어가 없습니다. Format은 이 라이브러리의 것인 nameform과 ditstructurerule 키워드를 쓰며 slapd는 이를 거부합니다. 이들은 HCL에 두거나 authnd만 읽는 파일에 두십시오.ditcontentrule은 slapd의 것입니다.
  • OBSOLETE 규칙은 비활성입니다(RFC 4512 §4.1.6). 그 이름 형식이나 구조 규칙도 마찬가지입니다. slapd는 대신 엔트리를 거부합니다.
  • 콘텐츠 규칙이 없으면 보조 클래스가 허용됩니다. 이것이 slapd의 동작이며(그SLAP_DISALLOW_AUX_WO_CR 플래그는 어떤 disallow 키워드로도 설정되지 않습니다)authnd의 동작이기도 합니다. RFC 4512 §2.4.3은 다르게 말하며, 라이브러리는 이를ValidateOptions{StrictAuxiliary: true}로 제공하고 authnd는 이를 설정하지 않습니다.
  • libldap은 구조 규칙의 SUP을 읽지 못합니다. SUP이 있는 구조 규칙은 여기서는 읽히지만 libldap에서는 읽히지 않으므로, 그런 파일에 대한 libldap의 거부는 파일에 대한 판정이 아닙니다.
  • 규칙을 재정의하는 파일은 다른 모든 정의처럼 글자 그대로 같더라도 거부됩니다(위).

비용

2026-10-30에 go-authn/ldap v0.11.3을 내장한 authnd v0.13.3에서BenchmarkPublish10k(go-authn/authnd, rules_bench_test.go, -cpu 1)로 측정했습니다. 사람 10,000명을 게시할 때 testdata/rules.schema의 규칙이 있으면엔트리당 할당 97회, 없으면 69회입니다(v0.13.2는 128회와 85회, v0.13.0은 416회와 265회). 한 번 실행에 쓰는 메모리는 규칙이 있으면 42.6 MiB, 없으면 25.7 MiB입니다(v0.13.2는 54.8 MiB와 33.7 MiB, v0.13.0은 147.5 MiB와 88.0 MiB). 여기에는 금지된 설명을 제거하고 다시 검증하는 것이 포함됩니다. 시간은 약 66 ms 대 36 ms이며 부하 4.8에서 번갈아 다섯 번 실행한 중앙값입니다. 규칙이 있으면 여전히 약 1.8배가 듭니다.설명을 제거하느라 필요한 두 번째 검증과 구조 규칙이 DN을 다시 읽는 것은 원인을 밝혀낸 차이 가운데 큰 부분에 속합니다.

업그레이드

규칙이 없는 스키마는 달라지는 것이 없습니다. v0.12.4는 세 종류를 모두 거부했으므로 그 버전에서 시작된 구성에는 규칙이 없습니다. 예외가 하나 있습니다. UTF-8이 아닌 schema { } 문자열(HCL이 통과시키는 과도한 인코딩)은 v0.12.4에서 시작되었지만 이제는 거부됩니다. 쓰인 그대로는 게시할 수 없기 때문입니다.

실제 예제로서의 SUPANN

SUPANN은 프랑스 고등 교육 및 연구 기관의 속성 집합(supannPerson,supannEtablissement, supannEntite…)이며, eduPerson이 곁에 있습니다. RENATER는 다른 것들과 함께 기술 스키마를 문서 페이지에 게시합니다.

https://services.renater.fr/documentation/supann/supann2021/recommandations/tables_references/schemas_techniques_supann

파일은 거기서 내려받으십시오. 이 사이트에는 복제하지 않습니다. 라이선스를 명시하고 있지 않으므로 이 페이지는 복사하지 않으며, 여기의 사본은 RENATER가 개정하면 낡아 버립니다. 그다음:

sudo install -o root -g authnd -m 0640 supann.schema eduperson.ldif /etc/authnd/
schema_files = ["/etc/authnd/supann.schema", "/etc/authnd/eduperson.ldif"]

users "sql" {
  # ...
  users_attributes     = "select login, sn, etab as \"supannEtablissement\" from staff"
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

authnd check를 실행하고 먼저 schema: 줄을 읽으십시오. slapd가 로드하는 파일은 여기서도 로드되며, 표준 정의를 재정의하는 파일은 그 줄과 함께 거부됩니다. 그다음 published without 줄을 읽으십시오. supannPerson이나 eduPerson의 MUST가 없는 사람은 그 클래스 없이 게시되며, check가 그 MUST를 알려 줍니다. 철자가 중요한 곳에서는 별칭에 따옴표를 쓰십시오(PostgreSQL은 따옴표 없는 별칭을 소문자로 바꿉니다.엔트리를 참조).

트랜스크립트에 대하여

이 페이지의 모든 명령은 2026-10-26에 v0.12.3 릴리스 바이너리(authnd-darwin-arm64, SHA256SUMS와 대조함; go version -m: go1.27.3, mod github.com/go-authn/authnd v0.12.3, vcs.modified=false)와 OpenLDAP의 ldapsearch로, 127.0.0.1에서 임시 디렉터리에 보여 준 파일을 두고 다시 실행한 것입니다. 경로가 상대 경로인 것은 그 때문이며, 서비스에서는 절대 경로를 사용합니다. 스키마는 이 페이지를 위해 작성한 예제입니다.

DIT 콘텐츠 규칙, 이름 형식, DIT 구조 규칙 절은 2026-10-26에 v0.13.0 릴리스 바이너리(authnd-darwin-arm64, relverify로 SHA256SUMS 및 그 증명과 대조함; go version -m: go1.27.3, mod github.com/go-authn/authnd v0.13.0; authnd --version: authnd version v0.13.0), OpenLDAP의 ldapsearch, 그리고 go-authn/ldap v0.11.0 태그로 빌드한 ldapschema(go install, go1.27.1, 릴리스 바이너리 없음)로 실행했습니다. 그곳의 모든 출력은 이 프로그램들이 127.0.0.1에서 임시 디렉터리에 출력한 것이며, 트랜스크립트 뒤의 파일은 그 옆에 보여 주거나 설명해 두었습니다.
