Site schemas

Site schemas, and the classes a source declares

Serve SUPANN, eduPerson or a site's own attributes: schema_files and the schema block add definitions, object_classes declares which auxiliary classes a source's people and groups carry, and check says what was left off. From v0.13.0, DIT content rules, name forms and DIT structure rules are enforced.

A SUPANN or eduPerson attribute is dropped unless a class of its entry allows it. authnd publishes only what the schema it serves permits (seethe entries),and the standard schema knows nothing of supannEtablissement oreduPersonAffiliation. From v0.12.0 a site says three things, in this order:

  1. which definitions to add: schema_files, the files its slapd already loads, and a schema { } block for what is only local;
  2. which auxiliary classes its people and groups carry: object_classes;
  3. nothing else. A class is declared, never inferred: an attribute appearing in a database does not change what an entry is published as.

The example on this page is an example

example.schema below was written for this page. Its OIDs are under1.3.6.1.4.1.99999, an arc nobody is assigned: use your own, and never copy these. For SUPANN, see the end of the page.

An example: a schema, a database, a configuration

A schema in OpenLDAP’s .schema form: one class a source can declare(exampleStaff, AUXILIARY, with a MUST), and one it cannot(exampleUnit, STRUCTURAL).

objectidentifier exampleRoot  1.3.6.1.4.1.99999
objectidentifier exampleAttr  exampleRoot:1
objectidentifier exampleClass exampleRoot:2

attributetype ( exampleAttr:1 NAME 'exampleBadge'
	DESC 'the number on a badge'
	EQUALITY caseIgnoreMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

attributetype ( exampleAttr:2 NAME 'exampleEmployeeId'
	DESC 'a staff number'
	EQUALITY caseExactMatch
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15
	SINGLE-VALUE )

# AUXILIARY: it can be declared. exampleStaff has a MUST.
objectclass ( exampleClass:1 NAME 'exampleStaff' SUP top AUXILIARY
	DESC 'somebody employed: has a staff number'
	MUST exampleEmployeeId
	MAY exampleBadge )

# STRUCTURAL: it cannot be declared (an entry has one structural chain).
objectclass ( exampleClass:2 NAME 'exampleUnit' SUP top STRUCTURAL
	MUST cn )

A SQLite database of three people, with sn, a badge and a staff number(sqlite3 var/people.db < people.sql):

create table staff (login text primary key, secret text);
create table person_attrs (login text primary key, sn text, badge text, empid text, locker text);
insert into staff values ('ann', 'ann-password'), ('ben', 'ben-password'), ('cat', 'cat-password');
insert into person_attrs values ('ann', 'Archer', 'B-0001', 'E-1001', 'L-12'), ('ben', 'Brook', 'B-0002', null, null), ('cat', 'Cole', null, 'E-1003', null);

And the configuration:

listen  = "127.0.0.1:3893"
base_dn = "dc=example,dc=org"

reader "cn=reader,dc=example,dc=org" { password_file = "etc/authnd/reader.pw" }

# Files first, then the blocks: a definition may use anything before it.
schema_files = ["etc/authnd/example.schema"]

schema {
  attribute_type "exampleLocker" {
    oid    = "1.3.6.1.4.1.99999.1.3"
    syntax = "1.3.6.1.4.1.1466.115.121.1.15"
  }
  object_class "exampleLockerHolder" {
    oid  = "1.3.6.1.4.1.99999.2.3"
    kind = "auxiliary"
    may  = ["exampleLocker"]
  }
}

users "sql" {
  driver   = "sqlite"
  dsn_file = "etc/authnd/people.dsn"
  users    = "select login, secret from staff"
  users_attributes = "select login, sn, badge as exampleBadge, empid as exampleEmployeeId, locker as exampleLocker from person_attrs"
  object_classes   = ["exampleStaff", "exampleLockerHolder"]   # declared, never inferred
}

schema_files

schema_files is a list of OpenLDAP .schema files or cn=config LDIF files.They are loaded as published, in order, on top of the standard schema (and Samba’s three definitions, with the samba block), by go-authn/ldap’s slapd-compatible readers:any order of terms, slapd and RFC 2849 continuations, base64, {N} length prefixes, and objectidentifier macros, which one file may define and the next use, as across slapd’s include. Nothing is converted beforehand, so the file a site’s slapd loads is the file authnd loads. The definitions are served atcn=Subschema.

  • A relative path is relative to the working directory, as every other path in the configuration is. Use absolute paths in a service: the working directory of a systemd unit is /.

  • Each file must be a regular file of at most 4 MiB, and is read once, at startup.

  • The files decide what every entry may hold. They are not secrets, but keep them with the rest of the configuration: root:authnd, mode 0640, in a directory only root writes (install).

  • A file that does not build refuses startup, and check, with the file, the line and the column where the definition starts, and the kind of refusal at the end of the message: an unknown superclass, attribute, matching rule or syntax (unknown reference), a structural class derived from an auxiliary one (kind violation), an OID or a name defined twice (duplicate OID,duplicate name). Since v0.12.1 the place and the kind come from go-authn/ldap’s typed*schema.BuildError, not from reading its message. A definition read from a file starts at column 1,also when its text is folded over several lines. A duplicate says where its first definition is, and a redefinition says which standard file, or which line of an earlier file, holds the original. Two examples:

    cases/unknown.schema has a MAY that is defined nowhere:

    # exampleB has a MAY that is defined nowhere.
objectclass ( 1.3.6.1.4.1.99999.2.9 NAME 'exampleB' SUP top AUXILIARY
	MAY noSuchAttribute )
    $ authnd check cases/unknown.hcl
authnd: schema_files: cases/unknown.schema:2:1: the object class exampleB has MAY noSuchAttribute, which is not a defined attribute type (unknown reference)

    cases/twice.schema gives one OID to two attribute types:

    attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleA'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )

attributetype ( 1.3.6.1.4.1.99999.1.9 NAME 'exampleB'
	SYNTAX 1.3.6.1.4.1.1466.115.121.1.15 )
    $ authnd check cases/twice.hcl
authnd: schema_files: cases/twice.schema:4:1: the attribute type 1.3.6.1.4.1.99999.1.9 is defined twice (first defined at cases/twice.schema:1:1) (duplicate OID)

A redefinition is refused, even an identical one

A file may not define what is already there: the standard schema’s definitions, Samba’s, or an earlier file’s. It is refused even word for word, which is slapd’s own rule: a schema file’s definitions go throughparse_at and parse_oc, and slapd answers an OID or a name already indexed with Duplicate attributeType (same OID and names) or Inconsistent duplicate attributeType (servers/slapd/at.c, oc.c). Only slapd’s own hard-coded schema is allowed the first. A file slapd refuses is a file authnd refuses.

The other reading would have to pick a winner, and that is a silent change to what every client is told a standard attribute is; refusing names the line instead. The refusal says whether the text was the same. A file that redefines cn (2.5.4.3) with a definition of its own:

$ authnd check cases/dup.hcl
authnd: schema_files: cases/cn-copy.schema:1:1: the attribute type cn (2.5.4.3) is already defined by the standard schema (rfc4519.schema:42:1), and this is a different definition: a schema file adds definitions and never replaces one -- slapd refuses this too ("Duplicate attributeType", servers/slapd/at.c and oc.c). Remove it from this file

The schema { } block

For definitions that are only local, a schema block holds them in HCL2, in hclschema’s shape:attribute_type, object_class, object_identifier, matching_rule andldap_syntax. It is read after the files, so it may use their definitions, and there may be several.

Values must be literals: no variables, no functions, no ${...} or%{...}. The block is decoded by the same decoder that reads an .hcl schema file, with the same bounds, and every error names the configuration’s own line and column. A block that is not in HCL’s native syntax is refused.

object_classes

A definition in the schema allows an attribute; it does not put the class on anybody. A source declares the auxiliary classes its people and groups are published with:

wherekeywhat it declares
users block, any kindobject_classesthe classes of every person the block gives
users block, any kindgroup_object_classesthe classes of every group
user blockobject_classesthe classes of that person
group blockobject_classesthe classes of that group
users "sql" {
  # ...
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

user  "alice" { object_classes = ["siteMember"] }
group "staff" { object_classes = ["supannGroupe"] }

These keys are go-authn/directory’s, from v0.15.0(library). Names are compared ignoring case, and kept once, in the order written.

What authnd does with a declared class:

  • It is published with its superclasses, after the classes authnd derives(RFC 4512 §3.3: all the superclasses of the named classes are implicitly added). The attributes the class allows are kept instead of dropped.
  • It is never inferred. A person whose source declares nothing keeps losing the attributes no class of theirs allows, whatever the database holds.
  • A person missing a MUST of a declared class is published without that class. Its attributes are dropped like any attribute no class allows, and both are reported. That is the rule authnd follows everywhere: the person stays published, the problem is said, nothing is changed silently.Withholding the person would take them out of every search for one missing attribute; publishing the class without its MUST would serve an entry that fails the schema served.
  • Two sources may declare different classes for one group. The first source that declares classes for a group decides, whole, and a later list is ignored: neither merged nor an error. check says so.

What is refused, and why

A declared class is checked at startup, and by check, against the schema served. It must be:

  • defined, by the standard schema, a file or a block;
  • AUXILIARY (RFC 4512 §4.1.1). An entry has exactly one structural chain(§2.4.2), which authnd chooses from what the person has; a declaration cannot add a second one;
  • not one authnd derives itself: account, inetOrgPerson and its superclasses, posixAccount, posixGroup, ldapPublicKey, uidObject,sambaSamAccount, groupOfNames and organizationalRole, under any of their names. Those follow from what a person or group has, and a declaration cannot overrule check.

Otherwise startup is refused, naming the block, its position and the class.exampleUnit is STRUCTURAL:

$ authnd check cases/structural.hcl
authnd: cases/structural.hcl:10:20: users "sql" object_classes: exampleUnit is STRUCTURAL, and an entry has exactly one structural chain (RFC 4512 §2.4.2), which authnd chooses: only an AUXILIARY class (§4.1.1) can be declared

go-authn/directory checks the spelling before that: a class is a descriptor, never an OID, a space, a quote or a parenthesis.

Refused too, and for the same reason of keeping the schema honest:

refusedwhy
a file that redefines a definition, even word for wordslapd’s rule: above
a file that is not a regular file, or is over 4 MiBa FIFO would block startup, /dev/zero would never end
a schema block with a variable, a function or ${...}literal values only, as in an .hcl schema file
an undefined class in object_classesa promise nothing can check
a STRUCTURAL class, or one authnd derivesthe list above

What check prints

Four kinds of lines, on top of the usual ones; the startup log carries the same:

  • schema: <file> adds … and schema: the schema block at <file>:<line>:<column> adds …:what each file and each block added, counted as object identifier macros, attribute types and object classes;
  • <file>:<line>:<column>: users "sql" declares … for its people (auser or group block says user "ann" declares … for this person andgroup "staff" declares … for this group): what each source declares;
  • <name> is published without <class>, which its source declares: …,naming the MUST the person lacks;
  • group staff: the configuration file declares supannGroupe and a postgres database declares eduMember; the first is published and the second is ignored (the first source that declares classes for a group decides):two sources disagreeing about a group, which would otherwise be silent.

Attributes dropped for want of a class are the lines is published without <attribute>: no class of the entry allows it; <classes> would thatthe entries already describe: with a declaration they name the class you have not declared.

DIT content rules, name forms and DIT structure rules

From v0.13.0, schema_files and the schema { } block also accept the three kinds of definition that RFC 4512 §4.1.6 and §4.1.7 add to classes and attributes, and authnd enforces them (go-authn/ldap v0.11.0 reads, builds and checks them; the library page says how):

definitionRFC 4512what it sayswhat authnd does with it
DIT content rule§4.1.6for one structural class: which auxiliary classes (AUX) may be added, which attributes are required (MUST), allowed (MAY) or precluded (NOT)shapes each entry (data)
name form§4.1.7.2which attribute names (the RDN) an entry of a structural classholds the tree (configuration)
DIT structure rule§4.1.7.1where a name form may be placed: under the entry governed by the rule its SUP namesholds the tree (configuration)

They are published at cn=Subschema (dITContentRules, nameForms,dITStructureRules) only when there are some. With none, nothing on this page applies, and nothing changes from v0.12.4.

Same example arc

rules.schema below is, like example.schema above, written for this page,under 1.3.6.1.4.1.99999. Use your own arc. The OIDs of the content rule and of inetOrgPerson are the same by definition: a content rule is named after the structural class it is for.

A schema with one of each, and its HCL

In OpenLDAP’s .schema form. ditcontentrule is slapd.conf(5)’s directive;nameform and ditstructurerule are go-authn/ldap’s, since slapd has none(below). authnd also checks the tree it publishes(suffix, ou=people, ou=groups, accounts, people and groups under them), so the file holds five name forms and five structure rules, not one of each:

# Rules for the tree authnd publishes. 1.3.6.1.4.1.99999 is an example arc:
# nobody is assigned it, use your own.

# A content rule belongs to a structural class and takes that class's OID.
# inetOrgPerson (2.16.840.1.113730.3.2.2): posixAccount and uidObject may be
# added, ldapPublicKey may not; telephoneNumber is required; description is
# precluded.
ditcontentrule ( 2.16.840.1.113730.3.2.2 NAME 'examplePersonRule'
	AUX ( posixAccount $ uidObject )
	MUST telephoneNumber
	NOT description )

# A name form says which attribute names an entry of a structural class.
nameform ( 1.3.6.1.4.1.99999.9.1 NAME 'exampleDomainForm' OC domain MUST dc )
nameform ( 1.3.6.1.4.1.99999.9.2 NAME 'exampleUnitForm' OC organizationalUnit MUST ou )
nameform ( 1.3.6.1.4.1.99999.9.3 NAME 'exampleAccountForm' OC account MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.4 NAME 'examplePersonForm' OC inetOrgPerson MUST uid )
nameform ( 1.3.6.1.4.1.99999.9.5 NAME 'examplePosixGroupForm' OC posixGroup MUST cn )

# A structure rule gives a name form a place: the rule ID is a number, SUP
# names the rule of the parent entry.
ditstructurerule ( 1 NAME 'exampleSuffix' FORM exampleDomainForm )
ditstructurerule ( 2 NAME 'exampleUnit' FORM exampleUnitForm SUP 1 )
ditstructurerule ( 3 NAME 'exampleAccounts' FORM exampleAccountForm SUP 2 )
ditstructurerule ( 4 NAME 'examplePersons' FORM examplePersonForm SUP 2 )
ditstructurerule ( 5 NAME 'examplePosixGroups' FORM examplePosixGroupForm SUP 2 )

The same definitions in HCL, as ldapschema v0.11.0 writes them(ldapschema to-hcl rules.schema). Each block is one definition, labelled with its first NAME; a structure rule has an id, the form it places and thesup rules it goes under:

dit_content_rule "examplePersonRule" {
  oid  = "2.16.840.1.113730.3.2.2"
  aux  = ["posixAccount", "uidObject"]
  must = ["telephoneNumber"]
  not  = ["description"]
}

name_form "exampleDomainForm" {
  oid  = "1.3.6.1.4.1.99999.9.1"
  oc   = "domain"
  must = ["dc"]
}

name_form "exampleUnitForm" {
  oid  = "1.3.6.1.4.1.99999.9.2"
  oc   = "organizationalUnit"
  must = ["ou"]
}

name_form "exampleAccountForm" {
  oid  = "1.3.6.1.4.1.99999.9.3"
  oc   = "account"
  must = ["uid"]
}

name_form "examplePersonForm" {
  oid  = "1.3.6.1.4.1.99999.9.4"
  oc   = "inetOrgPerson"
  must = ["uid"]
}

name_form "examplePosixGroupForm" {
  oid  = "1.3.6.1.4.1.99999.9.5"
  oc   = "posixGroup"
  must = ["cn"]
}

dit_structure_rule "exampleSuffix" {
  id   = 1
  form = "exampleDomainForm"
}

dit_structure_rule "exampleUnit" {
  id   = 2
  form = "exampleUnitForm"
  sup  = [1]
}

dit_structure_rule "exampleAccounts" {
  id   = 3
  form = "exampleAccountForm"
  sup  = [2]
}

dit_structure_rule "examplePersons" {
  id   = 4
  form = "examplePersonForm"
  sup  = [2]
}

dit_structure_rule "examplePosixGroups" {
  id   = 5
  form = "examplePosixGroupForm"
  sup  = [2]
}

That is what goes inside a schema { } block, unchanged; the .schema file is what schema_files takes. ldapschema to-schema rules.hcl turns it back into a.schema file with the same definitions, and ldapschema check builds it on top of the standard schema:

$ ldapschema check etc/authnd/rules.schema

What the structure rules do to the tree

With at least one active DIT structure rule, authnd walks the tree it will publish, at startup and in check:

  • the suffix (base_dn), given the class its RDN names: dc adomain, o an organization, ou an organizationalUnit, c acountry, l a locality. A suffix named by any other attribute is refused;
  • ou=people and ou=groups, as organizationalUnits;
  • the RDN attribute authnd names its people by (uid) and its groups by (cn).

A container no rule places, a suffix of a kind no rule has a name form for, a name form that refuses uid or cn, or a container under which nothing authnd publishes could be placed, refuses startup, and check: every refusal at once, naming the DN, the rule or name form and the clause, and never echoing a secret. A person or group whose structural class depends on its data (an sn,a gidNumber) and has no rule under its container is left out and said instead, as team was above: the server starts. With no active structure rule,nothing changes.

A schema whose only structure rule for people, peopleByCN, places a name form that wants cn (accountByCN: OC account MUST cn):

$ authnd check cases/bad.hcl
authnd: DIT structure rules: authnd names its people uid=<name>,ou=people,dc=example,dc=org, and an account named so is refused: the RDN (uid) is allowed by the name form of no DIT structure rule that places account under an entry governed by the rule 2: accountByCN needs cn

authnd names its people uid=<name>: the rules have to allow it. And a schema whose rule for organizationalUnit has no SUP, so that anorganizationalUnit can only be at the root, leaves both ou=people andou=groups without a place, and says both at once:

$ authnd check cases/root.hcl
authnd: DIT structure rules: ou=people,dc=example,dc=org, where authnd publishes its people, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)
DIT structure rules: ou=groups,dc=example,dc=org, where authnd publishes its groups, as an organizationalUnit: no DIT structure rule allows organizationalUnit under an entry governed by the rule suffix (X.501 13.7.5)

Both exit with status 1. The files behind them (cases/bad.schema andcases/root.schema) hold the same five name forms and only the structure rules that make the point.

Where authnd and slapd differ

go-authn/ldap reads the OpenLDAP files, and some of the rules are OpenLDAP’s.These are the differences, said rather than discovered:

  • slapd implements content rules only. It has no directive for name forms or structure rules. Format writes nameform and ditstructurerule keywords, which are this library’s, and slapd refuses them: keep those in the HCL, or in a file only authnd reads. ditcontentrule is slapd’s.
  • An OBSOLETE rule is inactive (RFC 4512 §4.1.6), as is its name form or structure rule. slapd refuses the entry instead.
  • Without a content rule, auxiliary classes are allowed. That is slapd’s behaviour (its SLAP_DISALLOW_AUX_WO_CR flag is set by no disallow keyword), and authnd’s. RFC 4512 §2.4.3 says otherwise; the library offers it as ValidateOptions{StrictAuxiliary: true}, and authnd does not set it.
  • libldap cannot read a structure rule’s SUP. A structure rule with aSUP is read here and not by libldap, so libldap’s refusal of such a file is not a verdict on the file.
  • A file that redefines a rule is refused, even word for word, like every other definition (above).

What it costs

Measured on 2026-10-30 with BenchmarkPublish10k (go-authn/authnd,rules_bench_test.go, -cpu 1) on authnd v0.13.3, which embeds go-authn/ldap v0.11.3: publishing 10,000 people makes 97 allocations per entry with the rules of testdata/rules.schema and 69 without (v0.13.2: 128 and 85; v0.13.0: 416 and 265), and a run takes 42.6 MiB with the rules and 25.7 MiB without (v0.13.2: 54.8 and 33.7; v0.13.0: 147.5 and 88.0). This includes dropping a precluded description and validating again.The times, about 66 ms against 36 ms, are the median of five interleaved runs at a load of 4.8: the rules still cost about 1.8 times as much. The second validation that dropping the description requires and the structure rules’ second read of the DN are among the largest parts of the difference that were attributed.

Upgrading

Nothing changes for a schema without rules: v0.12.4 refused all three kinds, so a configuration that started on it holds none. There is one exception. Aschema { } string that is not valid UTF-8 (an overlong encoding HCL lets through) started on v0.12.4 and is refused now, because it could not be published as it was written.

SUPANN, as the real example

SUPANN is the attribute set of French higher education and research(supannPerson, supannEtablissement, supannEntite…), with eduPerson beside it. RENATER publishes the technical schema, with the others, on its documentation page:

https://services.renater.fr/documentation/supann/supann2021/recommandations/tables_references/schemas_techniques_supann

Download the file from there. It is not reproduced on this site: it states no licence, so this page does not copy it, and a copy here would go stale when RENATER revises it. Then:

sudo install -o root -g authnd -m 0640 supann.schema eduperson.ldif /etc/authnd/
schema_files = ["/etc/authnd/supann.schema", "/etc/authnd/eduperson.ldif"]

users "sql" {
  # ...
  users_attributes     = "select login, sn, etab as \"supannEtablissement\" from staff"
  object_classes       = ["supannPerson", "eduPerson"]
  group_object_classes = ["supannGroupe"]
}

Run authnd check and read the schema: lines first: a file that slapd loads loads here, and one that redefines a standard definition is refused with its line. Then read the published without lines: a person lacking a MUST of supannPerson or eduPerson is published without the class, andcheck names the MUST. Quote an alias where its spelling matters(PostgreSQL lower-cases an unquoted one; seethe entries).
